# 余白リテラル → Spacing/Insets トークン翻訳（と較正値の保護）

> 旧ID: —（2026-07-13 新規・F(2) 残債19ファイル再翻訳が動機）
> 正本コード: `theme/Spacing.kt`（7段スケール `Spacing` object＋**同ファイル内の `Insets` object**＝別ファイルではない）・検査 `tools/check_design_tokens.py` Phase B。

## パターン

Compose の spacing-context（`padding`/`PaddingValues`/`Arrangement.spacedBy`/`Spacer` の height・width）内の
直書き `.dp` は、拡張7段 `Spacing.S{4,8,12,16,24,32,40}`（round-half-up・等距離は大きい側）へ翻訳する。
検査 Phase B が「数値 .dp が spacing-context にある」だけで NG にする＝**値がオンスケールでもトークン参照を強制**。

**機械化の勘所**: 一括変換スクリプトは検査の `get_enclosing_calls`/`is_spacing_context` を**そのまま流用**して
対象を抽出する。同一ロジックで拾う限り「変換後に検査 WARN=0」が保証され、size/border/RoundedCornerShape 等の
非 spacing を巻き込まない（右→左置換でオフセットずれ回避）。

## なぜ「盲目一括置換」が危険か（この翻訳の核心）

スケール外に置くべき値が2クラス混在し、**リンタはこれらを spacing と区別できない**（padding 文脈に居るため一律 NG）:

1. **構造インセット** = 他要素の寸法・回避距離で決まる値（`Insets.*`）。例: FAB 回避 96・本文下クリアランス 60。
2. **較正値** = 特定の視覚目標に合わせ込んだ値（丸めると等式・目標が崩れる）。例: 段落間隔14（+leading で行間）・
   朱印バッジ左下オフセット9（正本 `.seal` の「19dp/左下9」パリティ）・独自タブ縦10（実機#1で ~40px 高に詰めた）。

**落とし穴の機序**: 正本モックはこれらを **CSS の絶対配置（`left`/`top`/`bottom`）で保持**する。検査のモック Phase は
`padding`/`margin`/`gap` しか見ないので**絶対配置値は素通り＝モックは9pxのまま保たれる**。一方 Compose は絶対配置を
持たず**同じ配置を `padding` で表現**するため、一括変換が構造/較正値まで spacing とみなして丸めてしまう
（実際 seal 9→8・タブ 10→12 に潰れた）。結果：**モックは9・コードは8**の silent な乖離が生まれる。

## コミット前の炙り出し（2つの機械スキャン）

コード diff だけ見ても「9→8」は妥当に見えるので、以下で意味の異なる値を先に洗い出してから丸める:

1. **陳腐化コメント突合**: 変更ファイルのコメントから `数字+dp`/`数字+px` を grep し、直近コードの新値と矛盾する行を探す
   （`.padding(vertical = Spacing.S16), // 上下 18dp` のような嘘コメントが、丸めた値の手掛かりになる）。
2. **較正マーカー走査**: コメントの `フィードバック|実機|較正|詰め|揃える|パリティ|正本と同一` を grep。ヒット近傍の
   離散化値は「文書化された目標に合わせ込んだ値」の疑い＝スケール外へ退避（`Insets.*` か命名 `private val` で顕在化）。

**判断の線引き**: 明文化された較正/パリティを持つ値だけ保持し、それ以外は裁定スケールで淡々と丸める
（2dp の光学 nudge 等、文書化のない微小値は S4 へ丸めてよい＝過剰に「較正扱い」しない）。関連＝auto-memory
`agy-mechanical-batch-calibrated-values`。
