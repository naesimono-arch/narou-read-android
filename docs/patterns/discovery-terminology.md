# 発見・検索まわりの用語辞書（1概念=1語）

> 2026-07-12 UX/Design 全層監査 **ia Minor**（15-§C 一語一義）の是正で新設。
> なろう作品を「見つける／探す」領域が **UI 表層で 4 語（見つける／探す／検索／発見）** に呼び分けられ、
> 同じ着地画面を別語で指していた（例:『発見に戻る』『小説を探す』の着地がいずれも「見つける」画面）。
> ここは**この領域の UI 表層文言に用いる語を 1 概念 1 語へ固定する台帳**。コードが正本のため、
> 個々の文字列はコードを読めば分かる。ここは「どの概念にどの語を当て、なぜか」に絞る。

## 前提: 「見つける」と「探す」は別概念（2 語あってよい）

発見領域には**性質の異なる 2 画面**があり、それぞれモック正本（ADR 0005）がタイトルを与えている。
両者は別タスクなので**別語で正しい**。統一すべきは、この 2 概念を指す**第 3・第 4 の同義語**（発見／検索）の乱れ。

| 概念 | 正の語（表層） | モック正本 | 内容 |
|---|---|---|---|
| A: 発見ホーム（ランキング・ジャンル・気分で**受動的に出会う**場） | **見つける** | `discovery-home-D.html` `<h1>見つける</h1>` | order タブ×ランキング＋ジャンル入口＋気分プリセット |
| B: 検索（作品名・作者・キーワードで**能動的に絞り込む**操作/画面） | **探す** | `discovery-search-D.html`（タイトル「検索画面」／画面内 h1「探す」） | 入力欄＋範囲チップ＋履歴＋キュレーション語 |

## 統一ルール（表層文言）

1. **概念 A を指す表層語は「見つける」に固定**。`発見` を UI 表層に出さない。
   - 例: 結果一覧の Up の accessible name 旧「発見に戻る」→「**見つける画面に戻る**」（DiscoveryResultScreen）。
2. **概念 B を指す表層語は「探す」に固定**。単独の表層ラベルとして `検索` を出さない。
   - 例: 発見ホームの 🔍 アイコンの accessible name 旧「検索」→「**探す**」（DiscoveryHomeScreen）。
3. **`検索` は複合・技術ラベルにのみ残す**（`検索範囲`・`検索履歴`・`最近の検索`・`検索条件`）。これらは
   B の内部要素名で、単独の画面/操作呼称ではないため一語一義を破らない。
4. **内部識別子・コメント・ドメイン語は対象外**。コード内の `discovery` パッケージ名、`発見系`・`発見ホーム`
   というコメント/変数の説明語は表層に出ないため `発見` のまま可（英語 domain 名との対応も保つ）。

## 現況（コード側の状態）

- **統一済み（この監査で変更）**:
  - `DiscoveryResultScreen.kt` Up の contentDescription: 発見に戻る → 見つける画面に戻る。
  - `DiscoveryHomeScreen.kt` 検索アイコンの contentDescription: 検索 → 探す。
- **モック記載につき保留（モックと同期が要る＝提案のみ）**: 画面タイトル「見つける」「探す」自体は
  モック正本の文言なので変更しない（本辞書はこの 2 語を正として追認する）。
- **配線依頼（本監査の担当ファイル外＝別レーン/監督で反映）**:
  - `BookshelfScreen.kt` の 🔍 contentDescription「小説を探す」: 着地は概念 A（見つける画面）なのに B の語
    「探す」を使い、ラベルと着地がねじれている。**着地に合わせ「見つける」へ**（または着地を検索画面へ変える）。
    → どちらが正かは「本棚の 🔍 は受動発見へ送るか能動検索へ送るか」の設計判断。現状の着地（発見ホーム）
    を保つなら文言を「見つける」へ。
  - `BookshelfScreen.kt` 空棚 CTA「新しい物語を見つける」: 概念 A と整合（変更不要）。
  - `ContinuationCard.kt`「なろうで続きを探す」: これは「なろう側で続きの話を**開く**」外部導線であり、
    発見/検索領域の A・B とは別文脈のため対象外（“探す”の一般語）。
