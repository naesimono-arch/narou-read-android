# 多ブランチ統合の手順パターン（統合ブランチ --no-ff → main へ ff-only）

> 2026-07-08 の API系全ブランチ統合（`integrate/merge-all-20260708` → `fd758df`）で確立した
> **リポジトリ運用のパターン**（コードでなく手順が正本）。次回の多ブランチ統合はこの形で行う。

## 手順

1. main から統合ブランチを切る（例: `integrate/merge-all-YYYYMMDD`）
2. そこへ各作業ブランチを `--no-ff` で順にマージし、競合解消・ドキュメント台帳の合併・
   テスト（`testDebugUnitTest`）まで**統合ブランチ上で完了**させる
3. main を `git merge --ff-only <統合ブランチ>` で進める

## なぜこの形か（main 保護運用との相性）

- **センチネル発行が1回で済む**: main への書き込み（guard_commit_branch の人間発行センチネル）は
  最後の ff-only の1回だけ。main 上で N 本を直接マージすると N 回の発行と N 回の競合解消が main を汚す。
- **「main に載る木」＝「テストを通した木」が完全一致**: ff-only はコミットを新造しないため、
  統合ブランチで全緑を確認した木がバイト単位でそのまま main になる（マージ後の再解決・再テスト不要）。
- **失敗が無かったことにできる**: 統合が破綻したら統合ブランチを削除するだけで main は無傷。

## 罠（2026-07-08 実測）

- **マージ中のビルド／テストが Room スキーマ JSON（`android/app/schemas/*.json`）を再生成する**。
  旧版 JSON は「実機が保持する identity hash の記録」（task_diary #39 追補・v9→v10 再スタンプの根拠データ）
  なので、統合中のビルドで上書きされていないか確認し、**必要なら checkout で保全してからコミット**すること。
- **連番資源の再衝突チェックを統合前に**: 並列レーンが Room version・task_diary #N・ADR 番号を
  同番で消費していると統合時に衝突する（前例=2026-07-08 に task_diary 二重採番3件を解消）。
  全レーン grep の作法は CLAUDE.md「task_diary自動更新」ルールと `/db-migration` スキル参照。
