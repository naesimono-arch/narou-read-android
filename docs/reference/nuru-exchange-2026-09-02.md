- 動機はコストでない: 生成だけ移しても節約は約 3%（コスト主体は cache_read）。動機は「本体のコンテキスト保護」と「独立した第二の目」に置く。
- 発注文（ブリーフ）の必須項目（/orchestration skill）: 必読リスト（読む順番つき）／曖昧語は仮説分解／裁定は「確定事項」として明文化／完了定義の外給（存在確認可能な成果物・自己 diff・ゲート GREEN・報告様式）／想定ターン規模（子 1 体 30 ターン目安）／編集ファイルの所有権を互いに素に全数列挙。定型規律は SubagentStart フックが自動注入するので発注文にはタスク固有の内容だけ書く。
- 受け取り: 報告は 8〜25 行上限＋必須項目（変更ファイル／真因・機序／判断／ゲート出力要約）。自己申告 GREEN は信じず、ゲートは本体が再実行。
- 排他: 同一ファイルを触る体は並走させない（本体がキューを持つ）。Gradle など重いジョブは tools/gwlock.sh が作業ツリー単位でロック（理由は資源でなくゲート健全性）。真の並列は git worktree（wt-new）でツリーを分ける。
- 「Read の前に、このターンで自分が編集するか決める」＝編集しないなら調査 Read はサブへ。確かめるためだけに 3 ファイル以上開くなら必ず委譲。
- 発注文の知見: 厚さでなく「枠と完了条件」（95 文字でも網羅は上限に張り付く）。Opus を実行者にするときは完了定義を外給（近似禁止・真因・影響面の全組合せ・外部事実は一次ソース 2 点照合）。
- 計測: サブのツール使用数をフックで記録（delegation-stats.jsonl）し、子の適正長（谷 ~30 ターン）を再較正。

## 1. プロジェクト概要（3行）

## 2. 文書構造

- **正典は 1 つだけ**：`AGENTS.md`（171 行・全指示の実体）。Claude Code が自動読込する `CLAUDE.md` は**「AGENTS.md を読め」と書いてあるだけのポインタ**で、内容を持たない。
- **入口**：`HANDOVER.md`（316 行）＝冷えた状態から再開するときの現在地スナップショット。**薄く保つ**のが規約。
- **書く場所は 4 つしかない**（これが管理コストを抑える中核）：

| 何を | どこへ | 更新の型 |
|---|---|---|
| 現在地（いまどこ・次に何を） | `HANDOVER.md` | 上書き・薄く |
| 仮説の生死（何が確定し何が撤回されたか） | `docs/loops/LOOP-NNNN-*.md` | **1件1ファイル・本文は不変** |
| 観測と数値（生の実測値・論文精読） | `docs/records/evidence.md` | append（追記のみ） |
| 経緯（何をやってどう転んだか） | `docs/records/diary.md` | append |

  実測サイズ＝evidence **9,994 行**（`## 節` 75・`### 小節` 455）／diary **3,130 行**／loops **16 本**（ls）。
- **唯一かつ最重要のルール＝「手で追従し続ける二次ビューを作らない」**。理由は、一次ソースは追記で伸びるのに二次ビューには更新トリガーが無く、必ず腐るから。
  - 実例1：戦略文書が **14 セッション**「未測定」のまま放置され、しかも自ら「速習に使え」と名乗っていた（現在は凍結扱い）。
  - 実例2：別エージェントが作った指示書の 27KB 全複製が、**生成された時点で既に 3 箇所ずれていた**（実在しないパス 2 件＋事実改変 1 件）。
  - **∴ 主張が覆ったら書き換えず、新しい LOOP ファイルを 1 本書いて旧ファイルの Status に `Superseded by` を 1 行足す**（ADR 方式）。更新箇所が常に 1 行なので追従コストが積み上がらない。
- **死んだ経路のファイルは消さず、ファイル先頭に赤字で「死んでいる」と宣言する**（手順書は中身が正しく読めてしまうので、生死は本文でなく先頭で宣言）。
- **他ファイルへの参照は行番号で書かず、grep で一意にヒットする文字列（見出し・関数名）で指す**。実測＝同一ファイル内の行番号参照は **20 件中 9 件（45%）が着手前から既に腐っており**、別ファイルを指す参照は **20 件中 17 件（85%）**。しかも修理のための行挿入で、それまで正しかった 3 件が即座にずれた。例外＝日付つき歴史文書は行番号のまま残し、冒頭注記で「ずれている件数」だけ伝える（書き換えは記録の改変になるため）。

- **課題台帳**：`backlog-zero-*.md` に **D-01〜D-139 の 139 行**＋親項目 P **4 行**（`grep -c '^| D-'`）。各行が状態記号（済／部分／保留／裁定待ち）を持つ。判断が要る項目の待ち行列は別ファイル `rulings-queue-*.md`（1,052 行）。**件数は毎回スクリプトで数え直して突合する**（写した数字は信用しない）。
- **preflight（出発前チェック）**：`code/preflight.py` が **86 本**の検査を通し実行する。内訳は `--list` の出力が正典で、**本数を md に写さない**。
- **員数宣言ファイル**：`docs/records/preflight_roster.tsv`（161 行）に、検査 1 本ごとの name / group / kind / 引数 / 警告マーカーを**人が手で宣言**する。実測＝full 50・quick 36（合計 86）、うち py 82・bash 3・uv 1。
  - **このファイルの生成コマンドは作らない**——生成できるなら番人ではない。実装から期待値を引いた瞬間に「実装が自分自身を検査する」自己参照になる。照合器が毎走「宣言 ↔ import した実体 ↔ ソースの AST リテラル」の 3 系統一致を検査する。
  - 発端は実測事故＝員数の番人が固定値 8 に対し実測 13 本で、**5 本まで無言で消せる**状態だった。
- **期待値は「凍結された仕様」から引き、実装から引かない**。実装から引くと、実装が誤った瞬間に**検知が誤りを守る側へ回る**。実例＝ある検査が誤った式を期待値に固定してしまい、**正しい式へ戻すと必ず FAIL する**状態になっていた。検知を書くときは「この期待値の出所は仕様か実装か」を 1 行残す。
- **キルテスト**：新設した検知は**わざと壊して鳴ることを先に確認してから**登録する。roster 上で名前に killtest を含む Step は **20 本**、golden（合成 fixture で道具の振る舞いを固定する型）系は 2 本（name 列を集計）。設計思想は次の §3b。落とし穴の実測＝キルテストは「**変異が違反ですらないものに化ける**」ことで黙る（同型事故 3 件）。
- **監査で穴が見つかるたびに機械検知クラスを増刷する**（発見の都度）。新規の検知は**初走でほぼ必ず何か当てている**（実例：改行コード検知の新設初走で、Linux へ渡すと即死する実在の違反を 1 件検出）。
- ただし**機械と LLM は相補的**：ある回の実測では LLM 監査が見つけた 21 件のうち preflight が拾えたものは **0 件**だった。順序は固定＝**機械 → LLM**。

## 3b. 検知・テストの設計思想（このプロジェクトで一番作り込んだ部分）

### (A) 参照追跡＝文書中の数値・引用・出所を機械で突合する

- **問題設定**：このプロジェクトは「冷えた状態から台帳を読んで再開する」ので、**台帳の数字が間違うと次のセッションの前提が丸ごと間違う**。実際に再現不能・誤りの数字が 3 件見つかった（値の出所が不明／別ファイルの値の誤転記／算出コードがそもそも存在しない）。**3 件とも「値がずれた」のではなく「主張と根拠を結ぶリンクが無い」失敗**だった。
- **大原則＝値は人が書かない。** 人が書くのは「この主張はここを指す」という宣言だけ。3 ファイル構成：
  1. `numbers_manifest.tsv`（**人が編集**）＝ key / 出所ファイル / JSON パス / 桁 / 備考。**値の欄が無い**。
  2. `numbers.json`（**コードが生成・人は絶対に編集しない**）＝ key → 値・出所・出所ファイルの sha256・生成時刻。現在 **940 キー**（`_n_keys`）。
  3. markdown 側の**引用タグ**＝数値の直後に `〔#key〕`。例：`3B **0.380**〔#s23.ladder.b1_k300.3b〕`。
  `--extract` が 1→2 を作り、`--verify` が 3 と 2 を突合する（preflight の quick に登録）。
- **静かな破れの実例**：`--verify` が出所ファイルの sha を**読み直していなかった**時期があり、出所 JSON を作り直しても manifest を書き替えても「全一致」を返していた。＝「値は人が書かない」の原則が**「引いた時点で固定される」形で静かに破れる**。sha 再照合を足して塞いだ。
- **live markdown だけを見るマスク**（直近の追補）：`--verify` が名乗るのは「台帳が **live に主張している数値**が出所と一致すること」であって「`〔#…〕` という文字列がどこかに出てくること」ではない。∴ markdown が inert と定める領域（バッククォートのコードスパン／フェンス）の中身は**引用**であって照合対象外。動機が重要で、**壊れた書式の実例を追記専用台帳に引用した瞬間に検査器が赤くなり、append 台帳ではその行を直せない＝番人が永久に赤いまま**になる。台帳リント hook も同じ区別を先に凍結していた。
- **除外は fail-closed（黙る側へ倒さない）3 条**：F1 コードスパンの開き記号に同じ長さの閉じ記号が同じ行に無ければ**マスクしない**／F2 コードスパンは行をまたがない（前行の閉じ忘れが次行を黙らせない）／F3 フェンス行が奇数（閉じ忘れ）ならフェンスを 1 つもマスクしない。**除外機構そのものが「静かに全部を黙らせる」形で腐るのが最悪の腐り方**なので、曖昧なときは必ず**鳴る側**へ倒す。
- **マスクは長さと列位置を保存する**（中身を空白へ潰す）＝タグの行番号と「直前 200 字」の切り出し位置が 1 文字も動かない。長さが変われば**マスクを使わず生テキストで照合**。数値の読み取りは常に生テキストから＝マスクが決めるのは「どのタグが主張か」だけ。
- **黙る条件も fail-closed**：引用タグの定義は「数値の直後に `〔#key〕`」なので、(a) 直前の数値 と (b) manifest の key は**どちらもタグの構成要素**。∴ 黙るのは **両方欠けたときだけ**（数値があって key が未知＝リンク切れ／key があって数値が無い＝主張から剥がれた、はどちらも鳴る）。黙らせた件数と場所は毎走印字し、preflight の警告へ昇格させる。
- **出所の側も守る**：成果物の meta に刻む sha256 は「**書き終えたファイルをディスクから読み直したバイト列の sha**」に統一し、`out_sha256_is_disk_bytes: true` という自己申告キーを置いて毎走検査する。発端＝メモリ上の文字列の sha を刻んでおり、書き込み時の改行変換でディスク実体と一致していなかった（LF 版と実ファイルで sha が別）。**期待値は writer の実装から 1 つも引かない**（実装をオラクルにすると「両方いっしょに壊れる」形で無音になる）。
- **台帳インフラの整合そのものも番人が見る**：追記専用台帳の**過去の行が 1 行も消えていないか**（行の多重集合で比較）／`numbers.json` が抽出器の産物のままか（全エントリの生成者・エントリ数・manifest の実 sha）／**訂正記録が挙げる根拠**（リポジトリ相対パス・節番号・7〜40 桁の hex）が実在するか。
- **参照の腐り検知**：他ファイルを行番号で指した参照について、参照文の**近傍にある識別子が指し先でどこに定義されているか**を毎走ツリーから引き、引用された行域と重なるかを見る。**期待値は実装でも凍結件数表でもなく「参照文それ自身」**。近傍の任意の語で判定した試作版は **100 件中 51 件を誤検出**したので、候補を「指し先で定義されているシンボル」に絞り、定義区間はデコレータ行から本体末尾まで採った（参照は def 行でなく本体の一部を指すことが多い）。**番人は鳴きすぎると読まれなくなる ∴ 取りこぼしは許容し偽陽性ゼロを優先**する。
- **孤児化の検知**：構想文書が「冷間再開の実読経路」から名前で辿れるか（推移閉包）を見る。書く場所は規約が定めるが**読まれる導線は定めていない** ∴ ファイルは在るのに冷えた読者には存在しない、という別クラスの腐りが起きる。この番人は **read-only で導線を張らない**（どこから張るかは意味の判断＝人の仕事）。

### (B) killtest＝「番人が本当に鳴くか」を壊した別世界で測る

- **思想**：検算器は**黙って緑を返す**形で腐る（語彙が古い／アンカーが動いた／表の書式が変わった）。∴ 台帳やコードの**複製**に 1 箇所ずつ壊れ方を注入し、**鳴るべきものだけが鳴る**ことを見る。roster 上で名前に `killtest` を含む Step は **20 本**。
- **合格条件は終了コードだけではない**：各変異が「**どの検査を鳴らすはずか**」を宣言し、**宣言した文言が stderr に出ていること**まで見る（別の検査が偶然鳴っただけを成立扱いにしない）。
- **変異アンカーの実在も検査する**：文面が変わってアンカーが当たらなくなったら、「変異していないものを鳴らなかった」という偽陽性ではなく**キルテスト自身の FAIL** にする。
- **構造ロケータ化の経緯**（一番効いた設計変更）：初版は変異アンカーを台帳の**文字列リテラル**（合計値や内訳の数字）で持っていた。台帳を同期して数が動いた回に **20 脚中 7 脚のアンカーが一斉に外れた**——**台帳は正しく、腐っていたのはキルテストの方**。台帳は「同期のたびに数が動く」文書なので、値をリテラルで焼く限り同期のたびに再発する。∴ **形だけを焼き、値は実行時に現物から読む**（「合計行を探してその中の数を +1」「表の最後のデータ行を消す」「状態記号を検算器と同じ物差しで探して書き換える」）。期待文言も現物から数を読んで組み立てる ∴ 「終了コードだけで成立にしない」性質は 1 つも緩めていない。
- **射程を先に宣言する**：〈射程内〉対照（無傷の複製で終了コード 0）＋各変異が宣言どおりの検査で鳴ること。〈射程外〉網羅性（変異の列挙は閉じない）・本物の台帳での挙動・検算器が数える「意味」の正しさ。
- **「鳴らない変異を、鳴らないと記録する」ブロック**を持つ例がある：重い計算層は静的 fixture で、再走して照合する検知器が**1 本も存在しない**（再走に 2,408 秒）。壊しても全検知器が無音になる——**この無音を専用の変異群で毎走実証し、合否には算入しない**。守れない範囲を機械で可視化しておく、という発想。
- **golden との違い**：killtest は「番人が鳴るか」を測る。**golden（ゴールデンファイルテスト）は道具そのものの振る舞いを合成 fixture で固定する**。実例＝数値照合ツールの**抽出器**を守る golden は、実リポジトリを一切読まず（manifest も results も読まない）、ファイル内の文字列リテラルだけを一時ディレクトリへ展開する＝決定的・オフライン・数秒。**期待値は全部ツールの docstring（凍結仕様）と fixture から手で導き、実装を走らせて出た値を貼らない**。fixture の各値は「この分岐を踏ませるために置いた」ものなので、実装を見ずに期待値が導ける（例：`{"a.b": 1.5, "a": {"b": 2.5}}` に `dotted.a.b` を当てれば、最長一致なら 1.5・短一致へ退化すれば 2.5）。そして **golden 自身も killtest を持つ**（roster 上で対になっている）。
- golden の docstring は**守れない領域を正直に列挙する**（「隠すと『検証済み』の誤った安心を生む」）。

### (C) 員数宣言・quick と全走・判定汚染・selftest

- **員数宣言（roster）を生成しない理由**：preflight の Step 表は **1 行消せば 1 本の検知が消え、消えたことを誰も見ていない**。`len(STEPS)` を期待値にすると「実装が自分自身を検査する」自己参照になる ∴ 期待値は別ファイルの宣言に置く。照合は **5 点**＝(1) 宣言 ↔ import した実体 (2) 宣言 ↔ **AST で読んだリテラル引数** (3) 宣言の員数コメント ↔ 実数 (4) エントリポイントが実在ファイルか (5) **環境変数を変えて import し直しても Step 表が変わらないか**。
- **引数まで凍結する理由**：args は文言ではなく**実行対象**。Step 行を消さずに引数を no-op スクリプトへ差し替えるだけで検知は死ぬ。**警告マーカーも凍結する**——マーカーを空にする編集が「検知の存在理由そのもの」を黙らせた実例がある（終了コードに判定を持たない Step では、警告行が唯一の判定チャネルだった）。
- **quick と全走の区別**：quick **36 本**（台帳・数値・lint 系＝LLM 監査を投げる前や編集の合間に回す）／全走 **86 本**（重い smoke・killtest 込み・締めの前）。
- **判定汚染の検知**（全走の**先頭固定**）：リポジトリのコードを走らせている「**自分以外の**」python プロセスを見る。危ないのは落ちる時ではなく**落ちない時**——片方が書いている途中の JSON をもう片方が読んで**それらしい数字**を出すと判定が静かに汚染される（タイムスタンプも sha も「壊れている」とは言わない）。自分・祖先・子孫は除外（preflight が起動した Step を誤検知しないため）。書き方に依存せず拾い、作業ディレクトリが取れず解決できないものは**疑う側へ倒す**（承知で並走するときだけ環境変数で明示的に降格）。
- **selftest**：フック類は自分自身に `--selftest` を持ち、preflight から呼ばれる（文脈予算フックは 14 ケース、台帳リント hook は selftest と killtest の両方を持つ）。**fail-open で作った部品ほど、壊れていないことを外から見る必要がある**。

### (D) 「期待値は凍結仕様から引き、実装から引かない」の実例

- 走行またぎの再開整合を見る番人が、前セッションの**誤った式**を期待値に固定してしまい、**凍結どおりの正しい式へ戻すと必ず FAIL する**状態になっていた＝検知が誤りを守る側へ回った。以後、検知を書くときは「この期待値の出所は仕様か実装か」を 1 行残す規約になった。
- 逆向きの安全弁＝**ベースライン方式**：遡って全部落とすと preflight が永久に赤くなり、「**赤いのが常態**」になった瞬間に検知器の価値がゼロになる。∴ 現況を凍結し**新規・増加だけ FAIL**。ただし **「鳴ったからベースラインを更新する」は禁止**（貼り替えた瞬間にその lint の存在意義が消える）。

### (E) 番人が 1 本も鳴かなかった直近の事故（改行コード）

- 2026-09-02、Windows の `Path.write_text()`（改行指定なし）が LF を CRLF へ黙って変換し、**追記台帳 5 本（うち 1 本は 8,976 行）が丸ごと CRLF 化**した（全面書き換えとして commit される寸前）。**既存の番人は 1 本も鳴らなかった**——台帳リントも索引生成器も universal newlines（改行差を吸収する読み方）で読むので、**改行の差は判定に原理的に現れない**。
- 新設した検知の**期待値は実装ではなくリポジトリ自身の宣言 3 点**から引く：`.gitattributes` の属性（毎走 `git check-attr` で引き、検知本体に写さない）／`git ls-files --eol` の索引側／`git config core.autocrlf`。被検査側のコードからは 1 バイトも引かず、**件数のベースラインも持たない**。
- **判定線は「危険の在処」を実測してから引いた**：無宣言ファイルと `eol=lf` 宣言は add 時に正規化されて**同一 blob**（ただし後者は作業木を直接読む消費者＝bash が壊れる）／`-text` 宣言は変換が完全停止しているので**別 blob**＝全面書き換え＋出所 sha の全滅。∴ 「索引が LF なのに作業木が CRLF なら一律違反」ではなく**変換方針ごとに 4 検査**へ分けた（4 つ目は**裸 CR**＝CRLF の一部でない CR＝二重変換の署名）。
- **新設初走で実在の違反を 1 件検出**：`.gitattributes` が LF を宣言しているシェルスクリプトの作業木が CRLF ＝ Linux 側へ渡すと行末 CR で即死する経路。

### (F) そちら（Android アプリ）へ移植しうる考え方 3 点

1. **「値は人が書かない」を、数字が載る文書すべてに効かせる**。README・リリースノート・設計書の測定値（起動時間・APK サイズ・カバレッジ・ベンチ結果）は、人は**宣言（key と出所の指定）だけ**を書き、値はビルド成果物から引いて突合する。真の失敗様式は「値のずれ」ではなく**リンクの不在**。
2. **抑制・除外の機構は fail-closed に作る**。lint 抑制・コード引用の除外・baseline ファイルは、曖昧なときに黙る側へ倒すと「静かに全部を黙らせる」形で腐る。閉じ忘れを検出したら**マスクを一切適用しない**が正しい既定。ベースラインを使うなら「鳴ったから更新する、は禁止」を明文化する。
3. **CI のチェックが本当に鳴るかを、壊した別世界で常設的に測る**。(i) 合格は終了コードだけでなく**宣言したメッセージが出たこと**まで見る (ii) 注入アンカーは値のリテラルでなく**構造**で指す（バージョン番号や件数を焼くと、更新のたびに脚が一斉に外れて「テストの方が腐る」）(iii) **守れない範囲を docstring に列挙する**——無音の領域を可視化しておかないと「検証済み」の誤った安心が残る。

## 4. セッション運用

- **1 ループ／1 セッション＝1 コミット**。機能別の分割（code: / docs: …）はしない。実際にやったら「skill 圧縮」という 1 つの作業が 4 コミットに割れ、**どれも単独では戻す意味を持たなかった**。研究の単位は機能ではなく仮説の一巡。
- **件名は「そのセッションで何が起きたか」を 1 行＋数字**。本文に「なぜ」を数字と根拠つきで書く。作業中の退避コミットは自由に作り、最後に squash して 1 本にする。実際の件名は 200〜400 字級になることもある（後から読んで分かることを優先）。
- **締めは一体**＝`evidence §NN` ＋ `diary 第N` ＋ `LOOP-NNNN` ＋ `HANDOVER` を同じコミットに入れる。分けると「loops はあるが HANDOVER が古い」という壊れた中間状態ができる。
- **締めた直後にしか値が確定しない番人が 2 本ある**（HANDOVER の鮮度ヘッダの親コミット sha・締めコミットの diff を見る一体性検査）。これらは**締め前の全走には原理的に映らない**ので、締めコミット直後に静止した作業木で再走して緑を確認する。FAIL したら amend せず修正コミットを重ねる（締めの diff は不変にする）。
- **記録層の役割分担**：evidence＝観測と数値の唯一の出所／diary＝経緯と決定の時系列／HANDOVER＝現在地と次アクションと導線だけ。**HANDOVER にセッション結果のブロックを積まない**——積んだ結果、入口が **6 セッション前**を指す事故が起きた。2026-08-30 の実測では 693 行のうち **434 行（63%）が「締めた」節**で、現在地に着くまで 498 行読まされていた。畳んで 300 行にし、**「中身の 63% が履歴」を機械で止める検知を増刷**（総行数しか見ない従来の検知は素通しだった）。
- **relay（セッションの引き継ぎ）**：コンテキストが嵩んだら畳んで新セッションへ渡す。引き継ぎ文書は `logs/relay-YYYY-MM-DD-HHMM.md` に置き、**15 本**蓄積（ls で集計）。relay コミットは件名を「第N」で始めない（締め判定の対象を動かさないため）。
- **Stop フックによる文脈予算**：`.claude/hooks/check_context_budget.py`。1 ターンの費用はその時点のコンテキスト長そのもの（毎ターン全長を読み直す）で、セッション累積は **O(n²)**。実測（291 セッション／45,148 ターン横断）＝セッション長 5〜25 ターンで 1 ターン 53.0k、401 ターン超で **317.5k（6.0 倍）**。
  - 判定は**絶対値ではなく「床からの差」**：床＝そのセッション最初の assistant ターンのコンテキスト長（会話が 1 文字も積まれる前の固定注入ぶん・実測で中央 45,441・±20k 動く）。**`ctx − floor >= 75,000` で 1 セッション 1 回だけ通告**。
  - **フックは検知だけで実行しない**——引き継ぎ文書の作成は「何が終わって何が途中か」の判断であり、コードには書けない。全経路 exit 0 の fail-open（壊れたら通告が消える＝ユーザーを絶対に止めない）にし、**壊れていないことは外から preflight とキルテストで見る**。
  - 他に常設フックは 3 本：追記台帳の構造破損検知（Write/Edit ごとに発火）・未コミット退避（Stop/PreCompact）・セッション開始時ガード。**Stop フックでの preflight 自動起動は無効化済み**＝代わりに「セッションを終える時にコードは preflight が通る状態にする」という規約が単独の防波堤。

## 5. サブエージェント運用

- **本体はオーケストレーター専任**（3 層構成）＝本体はファイルを直接読まず全部委譲し、**排他はレーン（作業の束）単位のファイル集合**で取る。「別の行だけ触る」も禁止（走行中の監査を巻き込んで偽 NG が 5 件出た実測がある）。追記台帳への書き込みは同時 1 レーンのみ、書く前に最新末尾を読んでから追記する。
- **発注文に書くのは 4 つだけ**：目的／検収条件／排他するファイル／報告書式。**手法は正典へのアンカーで指す**（発注文に手法を写すと二次ビューになる）。
- **監査は 4 種別。混ぜない**（混ぜると観点が薄まり報告が散文化してトークンだけ増える）：
  - **A 実装監査**＝GPU に金を払う前／自分がコードを直した直後。**最優先**（判定はやり直せるが焼いた GPU 時間は戻らない）。最も当たる型＝「GPU を使い切った後にだけ通る経路 × smoke が通らない経路」。
  - **B 反対査読**＝結論を台帳に書く前。主張を 8〜13 件に列挙して渡す。変種 **B′ 偽陰性監査**＝「撤回しすぎていないか」を問う（撤回は台帳では安全側に見えるが、次の実験の使い道を誤らせる点で偽陽性と同コスト。実測＝撤回 4 件中 3 件に問題）。
  - **C 設計監査**＝事前登録を書いた時。**D 数値監査**＝LLM 不要、機械で照合。
- **並列の分割軸は「ファイル」でなく「観点」**（非破壊性／終端到達性／実行キューの構造／設計の反対査読）。ある回はこの 4 観点で並列に投げ、**当たった欠陥の種類がまったく違い重なりはほぼ無かった**。ファイルで割ると同じ観点が重複し、逆に誰も見ない観点が残る。
- **もう 1 本の分割線＝同じ不変条件を「独立に二度実装」させる**（互いを見せない）。階層で割るとインターフェースに穴が開き、二度実装なら開かない。ただし**一致は正しさの証明ではない**（両方が実装から期待値を引くと同じ誤りへ収束する）。割れたら多数決にせず両方保留し、凍結宣言に当たり直す。
- **既知欠陥の再報告防止**：`known-defects.md`（804 行）を毎回添付し「ここに載っているものは再報告禁止」と明記。セクションは A（修正済み・A-1〜A-21）／B（ガード済みの既知制約）／C（シロ確認済み）／**D（確定した誤指摘）**／E（未解決として既知）／**Z（卒業＝機械検知が守るので添付しない）**。
  - **卒業の規律**＝機械検知に変換できた欠陥は Z へ**移す（消さない）**。条件は (1) 検知を Step 名で名指しできる (2) その壊し方で鳴る実測記録がある、の 2 つ。**説明文が「守っている」と名乗るだけでは卒業させない**（名乗りと実態のずれが 3 例実在）。検知を消したり射程を縮めたら Z より上へ戻す（卒業は不可逆ではない）。
- **採用前の検問 3 つ（省略不可）**：①数値の訂正は真の出所を特定してから（候補の出所を 1 つ反証しても特定にはならない。これを飛ばして**正しい値を誤った値に書き換えた**事故がある）／②誤指摘は実在する（機序を自分で再現できるか確認）／③監査自身にも疑いを当てる（格下げ方向のバイアスも検出対象）。**修正したら、その修正をもう一度監査に見せる**（修正は新しい欠陥の発生源＝実例 5 件、1 巡で足りず 2 巡回した回もある）。
- トークン規律＝巨大台帳は全読み禁止（節と範囲を指定して渡す）・報告フォーマット固定（重大度／ファイル:行／機序／発火条件／提案）・「たぶん大丈夫」は報告させない・読んだファイルの中身を報告に貼らせない・同じ軸に 2 本投げない。

## 6. 外部独立監査

- **隔離環境**：プロジェクト外の兄弟ディレクトリを新設し、環境説明だけの `CLAUDE.md`（「このディレクトリの外を読むな」明記）＋不変のブリーフ＋一次資料だけを置く。**親〜ホームの指示書にプロジェクト記述が無いこと**を確認し、git init して引き渡し点を固定する。
- **メモリ鍵の分離**：エージェントの記憶キーは作業ディレクトリ名から生成され、**非 ASCII 文字は `-` に潰される**。ゆえに非 ASCII を含む別名でも鍵が衝突しうる（実際に衝突した）。∴ 環境は **ASCII 名で立てる**。衝突したら**回収後に同鍵配下のメモリファイルの有無を実測で検査する**（実測＝自動メモリの書き込み 0 件＝汚染なし）。なお新規フォルダで立てたセッションは信頼確認画面で待機したまま登録されず宛先として使えない＝**発注前に一度人手で起動して登録まで通す**。
- **盲検ラウンド**（`return-01`〜`return-09` の 9 本）＝内部の判定・死んだ仮説・実測値を**意図的に伏せて**外部思考者に渡し、共通盲点を炙り出す。規約は事前登録ファイル `prereg-NN.md` が正典で、**読んだ後は書き換えず後継を立てる**。同じブリーフを引き続けると最頻回答が繰り返し出るだけなので、毎回「変奏」（系統を変える＞役割を変える＞最頻回答の名指し禁止）を決める。
- **裁定ラウンド（別種・初回 ruling-01）**＝内部で決めきれない判断を外部に委ねる。盲検とは逆に**内部資料を全部渡す**（汚染規律は適用しない）。判定対象 55 件・回収物 939 行。
  - **二段設計**：第1段＝内部推奨を封じたファイルを**開けないまま**全件を裁定（各件に 裁定／理由／根拠の所在／**何が観測されたら翻すか**）→ 第1段を別名の凍結ファイルに確定 → 第2段＝封を開けて一致／不一致を**追記のみ**（第1段の本文は書き換えない）。
  - **検証は文面の申告ではなく機械で**：発注時に区切り行を指定しておき、回収時に `head -n <区切り行>` と凍結ファイルを `cmp` して byte 同一を実測（実測＝両ファイルとも 854 行目・rc=0）。突合結果＝封に推奨があった 31 件中 一致 28／不一致 2／時点のみ不一致 1、**推奨を読んで裁定を変えた件 0**。
  - **封の漏洩**が事前査読の必須観点。実例＝スナップショットに入れたログの中に封と同一の推奨行が残っており、封を開けずに到達できた。塞ぎ方＝該当行を伏せ字 1 行へ置換し**行数を保存する**（`ファイル:行` の出所が有効なまま＝根拠の検証可能性を壊さない）。実測 86 行／13 ファイル。照合を完全一致で実装すると**封の一文を一部として含む行を取りこぼす**ので部分一致（25 字以上）へ作り直して残存 0 を実測した。
  - **較正回**：ラウンドの検出力そのものを測る回を挟む（既知解プローブを仕込む＋回収した生 JSON を独自に集計し直す）。実測＝プローブは部分検出（3 レーン同一結論だが機序が凍結記載と逆側）・独自集計は 6/6 一致。
  - **限界の一次観測**＝裁定書は発注時点のスナップショットを見ているので、**現物とずれた前提が 3 件**あった（既に執行済みの件など）。ただし判断の枝は 3 件とも生き残った。

## 7. 事故から得た規則

**常設規則 12 項の要旨**（本体指示書の索引・実体は各アンカー先）：①手で追従する二次ビューを作らない（最重要）／②`CLAUDE.md` に内容を二重に持たない／③検知の員数宣言の生成コマンドを作らない／④監査で穴が見つかるたび機械検知を増刷／⑤増刷した検知の期待値は凍結仕様から引く／⑥コミットの機能別分割をしない／⑦旧コミット形式は廃止のまま／⑧本文が切れている論文 md は引用に使わず txt を使う／⑨事前登録は読んだ後に書き換えず後継を立てる／⑩欠番（削除理由は別ファイルへ移送＝削除ではない）／⑪外部発注文・回答の原文を本体セッションで読まない（本体が扱うのは sha256・件数・パスのみ、原文はサブエージェントへ隔離）／⑫未実測の因果を断定しない（観測と推論を分けて書き、記録中の件数は引用前に数え直す）。

代表的な事故と、そこから立った規則：

1. **入口文書が 6 セッション前を指した** → HANDOVER にセッション結果を積まない＋「履歴が本文の 63%」を機械で止める検知を増刷。
2. **行番号参照の 45〜85% が腐っていた** → 参照は grep アンカーで指す。修理のための行挿入自体が「1 コミットで一斉に腐る」を実演した。
3. **検知が誤った実装を守る側に回った**（正しい式に戻すと必ず FAIL する状態） → 期待値は凍結仕様から引き、出所を 1 行残す。
4. **員数の番人が固定値で、5 本まで無言で消せた** → 人が手で書く員数宣言＋3 系統照合。生成コマンドは作らない。
5. **正しい値を誤った値に書き換えた** → 訂正前に 3 点（同じ量が他ファイルに無いか全走査／後発版・増強版が正典か／生成スクリプトの docstring とコミットメッセージ）を通す。通せない訂正は保留にして、そう報告する。
6. **Windows のファイル書き込み API が改行を黙って変換し、追記台帳 5 本が丸ごと書き換わった**（全面置換として commit される寸前）。**既存の検知は 1 本も鳴らなかった**——どれも universal newlines で読むので改行事故が原理的に映らない → 改行専用の検知を新設。新設初走で、Linux 側へ渡すと即死する実在の違反を 1 件検出。
7. **キルテストが「変異が違反ですらないものに化ける」ことで黙った**（同型 3 件） → 変異が本当にキルになっているかを別世界で確認してから登録する。
8. **サブエージェントが背景プロセスを投げて自分は停止し、計算が迷子になった**（逆に、サブ内の背景プロセスがハーネスに kill されてワーカープールごと道連れになる事故も別に実測） → 長時間走行は detached 起動＋短い前景ポーリング、復旧は プロセス確認 → 見張り → 再開メッセージ の 3 手順。

## 8. そちらに聞きたいこと（5 件）

1. **文書の腐り検知**：nuru は行番号参照の腐りと「履歴が本文の 63%」を機械検知に落としたが、**内容が古くなったこと自体**（例：「未測定」と書いてある項目が実は測定済み）は検知できていない。長期運用で「本文の主張が現実とずれた」をどう検知しているか。
2. **コンテキスト予算**：床からの差 75k で通告する方式を採ったが、**閾値は裁定で決めた 1 つの数字**で、切りどきの最適性は検証していない。そちらの relay 運用では、切る判断を何で決めているか（ターン数・コスト・作業の切れ目のどれか）。
3. **人間の判断待ちの受け皿**：判断が要る項目（現在 17 件が裁定待ち）について、裁定の中で分割された残・後続送りになった分が**どの未消化リストにも現れない**という構造的欠落を実測した。人間の判断待ちタスクを滞留させずに追跡する仕組みがあるか。
4. **検知の増え方**：86 本まで増え、全走が長くなって「preflight 中は他の python を並走させない」という運用制約まで生まれた。**卒業（検知に守られた既知欠陥をリストから抜く）**の規律は作ったが、検知そのものを減らす仕組みは無い。増え続ける自動チェックをどう抑えているか。
5. **正典 1 本主義の限界**：「二次ビューを作らない」を徹底すると入口文書が薄くなり、**文脈ゼロの読者が停止する**（実測あり＝フレーミング無しの単体読みで停止した）。読む順を強制する以外に、要約を持たずに新規参加者を立ち上げる方法があるか。

## 9. そちらからの質問への回答

### Q1. 文書の腐りをどう機械検知しているか／何を「テスト」と呼ぶか

- **参照切れ**＝`audit_line_ref_lint`（行番号で他ファイルを指した参照の指し先ずれ。`code/**/*.py` 限定＝日付つき歴史文書は行番号のまま残す裁定があるため）と `thinking_reachability_check`（構想文書が入口から名前で辿れるか＝**孤児化**。read-only で導線は張らない）。
- **数値のずれ**＝`check_numbers --verify`（`〔#key〕` タグ **940 キー** ↔ 出所 JSON。出所ファイルの sha256 まで再照合する）＋ `audit_check_numbers_golden`（抽出器そのものの振る舞いを合成 fixture で固定）。詳細は §3b (A)。
- **定義の重複**＝`numbers_shadow_lint`。共有定数モジュールの公開定数と**同名のリテラルが `code/*.py` に独立定義**されていないかを **AST で毎走探す**（grep では `ROOT = Path(...)` 等の約 60 件が誤検出になるので AST）。発端の実測＝独立定義が 40 件超あり、手書きのペア表が値まで見ていたのは **8 件だけ**だった＝「表に無いペアは存在しないのと同じ」。値は比較せず**同名の存在だけ**で鳴らす（値の一致／不一致は詳細行に注記）。
- ほかに文書の構造と規律を見る 2 本＝`ledger_lint`（編集のたびに発火する hook・見出しの欠番／箇条書きへの癒着／角括弧注記の不対応）と `ledger_discipline_lint`（凍結物の sha 固定・追記専用台帳の過去改変・訂正記録が挙げる根拠の実在・締めの一体性・入口の鮮度と行数）。
- **「テスト」と呼んでいるものは無い**〔実測＝`tests/` ディレクトリ無し・`import pytest` 0 件〕。あるのは preflight の **86 Step** で、名前で役割が分かれる：`*_killtest` **20**／`*_selftest` **7**／`*_smoke` **7**／`*_lint` **4**／`golden` **1**／残り **47** が `*_check`（照合器）。呼称は一貫して**「番人（検知器）」**で、単体テストという語は使っていない。
- 順序は固定＝**機械 → LLM**。ただし置き換え関係ではない——ある回の実測で **LLM 監査が見つけた 21 件のうち preflight が拾えたものは 0 件**だった。

### Q2. 台帳の上限の決め方と、超えたときの第一手

- **上限を持つのは入口文書 `HANDOVER.md` だけ**で、**行数で測る。文字数では測っていない。** 宣言値は `ledger_discipline_lint.py` 内〔実測〕＝総行数 **700**（L5）／「締めた・畳んだ」を名乗る節の**合計 120 行**（L6-E1）／`## 現在地` 節が **150 行目**までに現れること（L6-E2）／鮮度ヘッダの生成時刻が最後の commit から **24 時間**以上古くないこと。現況 316 行。
