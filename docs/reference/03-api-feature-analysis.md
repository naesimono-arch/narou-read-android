# 03 API機能の検討

対象: `novel-reader_andloid` に「小説家になろう」公式API連携を足す件（handover.md §D Phase3-②）。
前提は `01`（アプリ現状＝完全ローカル）と `02`（API＝メタデータ専用）。
関連: [04 競合アプリの「非読書機能」横断解析](04-competitor-app-features.md) — 本検討の各オプションを、実在する競合5アプリの実装で裏取りした横断解析。

---

## 1. 問いの分解

「API機能」と一口に言うが、実は**2つの別々の機能**が混ざっている。切り分けが検討の肝。

- **A. ディスカバリ（発見）**: ランキング／検索／ジャンル別一覧／作品情報カード。
  → **なろうAPIだけで完結する**。本文は要らない。実装リスク小。
- **B. リーディング（そのまま読む）**: 発見した作品の本文を取り込み、既存の読書パイプラインで読む。
  → **APIでは不可能**（本文が返らない）。本文取得の別経路が要り、規約・技術リスクが跳ね上がる。

この A / B の分界が、後述の全オプションを貫く軸になる。

---

## 2. 最重要の制約（ここを外すと設計を誤る）

1. **API＝メタデータのみ。本文テキストは絶対に返らない。**（`02` 参照）
2. 既存の本文抽出（章分割・ルビ・前後書き）は **PDFレイアウト座標に強依存**。
   Webの本文HTMLは座標を持たない別物なので、**このロジックは流用できず新パーサが要る**。
3. アプリは今 **ネットワーク層ゼロ**（`INTERNET` 権限すら無い）。A だけでも新規レイヤの新設。
4. 本文をWebから取るとスクレイピング領域＝**利用規約・robots・負荷・再配布可否**の判断が必要（技術以前の問題）。

---

## 3. 設計オプション（3案 + 段階導入）

### 案A：ディスカバリのみ（読書は従来のPDF取込のまま）
APIはランキング/検索/作品カードだけ。「この作品よさそう」と分かったら、本文はユーザーが
従来どおり別手段でPDF化して取り込む（動線は分断されるが）。

- **利点**: 実装が最小・規約リスクほぼ無し・既存の読書系に一切手を入れない。API層の価値検証を最速で回せる。
- **欠点**: 「発見」と「読書」が地続きにならず、体験としては片手落ち。
- **リスク**: 小。

### 案B：発見→本文HTML取得→既存の保存/読書系へ流し込む（フル統合）
APIでメタ取得 → `ncode.syosetu.com/{ncode}/{話数}/` のHTMLを取得・パース →
`index.html + chap_N.html` 相当を生成して `filesDir/novels/` に保存 → 既存のネイティブ読書で読む。

- **利点**: アプリ内で発見から読書まで完結。読書/保存/Roomの資産をフル活用できる。
- **欠点/リスク（大）**:
  - (i) **本文取得は非公式**＝HTMLスクレイピング。**利用規約・robots・負荷配慮・キャッシュ/再配布の可否**をユーザーが判断・許容する必要（技術で解決しない）。
  - (ii) **新規HTML本文パーサ**が要る（既存はPDF座標前提で流用不可）。ルビは本文HTMLの `<ruby>`/`｜《》` 記法から再構築。話数ページング・前書き/後書き構造もサイト構造依存。
  - (iii) サイトのHTML構造変更で壊れる継続保守コスト。
  - (iv) 長編の全話取得は**通信量・時間・OEM kill**（既存の前景サービス＋WakeLock設計を通信にも適用）。

### 案C：内部ブラウザ経由（handover §D ① と接続）
アプリ内WebViewでなろうページを開き、そこから取り込む（PDF化 or ページ保存）。API発見と組み合わせ。

- **利点**: 「サイトを見る」体験はサイトのまま（規約的にグレーが少ない）。①の宿題と一石二鳥。
- **欠点**: WebView（現アプリは意図的にWebViewを捨ててネイティブ化した経緯あり＝逆行感）。取り込み品質が不安定。中途半端になりやすい。

### 推奨：**段階導入（A を土台に据え、B/C は別判断）**
まず**案A（ディスカバリ）を第1マイルストーン**にする。理由:
- APIメタだけで完結＝**規約リスクが低く、価値（ランキング/検索の使い勝手）を最速で検証**できる。
- ネットワーク層・キャッシュ・ランキングUIという**B/Cでも必ず要る共通土台**を、低リスクな範囲で先に作れる。
- 本文取得（B/C）は規約判断が絡む**重い意思決定**なので、Aで基盤を固めてから別フェーズで独立に決める。

## 4. 必要になる技術レイヤ（どの案でもAPIを叩くなら共通）

| レイヤ | 追加物 | メモ |
|---|---|---|
| 権限 | `AndroidManifest` に `<uses-permission android:name="android.permission.INTERNET"/>` | 現状ゼロなので新規。ネットワーク状態を見るなら `ACCESS_NETWORK_STATE` も |
| HTTPクライアント | **OkHttp** 推奨（gzip自動・枯れてる・Android定番）。最小主義なら `HttpURLConnection` でも可。Ktor client も選択肢 | 依存追加＝APKは微増（Aで24MiBを大きく崩さない範囲） |
| JSONパース | **kotlinx.serialization**（Kotlin純正・リフレクション不要）。Moshi/Gsonでも可 | `out=json` のレスポンス→data class |
| データモデル | `NarouNovel`(1作品) / `NarouListResponse`（先頭要素が `allcount`）。※`novel_type` は of指定時 `noveltype` で返る等の癖に注意（`02`/正本参照） | |
| Repository | `NarouApiRepository`（検索/ランキング取得＋**キャッシュ**）。既存 `BookRepository`（ローカルPDF/Room）とは**別系統**として並置 | 混ぜない。発見系とローカル蔵書系は責務が別 |
| キャッシュ | Room に軽い `cached_ranking` 等 or メモリ+DataStore。公式推奨=最長2週間で更新/削除 | ランキングは分単位で変わらず端末キャッシュが効く（転送量とレート制限休止解除に備える） |
| ViewModel | `DiscoveryViewModel`（Flow/StateFlow でランキング一覧・検索状態） | 既存の Compose/StateFlow 流儀に合わせる |
| UI（Compose） | ランキング画面（`order` タブ切替）／検索画面／作品詳細カード。ナビは既存 NavHost に "discovery" ルート追加 | 見た目は `/design` モックが正本ルール（`docs/decisions/0005`）＝**新画面のモックを先に作る**必要あり |
| 非同期/失敗 | Coroutines（既存）＋ネットワーク失敗/オフライン/遅延（最大2時間反映遅延）のハンドリング | 既存の `errorEvents` Channel 流儀に載せられる |

### 転送量・行儀（`02` §転送量作法を実装に落とす）
- リクエストは常に `out=json&gzip=5&of=<必要項目だけ>`。
- `lim`/`st` でページング。無駄な再取得をキャッシュで抑止。
- User-Agent を明示し、短間隔連打を避ける（レート制限休止中でも行儀よく）。

## 5. UI/導線の素案（案A想定）

```
本棚（既存）
  └─ 新規タブ/導線「さがす」
       ├─ ランキング（order: 総合 / 日間 / 週間 / 月間 / ブックマーク / 新着）  ← タブ切替
       ├─ ジャンル別（biggenre/genre）
       ├─ フリーワード検索（word + 対象範囲 title/あらすじ/keyword/作者）
       └─ 作品カード（title・作者・あらすじ・文字数・話数・完結/連載・総合pt）
              └─（案B/Cを入れる場合のみ）「この作品を取り込む」ボタン → 本文取得フェーズへ
```

- 見た目は既存の「和モダン・余白」視覚言語（ADR 0005）に揃える。**新画面はHTMLモックを先に作る**のが本プロジェクトの規約。

## 6. ユーザーに決めてほしいこと（未決事項）

検討を前に進めるには、以下の方向づけが要る。特に ① が全体を左右する。

1. **スコープはどこまで？** — 案A（発見だけ）／案B（本文まで取り込んで読む）／案C（内部ブラウザ経由）／段階導入（Aから）。
2. **本文の自動取得（スクレイピング）を許容するか？** — 案B/Cの前提。なろうの利用規約・負荷配慮・再配布可否をどう扱うか（技術以前の意思決定）。許容しないなら案A確定。
3. **ランキング/検索のどの軸を出すか？** — order（総合/日間/週間/月間/ブックマーク/新着…）・ジャンル・フリーワードの範囲。
4. **オフライン/キャッシュ方針** — どこまで端末に貯めるか（公式推奨=最長2週間）。
5. **このアプリの立ち位置** — 「手元PDFを読むリーダー」に発見を足す程度か、「なろうを直接ブラウズ・購読する」クライアントに寄せるか。方向で作り込み量が大きく変わる。

## 7. 次アクションの候補（方向が決まり次第）

- **案A採用なら**: ①INTERNET権限＋OkHttp＋kotlinx.serialization 依存追加 → ②`NarouApiRepository`（1本のランキング取得＋JSONパース＋キャッシュ）で**縦スライス1本**を通す → ③ランキング画面モック（/design）→ Compose 翻訳。まず「週間ランキング一覧が出る」最小疎通をゴールに。
- **案B/Cを視野に入れるなら**: 先に**規約・robotsの調査メモ**（本フォルダに `04-content-fetch-legal.md` 等）を作り、本文取得の可否を独立に固めてから技術検討へ。
  ※このメモは**未着手＝存在しない**（案A 先行が確定したため。規約線の実際の決着は ADR 0024 の `SiteAdapterRegistry` 3値ゲート）。
