# 同一ツリーで Gradle が並走すると、結果 XML が上書きされて「偽 GREEN」になる

> 2026-09-07 に委譲便が実際に踏み、自力で検出して報告した。⚠️ **既知の2つとは別方向の事故**＝
> `/build` の「同じツリーで2本走らせると**偽の赤**が出る」でも、memory `bash-pipe-masks-exit-code-false-green`
> の「パイプが exit code を潰す」でもない。**BUILD SUCCESSFUL が出て、失敗数も 0 で、しかも自分のテストは1本も走っていない**。

## 症状

`testDebugUnitTest` が `BUILD SUCCESSFUL` で終わり、結果 XML の集計も failures 0。
ところが**この便で新設したテストが report に1本も存在しない**。ログには `compileDebugKotlin UP-TO-DATE` が出ており、
自分の変更がコンパイルすらされていない。

## 機序

同じ作業ツリーで**別の Gradle 実行が並走**していた（当該例では別便の Roborazzi `record` 付き `--tests` 実行）。

- 出力ルート（`build/test-results/`）は**ツリー単位でしか分かれていない**＝相手の実行結果が自分の XML を上書きする。
- 相手が `--tests` で絞っていると、書かれる XML は**相手が選んだクラスのぶんだけ**になる。
- 自分側は相手のビルドで入力が既に処理済みと見えて `UP-TO-DATE` で素通りする。
- ∴ 「成功した」「失敗0」という2つの徴候が揃うのに、**検証は一度も行われていない**。

## 検出のしかた（合否を信じる前に必ずやる）

**結果 XML に自分の新テスト名が在るかを直接照合する。** 失敗数が 0 であることは何の担保にもならない。
`BUILD SUCCESSFUL` と `UP-TO-DATE` が同時に出たら、それは「速かった」ではなく「走っていない」を疑う合図。

## 復旧

ロックを取り直した直後にツリーの状態をスナップショットしてから**再実行する**（当該例ではこれで
`failures 15`＝別便由来の実際の赤が出て、初めて本当の状態が見えた）。

## ⚠️ 未確定

`tools/gwlock.sh` は**ツリー単位で排他する**ので、両者がそれを経由していれば並走は起こらないはずだった。
どちらかが gwlock を通さず `./gradlew` を直接叩いた疑いが濃いが、**どの実行が経路を外れたかは特定できていない**
（推定であって確認ではない）。∴ 「gwlock を使えば安全」と読まず、**上の検出手順は毎回踏むこと**。
