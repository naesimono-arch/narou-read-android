# 並列ビルドで共有された出力先が「ビルドの成否」を汚染する（偽の赤）

★★★ / 2026-08-21 / **同じ作業ツリーに Gradle を2本走らせると、テストが全緑でもビルドが FAILED になる。**
落ちるのはテストではなく I/O。単独実行では絶対に再現しないので、並列委譲を始めた瞬間に初めて出る。

## 症状

- `BUILD FAILED` で終わるのに、**結果 XML は `failures="0"` で揃っている**（テストは完走している）。
- 実際に出たメッセージ: `Could not write XML test results …`。
- 同じコマンドを1本だけで流すと通る＝再現手順を書けない・原因をコードに探しに行ってしまう。
- 実害: ある便が **70 分 Gradle を待って何もコミットできず**、作業をパッチへ退避した。

## 真因

**Gradle は「同じプロジェクトツリーに対する2本目のビルド」を自分では拒まない。**
（daemon が直列化するのは *1つの daemon 内* の話で、別プロセスのビルドは素通りする。）
そしてビルドが書き換える可変資源は、**どれも作業ツリー単位でしか分かれていない**:

| 共有される資源 | 例 |
|---|---|
| 出力ルート | `android/app/build/` と、canonical でそれを ext4 へ逃がした退避先 |
| プロジェクト直下の `.gradle/` | file hash キャッシュ・configuration cache |
| ソースツリーへの書き戻し | golden PNG の record、生成コードの出力 |
| タスクごとの作業領域 | 中間ディレクトリ・レポート出力・各種ロックファイル |

2本が同時に走ると、片方が掃除した／掴んだファイルをもう片方が書こうとして I/O エラーになる。
**⚠️ これは `test-results` 固有の問題ではない**——上のどれで先に当たるかが運任せなだけで、機序は同一。
次に別の共有物（キャッシュ・レポート・ロックファイル）で当たったとき、症状のメッセージだけが変わる。

## 何が一番まずいか＝判定が壊れること

普通の赤は「直すべきものがある」という情報だが、これは**情報がゼロの赤**。
テストは通っているのにビルドは失敗しているので、**「ゲートが緑か」という問いに答えられなくなる**。
サブエージェントは自己申告 GREEN を禁じられているため、ここで正しく詰まる＝
**並列委譲の便が丸ごと1本、成果を出せずに終わる**。

## 対処（2026-08-21 に恒久化）

1. **`tools/gwlock.sh` 経由でしか Gradle を起動しない**。資源の粒度（＝作業ツリー）と同じ粒度で
   flock を取り、2本目は待つ。**待つ側は保持者（pid・開始時刻・タスク名）と待ち秒数を 30 秒ごとに表示**
   する——待ちが見えないと「固まった」と誤認されて中断されるため、可視化は対策の一部。
   ロックファイルは必ず ext4 に置く（drvfs の flock は当てにしない）。
2. **並列で回したいなら worktree**（`wt-new`）＝ツリーが別ならロックも別で待ちゼロ。
   ⚠️ 代償: worktree は作業ツリーが別＝**他便の未コミット変更を持ち込めない**。
   canonical で他便の変更ごと確かめたいなら、待つ側が正しい。
3. 退避先（canonical の ext4 redirect）は **所有ツリーを1つ記録して分離**する。別ツリーから誤って
   同じ init スクリプトを渡しても、そのツリーには派生ディレクトリが割り当たり共有されない。

**採らなかった案＝退避先を呼び出しごとにユニーク化**: 衝突を出力ルートから `.gradle/` や
ソースツリー書き戻しへ移すだけで機序は残り、しかも増分ビルドとビルドキャッシュを毎回捨てるので
極端に遅くなる。**分けるべきは出力先ではなく「同時に走るビルドの数」**だった。

## 一般化（次に同じ形で刺されないために）

**「並列実行で共有された出力先は、成果物ではなくジョブの成否を汚染する」**——
テストの合否・計測値といった *中身* は正しいまま、ラッパーである**ビルドの終了コードだけが嘘になる**。
Gradle に限らず、単一の固定パスへ書き出すツール（レポート生成・ゴールデン記録・ベンチ・スクレイプ）を
複数便で同時に回すときは、**「その出力先を同時に触るジョブは1つだけ」を出力先と同じ粒度のロックで**
担保する。出力先を増やして逃げると、共有物が別の層に残っているぶんだけ後で必ず再発する。

## ⚠️ 同じ並走は「偽 GREEN」側にも倒れる（2026-09-07 追記）

上は**成否だけが嘘になり中身は正しい**という顔だが、相手が `--tests` で絞って走っていると
**逆向き**の顔が出る。実際に踏んだ例（別便の Roborazzi `record` 付き `--tests` 実行と並走）:

- `BUILD SUCCESSFUL` で終わり、結果 XML の集計も `failures 0`。
- しかし**この便で新設したテストが report に1本も無い**。ログには `compileDebugKotlin UP-TO-DATE`。
- 機序＝相手の実行が `build/test-results/` を**相手が選んだクラスのぶんだけ**で上書きし、
  自分側は入力が処理済みと見えて素通りする。∴「成功した」「失敗0」の2つが揃うのに**検証は一度も行われていない**。

**検出**＝失敗数が 0 であることは何の担保にもならない。**結果 XML に自分の新テスト名が在るかを直接照合する**。
`BUILD SUCCESSFUL` と `UP-TO-DATE` が同時に出たら、「速かった」ではなく「走っていない」を疑う合図。
**復旧**＝ロックを取り直した直後に再実行する（当該例ではこれで別便由来の実際の赤が初めて見えた）。

⚠️ 上の「残る制約」のとおり**ロックは `gwlock.sh` を通った起動にしか効かない**＝並走が起きた時点で
どちらかが経路を外れている。偽 GREEN は成功側に倒れるぶん、偽の赤より気づきにくい。

## 残る制約

- canonical での2本目は**壊れないが待つ**（直列化なので合計時間は変わらない）。長い待ちを避けたいなら worktree。
- ロックは `tools/gwlock.sh` を通った起動にしか効かない。`java … GradleWrapperMain` を直に叩く
  古いコマンド列はロックを取らない（`/build` skill の「素の起動列」節に警告を置いてある）。
