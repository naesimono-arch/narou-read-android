# LazyColumn→LazyRow の鏡写し翻訳で contentPadding の top/bottom は意味が変わる（軸シフトの罠）

**重要度**: ★★
**確定日**: 2026-07-17（PGEM10 実機・縦書き横画面で列高が約4割に潰れる実測）
**1行要約**: 縦横の鏡写しで同じ top/bottom が「スクロール軸の一回きり余白」から「交差軸の毎アイテム恒久課金」へシフトする——dp 値のコピーは軸判定の代替にならない。

## 事象

縦書き本文（LazyRow）を横書き（LazyColumn）の鏡写しとして実装した際、contentPadding の
top/bottom（バークリアランス 64/80dp）を「同じ算出だから」とコピーした結果、横画面（視野高 360dp）で
列高が約 134dp＝画面の約4割まで潰れ、「一列の文字数が極少・上下余白が本文の2倍」として顕在化した。

## 機序（一般化）

contentPadding の各辺は **スクロール軸に載る辺か交差軸に載る辺かで課金モデルが別物**になる:

- **スクロール軸の辺**（LazyColumn の top/bottom・LazyRow の start/end）＝リスト先頭/末尾に
  一度だけ効く余白。コンテンツはスクロールで余白の外へ出られる＝**一回きりの課金**。
- **交差軸の辺**（LazyColumn の start/end・LazyRow の top/bottom）＝**全アイテムの実寸から
  恒久的に差し引かれる**。スクロールしても回復しない＝**毎アイテム課金**。

縦横を鏡写しにすると同じ「top/bottom」が前者から後者へシフトする。dp 値のコピーは式として同一でも
意味論が変わる。特にバークリアランスのような大きい値（今回 計144dp）は交差軸に載せた瞬間に
視野の短辺を食い尽くす（縦画面では長辺持ちで潜伏し、横画面で顕在化した）。

## 横展開の注意

- 縦書き系の今後の調整（P6/P7・覗きパネル・継続スロット）で横書きの余白式を移植するときは、
  **各辺がどちらの軸に載るか**を先に判定してから値を決める（コピーは軸判定の代替にならない）。
- 同型の罠は insets の読み替え（statusBars/navigationBars は物理 top/bottom 固定＝縦書きでは交差軸）にもある。
  今回 insets 分は「バーの物理位置に在る」ため交差軸課金を意図的に許容した（正当なコスト）。
  誤りだったのは物理バーと無関係に運ばれた「クリアランス定数」の方。
- 不採用の代替案＝バー可視状態へ列高を追従（モック `.reader` の非没入 margin-bottom:60px の直訳）:
  タップトグルのたびに全列の再組版（BoxWithConstraints 高さ変化→typeset やり直し）が走るため翻訳せず、
  没入全面＋バー表示中の列端重なり許容へ倒した（横書きが本文行のバー下通過を許容するのと同じ取引。
  詳細コメント＝`VerticalChapterContent.kt` contentPadding 付近）。
