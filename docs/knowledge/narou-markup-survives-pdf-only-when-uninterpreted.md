# なろうの制御記法は「解釈されなかったとき」だけ PDF に残る（挿絵だけが例外）

★★ Important（2026-09-05 確定・一次ソース照合済み）

## 結論（先に使う規則）

なろう公式の縦書きPDF の本文グリフ列に**制御記法の字面が残っている**なら、それは
**なろうがその記法を解釈しなかった**ことの証拠であり、**web の読者にも同じ記号列が見えている**。

∴ **残っている記法を解釈して描き変えてはいけない**——それは「原文に無い見え」を作る側の誤り
（忠実性の相手は web 原文の見え＝ADR 0041）。

**例外は挿絵記法ただ1つ**。なろう公式の縦書きPDF は画像を**1枚も**持てない
（sample_pdfs 全12本で `/Subtype /Image` が 0 件・`/XObject <<>>` が空）ため、
生成器は解釈結果（画像）を出力できずタグの字面だけを落とす。
**web と PDF の見えが食い違うのはここだけ**なので、挿絵記法だけは除去が忠実性の回復になる。

## なぜそう言えるか（機序）

- 解釈された記法は、解釈された時点で**描画結果に置き換わる**（ルビなら小さいフォントのグリフ）。
  記法の文字そのものは出力に残らない。
- 抽出側の `TextProcessor` は、その小フォントのグリフを見つけて `|親《読み》` という
  **ASCII 縦線のマーカーを自分で組み立てる**（`sb.append("|")`＝全角は1つも出さない）。
  ∴ 抽出出力の ASCII マーカーは「なろうが確かにルビを描いた」ことの証拠であって著者の入力ではない。
- 逆に**全角縦線・全角括弧などの記法文字は PDF に literal で在ったもの**＝非解釈の証拠。

⚠️ **この非対称が最大の落とし穴**。同じ `《…》` でも、ASCII 縦線付きは「解釈された結果の復元」、
全角縦線付きは「解釈されなかった生の記法」で、**意味が正反対**。字面だけを見て一律に扱うと、
必ずどちらかを壊す。

## 実測（sample_pdfs 全12本・抽出出力を全数走査）

| 記法（一次ソース） | 形 | 12本での件数 | 判定 |
|---|---|---|---|
| ルビ 標準形（helppageid/42） | `\|親《読み》`（ASCII 縦線） | 23,017 | 全て `TextProcessor` の復元＝解釈済み。`<ruby>` へ変換するのが正しい |
| ルビ 標準形（同） | `｜親《読み》`（全角縦線） | 1（N6169DZ） | **非解釈**。web でも記法のまま見える（下記の裏取り）＝触らない |
| ルビ 縦線省略形（同） | `漢字《かな》` | **0** | 縦線なし `《…》` は 169 件あるが、直前が漢字かつ中身が純かなのものは 0 件 |
| ルビ 括弧形（同） | `漢字（かな）` | **0** | 漢字直後の全角括弧は 1,435 件あるが、中身が純かなのものは 0 件 |
| ルビ打ち消し（同） | `｜` を `（` の**直前**に置く形 | 0 | — |
| 傍点（helppageid/43） | ルビ機能で各文字に `・` を振る | 実在（N3957FQ 等） | ルビとして描かれるので ASCII マーカーで復元され、`<ruby>` 経路で正しく出る＝**専用対応は不要** |
| 挿絵（helppageid/44） | `＜ｉコード｜ユーザID＞` | 127（全て全角・半角形 0） | **唯一の例外**＝除去する |
| 文字サイズ変更（46）・記号挿入（47） | — | — | 本文へ埋まる記法ではない（前者は入力欄の表示設定・後者は素の文字を挿入するだけ） |

**省略形・括弧形が 0 件なのは「なろうが全て解釈してルビグリフに変えたから」**であって、
「なろう作者が使っていないから」ではない。∴ **これらを実装してはいけない**——
PDF に残った同形の文字列を拾えば、拾えるのは非解釈のものだけ＝必ず捏造になる。

## 一次ソースでの裏取り（2 点）

- **全角ルビは適用されない**: N6169DZ 第686話「鏡面に響け、摩天より吼えろ　其の四」の作品ページで、
  当該箇所は縦線と `《》` を含む素の文字列のまま表示されている（同じ段落内の別のルビは ruby として
  描かれているので、その話でルビ機能が死んでいるわけではない）。
  ⚠️ ヘルプ helppageid/42 は「｜は全角・半角どちらであっても問題ありません」と書くが**実挙動と食い違う**。
- **全角の挿絵タグは適用される**: N5892FB の作品ページ本文にはみてみんの `<img>` が出ており、
  タグの字面は表示されていない。
  ⚠️ ヘルプ helppageid/44 は「括弧と縦線は半角で入力してください」と書くが**実挙動は全角も受ける**。

∴ **ヘルプの記述を仕様として信用しない**。どちらの記法でも実挙動がヘルプとずれていた。

## 原理的に区別できない変種（塞げない穴）

著者が **ASCII** 縦線で書き、なろうが解釈しなかった記法は、`TextProcessor` が組み立てたマーカーと
**字面が完全に同一**で区別できない。読みの長さでも切り分けられない——抽出側は隣接するルビを
1 つのマーカーへ合成するため、11〜29 字の読みを持つマーカーが 520 件ある（傍点がこの形になる）。
∴ この型はルビ化され、同型の捏造が残る。corpus に観測手段が無く件数も出せない。

## 経緯（同じ型を 2 回踏んだ）

2026-09-05 に「挿絵記法とルビ記法が続けて素通しになっている」と読んで両方に解釈側を足したが、
**ルビ側は素通しではなかった**（記法のまま出るのが正しい見えだった）。
症状が同じ「記号列が本文に見える」でも、原因が〈生成器が解釈結果を出力できない〉か
〈なろうがそもそも解釈しなかった〉かで**対処が正反対になる**。
先に確かめるべきは記法の形ではなく、**web でその位置に何が見えているか**。
