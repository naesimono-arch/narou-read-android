# Auto Backup は永続 URI 権限を復元しない — 「記録済み sourceUri から自動再取込」は主機序で必ず0件になる

- 重要度: ★★★（2026-07-29 実機実測で確定・**導線の失敗がそのままユーザーのデータ喪失に直結した実例**）
- 1行要約: uninstall すれば `takePersistableUriPermission` で取った権限も**必ず一緒に消える**ため、
  「DB に残った `books.sourceUri` を使ってアプリが自動で再取込する」設計は、想定した主機序（uninstall→Auto Backup 復元）では**構造的に成立しない**。

## 症状

蔵書の本文欠落（`files/novels/` が消え DB だけ残る片肺状態＝`upload-signing-verify-wipes-device-library.md`）に対して実装した
復旧導線（起動時に一括検出 →「まとめて再取込」）が、**実機で常に「0冊」**となり機能しなかった。

## 真因

導線は自動再取込の対象を①**永続 URI 権限が生存している PDF** と④Web 蔵書に限定していた。ところが、

- **Auto Backup が復元するのは層別設定（ADR 0015）どおり DB・prefs・DataStore だけ**。
- **永続 URI 権限はアプリのアンインストールで失効し、Auto Backup の復元対象にも入らない。**

したがって主機序（uninstall → 再インストール → Auto Backup が DB を戻す）を通った PDF 本は **100%** が
「権限が無い＝自動再取込できない」分岐へ落ちる。①が成立するのは「アプリは消えていないが本文ファイルだけが消えた」稀ケースのみ。

## 実害

ユーザーは導線を使えず、**欠落本を削除して新規取込し直し、読書位置・栞・追加日を永久に失った**
（実機DB実測＝全冊の `addedAt` が入れ直し時刻・`progress` も入れ直し後の記録）。

## 対処（設計含意）

- **URI（権限つきの参照）を復元の鍵にしない。** 権限はアプリの生存と運命を共にするため、アプリが消える系の事故では必ず切れる。
- 代わりに**中身で照合する**。判別の非対称性が根拠＝**人間はファイル名では判別できない**（なろうPDF は `n0000xx.pdf`）が、
  **アプリは中身のハッシュで判別できる**。実機実測でも現行蔵書は全冊 `contentSha256` を保有（`sourceUrl`/`ncode` は PDF 由来では全冊 NULL）。
- 場所は**フォルダ単位で1回だけ**教えてもらう（`ACTION_OPEN_DOCUMENT_TREE`）。**ツリー権限は永続化できる**ので、
  次回以降は「フォルダを選ぶ」すら不要な自動走査にできる＝「①が主機序では成立しない」という構造問題そのものへの解になる。
- **記録済み `sourceUri` の形にも注意**: MediaStore Documents Provider 経由だと
  `content://com.android.providers.media.documents/document/document%3A<数値ID>` の形でファイル名を含まない。
  かつて UI に「取込元の PDF: 1000027648」と数値が出ていたのはこれが原因（`primary:Download/foo.pdf` 形式しか想定していない表示関数の穴）。
  **表示側は是正済み**＝`sourceFileNameHint()` が拡張子の有無で〈人が探せる文字列〉と〈provider の内部ID〉を分け、
  後者は `null` を返して行ごと出さない（回帰は `ReimportPlanTest` が実測値 `1000027648` と UUID 形式を名指しで固定）。
  **ただし「ファイル名を含まない `sourceUri` が実在する」という事実自体は変わらない**＝ここを前提に設計すること。

## 一般化

**復旧導線は「復旧できるか」ではなく「復旧の鍵が事故と一緒に消えないか」で設計する。**
鍵（権限・ハンドル・キャッシュ）が事故の巻き添えで消えるなら、その導線は事故のときだけ効かない。
