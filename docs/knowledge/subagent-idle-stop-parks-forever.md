# サブエージェントは「子ゼロ停止」で駐機する——background 完了待ちはサブ環境に無い

2026-08-06 に device-verify 便2件が連続で踏んだ（tab-swipe 較正便・pdf-import 切り分け便＝長走行系 2/2）。

- **機序（確定）**: サブエージェントが追跡中のバックグラウンド子タスク無しでターンを終えると、その時点で
  ハーネス上 completed 扱い＝完了通知が親へ飛び、**自走で再開される経路が無い（駐機）**。「死ぬ」のではない——
  transcript は保持され、**SendMessage 一発で文脈ごと再開できる**（実測2件とも再開後そのまま完走）。
  切り離された実作業（デバイス上のベンチ等）は駐機後も生きて動き続ける（エージェント≠プロセス）。
- **機序（推定）**: モデルはメインセッションの Bash 仕様（run_in_background 完了でターン再起動）をサブ環境へ
  持ち込み「待てば起こしてもらえる」と誤信する。追跡が切れる経路は
  (a) script が fork して親 bash が即 return（adb 経由の非同期ベンチ等＝実作業は生きているのに追跡上は子ゼロ）
  (b) 子が即終了（ビルド即失敗など）。長走行が多い device 系ほど「待つ」誘惑が構造的に強い。
- **ストールとの識別**: Stream idle timeout（orchestration §5）は応答が途切れ**完了通知も来ない**。本件は
  自発的な「待ちます」宣言＋**完了通知あり**＝別の故障モード。復旧はどちらも SendMessage（ストールは TaskStop が先）。
- **恒久対策（2026-08-06）**: SubagentStart 注入 `inject_subagent_briefing.py` の `FOREGROUND_RULE`
  （長走行はフォアグラウンド・「通知待ち」でターンを終えない・fork 形はポーリング回収）を実装系＋実機系へ
  自動配布＝読み忘れ不可能。回帰＝`test_inject_subagent_briefing.py`。監督側の作法＝orchestration §5
  （「待ちます」型の完了通知を見たら即 SendMessage 再開）。
