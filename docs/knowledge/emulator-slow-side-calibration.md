# エミュを「遅い側へ振る」——効いた手・効かなかった手（実測）

対象＝`emulator-5554`（AVD `nr_lowmem` / API 36 / 1080x1920 / ゲスト4コア・ホスト20コア・WSL2）。
**debug APK で計測**（絶対値は元々実機の代用にしない前提なので debug で足りる）。
計測作法の前提は `ranking-pager-jank-slow-ui-thread.md` と同じ＝**率で比べない**。

## 結論（先に線を引く）

- **遅い側へは振れる。ただし振れるのは「コア数」だけで、「クロック」でも「メモリ」でもない。**
  唯一効いたのは**ホスト側 `taskset` で qemu を1コアに縛る**手＝**アプリのコールドスタートが約3.2倍**に伸びた。
- **`heapsize` 絞りは速度に効かない**（32m まで絞っても素と誤差内）。あれは**OOM の天井**を動かす手であって
  速度のつまみではない。
- **使えるのは〈回帰検出〉と〈CPU 律速の切り分け〉まで**。**低スペック実機の体感の代用にはならない**
  （実機の遅さは GPU ドライバ・メモリ帯域・サーマルの複合で、そのどれもここでは再現していない）。

## 計測に使ったゲージ（なぜこの形か）

**時間の指標は「固定量の仕事の壁時計」だけを使い、ジャンク率は使わなかった。**
率は「測る対象そのものが走っていない」失敗モードを表現できない（`ranking-pager-jank-slow-ui-thread.md`）。
固定量の仕事なら分母が定義上動かないので、この罠を構造的に踏まない。

| ゲージ | 中身 | 効く律速 |
|---|---|---|
| G1 | ゲスト shell の固定回数ループ（20万回）×1本 | 単スレッド CPU |
| G2 | 同じループ ×4本並列の壁時計 | 並列 CPU（コア数） |
| G3 | アプリのコールドスタート（`am start -W -S`） | アプリの実挙動（多スレッド） |

⚠️ **壁時計はホスト側で取る**。**1コアに縛るとゲストの `date +%s%N` が巻き戻り、経過が負値になる**
（実際に `-1750ms` が出た）。ゲスト内の時刻でベンチを取ると、遅くした瞬間に静かに壊れる。
`sleep 1` は 1015ms と正常なので、**壊れるのは単調時刻でなく差分の取り方**＝気づきにくい。

⚠️ **G1 はホスト負荷の対照として使う**。ホストは他エージェントと共用で load が 4〜11 まで動く。
G1 は shell ループ＝ART も GPU も無関係なので、**G1 が伸びていたらそれはホストが混んだだけ**。
**G3/G1 で正規化して初めて条件間を比較できる。**

## 実測

ホスト負荷のドリフトを潰すため **A/B を交互に取った**（素→1コア→素→1コア）。

| 条件 | G1 | G2 | G3 | **G3/G1** | host load |
|---|---|---|---|---|---|
| A1 素（20コア） | 618 | 1348 | 2284 | 3.70 | 4.66 |
| **B1 taskset 1コア** | 610 | 2531 | **6984** | **11.45** | 9.24 |
| A2 素 | 598 | 1193 | 2131 | 3.56 | 7.10 |
| **B2 taskset 1コア** | 631 | 2879 | **7092** | **11.24** | 6.53 |
| C1 heap 128m + low_ram | 661 | 1279 | 2333 | 3.53 | 11.35 |
| C2 heap 32m + low_ram | 833 | 1706 | 2420 | 2.91 | 11.17 |
| A3 素（C と同時期の対照） | 604 | 1299 | 2672 | 4.42 | 7.20 |

（単位 ms・各3回の中央値）

- **素の G3/G1 は 3.56〜4.42 に散らばる**＝これがノイズ幅。
- **1コア固定は 11.2〜11.5**＝ノイズ幅の外・**約3.2倍**。効いている。
- **heap 絞りは 2.91〜3.53**＝**素の幅の中かむしろ下**。効いていない。

### ① ホスト側 `taskset` で qemu を1コアに縛る — **効く（唯一の当たり）**

```bash
# pid は必ず「AVD 名」でなく待受ポートで同定する（複数台あるとき取り違えると他人の台を遅くする）
ls -l /proc/<pid>/fd | grep -o 'socket:\[[0-9]*\]' | ... # 5554/5555 を持つ pid が emulator-5554
taskset -a -pc 19 <qemu-pid>     # -a を落とすと主スレッドしか縛れない（qemu は120本超のスレッドを持つ）
taskset -a -pc 0-19 <qemu-pid>   # 戻す
```

- **台の再起動が要らない**（`-cores 1` は再起動が要る＝走行中の検証を捨てることになる）。効果は同種。
- ⚠️ **単スレッドの仕事は遅くならない**（G1 は 618→610＝不変）。1本の実行スレッドはもともと1コアしか使わない。
  **遅くなるのは並列に走る仕事だけ**＝G2 が 2.1倍、G3（アプリ起動＝多スレッド）が 3.2倍。
  ⚠️ **裏を返すと、これは「CPU が遅い端末」ではなく「コアが少ない端末」の再現**。
  単スレッド律速の重さ（＝1本の重い組版）はこの手では一切あぶり出せない。

### ② `dalvik.vm.heapsize` を絞る — **速度には効かない**

`setprop` ＋ `stop; start` は正しく効いている（プロパティ機構の問題ではない）:
**32m まで絞ると `com.novelreader` の GC ログが出はじめる**（128m では自アプリの GC 行は 0 で、
出ていたのは launcher と system_server のもの＝他人の GC を自分のものと誤読しやすい）。

にもかかわらず**速度は動かない**。理由は単純で、**読書中のアプリの footprint が ~11MB しかない**
（GC ログの `8799KB/11MB`）＝128m どころか 32m でも天井に当たらない。
**`heapsize` は OOM の天井であって速度のつまみではない**——絞って遅くなるのは「天井に当たってGCが暴れる」場合だけで、
このアプリはそこまで使わない。**低メモリ端末で殺されるかを見る手**としては有効、**遅さを見る手**としては無効。

⚠️ **`ro.config.low_ram` は一度 true にすると `setprop` で戻せない**（`ro.` は書き込み一度きり。
`Failed to set property` で拒否される）。**戻すには台の再起動が要る**＝軽い気持ちで立てない。

### ③ 試していない手と、その理由

- **`-cores 1` / `-gpu guest`（ソフトレンダリング）**＝どちらも**台の再起動が必要**で、本便は再起動禁止のため未実施。
  ただし `-cores 1` は ① と同種の効果（コア数）で、① が再起動なしで足りる。
- **`-gpu swiftshader_indirect`** は segfault で使えない（skill §1・memory `wsl-android-emulator-kvm`）。

⚠️ **そもそも GPU 側の手は要らない可能性が高い**——この構成の `-gpu host` は
**実 GPU ではなく llvmpipe（Mesa のソフトラスタライザ）に落ちている**:

```
GLES: Google (Mesa), Android Emulator OpenGL ES Translator (llvmpipe (LLVM 21.1.8, 256 bits))
```

qemu プロセスは `llvmpipe-*` スレッドを20本持つ。**headless WSL の `-gpu host` は既にソフト描画**＝
描画性能はもともと実機より大きく遅い側に振れている。**「エミュだから速い」は CPU の話で、GPU は逆。**

## 「仕事量」指標は本当に端末非依存だった（実証できた）

`tools/measure_typeset_work.sh`（組版コストを**回数**で測る）を、**素の台**と**1コア固定＝G3 が 3.2倍遅い台**で
それぞれ走らせ、**全6ケースが1カウントも違わなかった**:

| ケース | 素・1コア固定とも同値 |
|---|---|
| 縦 / 章送り | `v_typeset=21 v_glyphs=765 v_cols=33 v_advance=765` |
| 縦 / フォントdrag | `v_typeset=44 v_glyphs=782 v_cols=55 v_advance=789 font_eff=10` |
| 縦 / 行間drag | `v_typeset=23 v_glyphs=366 v_cols=28 v_advance=366 lh_eff=5` |
| 横 / 章送り | `h_layout=19 h_chars=859` |
| 横 / フォントdrag | `h_layout=36 h_chars=1190 font_eff=10` |
| 横 / 行間drag | `h_layout=20 h_chars=755 lh_eff=5` |

同一条件の連続2走行も全ケース完全一致＝**run-to-run のばらつきもゼロ**。
（**先に同条件で2回取ること**。同じ速度で再現しない指標を速度違いで比べても意味がないため。）

⇒ **スクリプト冒頭が主張する「端末性能に依存しない」は、速度を3.2倍動かした対照で裏が取れた。**
性能回帰は**この指標でハイエンド機のまま止められる**。

### ⚠️ ただし遅い台では計測スクリプト側が先に壊れる

`measure_typeset_work.sh` は**固定 `sleep` で画面の据わりを待っている**（`launch_reading` は `sleep 4`）。
1コア固定ではコールドスタートが ~7s に伸びるため、**据わる前に a11y ダンプを取り、面を誤判定して落ちる**
（`面が指定と違う: want=vertical got=horizontal (縦長=0 横長=2)`。正常時は `横長=3`＝**枚数が足りないのが半端な描画の証拠**）。

⚠️ **これを「遅くしたら組版の挙動が変わった」と読んではいけない**——変わったのは**計測装置の待ち時間**だけ。
sleep を約3倍にした複製で走らせたら6ケースとも素と同値に戻った（＝上の表）。
**遅い台で自動化を回すなら、固定 sleep は必ず伸ばす**か、据わりをポーリングで待つこと。

なお**プリファレンスの書き戻し競合ではない**（`am force-stop` は同期的で、停止後に prefs が巻き戻らないことを実測で確認）。
最初はそれを疑ったが外れ。

## 使える用途 / 使えない用途

**使える**
- **CPU 律速かどうかの切り分け**＝1コアに縛って伸びるなら CPU（しかも**並列**）律速。伸びないなら別（I/O・GPU・待ち）。
- **コア数が少ない端末での「操作が間に合うか」の粗い確認**（起動・遷移が3倍になっても破綻しないか）。
- **回帰検出**＝ただし**時間ではなく「仕事量」で**。時間軸の回帰検出はホスト負荷が 4〜11 に動く共用機では
  G1 正規化を挟んでも素の幅が 3.56〜4.42 と広く、**2割程度の回帰は埋もれる**。

**使えない**
- **低スペック実機の体感の代用**。ここで再現したのは**コア数だけ**で、GPU ドライバ・メモリ帯域・サーマルは未再現。
  **「1コアで N ms だったから実機でも N ms」は言えない。**
- **メモリ制約の体感**（`heapsize` は速度に無関係。低メモリで**殺されるか**を見る手としてのみ有効）。
- **単スレッド律速の重さのあぶり出し**（① では原理的に伸びない）。

## この台に残した状態（次便への申し送り）

`emulator-5554` は `heapsize=576m` / `heapgrowthlimit=192m` / affinity `0-19` へ**戻してある**。
⚠️ **`ro.config.low_ram=true` だけは戻せていない**（`ro.` は書き込み一度きり・台の再起動が必要）。
低メモリ挙動が紛れ込むと困る計測をこの台でするなら、**先に台を作り直すこと**。
