# ランキング横スワイプのジャンクは「描画記録の削減」では届かない（残りは Slow UI thread）

## 何が起きたか

さがす→ランキングの期間横スワイプが 12%級のジャンクを出していた。真因を
「1ページ30行を単一 item で抱えており LazyColumn の間引き粒度を下回っていた」と特定し、
**順位1行＝1 item への平坦化**で構造是正した（設計＝`.claude/plans/ranking-pager-flatten-2026-08-06.md`）。

**狙った支配コストは実際に半減した。しかしジャンク率は 1 ポイントも動かなかった。**

## 実測（2026-08-07・統一条件＝12フリック/16秒・60Hz・スキンK ライト）

| 指標 | 是正前 | 是正後 |
|---|---|---|
| `draw/record`（DrawStart→SyncQueued）max | 131〜167ms（100.6ms 一点集中） | **59.9ms**（p99 47.1 / median 1.0・n=224） |
| ジャンク率 | 11.89%（p99 150ms）・再測 12.23% / 8.90% | **12.45%**（p99 150ms）／再走 **13.84%**（p99 89ms） |

＝**行平坦化は意図どおり効いているが、ジャンク率は誤差内で改善なし**。

対照に退行は無い: さがす縦 2.95%（基準 2.29%）／本棚グリッド 3.17%・p99 31ms（基準 3.82%・p99 36ms）。
遷移窓も浄化済み（push 最悪 59.7ms・**100ms超ゼロ**／pop 最悪 80.4ms）＝**ランキング横以外に特筆すべき重さは無い**。
期間送り（週間→月間）は正しく駆動＝内側ページャの機能は健全。

## ⚠️ 2026-08-14 の再計測で前提が変わった（悪化＋据わり失敗の発見）

同じ統一条件で測り直したところ、**ジャンク率は 23.39%**（n=120・p50 15ms / p90 97ms / p95 113ms / p99 133ms・
100ms 超が10枚・Slow UI thread 28）＝**ベースライン 11.89% の約2倍へ悪化**していた。
p99 だけが 150→133ms と微減。対照の本棚グリッド縦は 4.10%（p99 30ms・100ms超0枚）で台帳の 3.82% とほぼ一致
＝**計測法自体はベースラインと比較可能**（悪化は計測の揺れではない）。

決定的なのは**総描画フレーム数**で、**16秒のフリング操作で 124 フレームしか出ていない**
（対照の本棚グリッドは同条件で 463 フレーム）。これは「重いフレームが混ざる」のではなく
**フリングそのものが途中で死んでいる**ことを示す。

同じツアーで**据わり失敗**が新規に見つかった＝横スワイプ後、タブ表示は新しい期間で正しいのに
**中身だけ画面幅の 1/3〜2/3 ずれた位置で 6秒以上静止する**（縦横とも・素の `input swipe` で再現・
アニメスケール 1.0 で確認済み＝アニメ遅延ではない）。ユーザーからも独立に
「半分次のランキングが表示されて、もう一度スワイプしないと埋まらない」と報告があり、同一症状。

**帰結＝下の「次に見るべき手掛かり」の順序は変わる。** Perfetto で UI スレッド占有を名指しする前に、
**まず据わり失敗を直して測り直す**こと——低フレーム数が同根なら、08-07 の「Slow UI thread が残る」という
見立て自体が据わり失敗の影を測っていた可能性がある。

### 据わり失敗の真因＝行スロットの key に期間を含めていたこと（2026-08-14 に確定・修正済み）

当初の推定は「外側 LazyColumn の再利用や新データ差替えで行が composition を離れる」だったが、**外れていた**。
実際は**ページ送りそのものが毎回引き起こす決定論的な破棄**だった:

`items(key = "ranking_<期間名>_<index>")` が行スロットの同一性を**期間**に結び付けていた。送りが半ページを越えた
瞬間に `PagerState.currentPage` が次ページへ切り替わり、それを読む `pageOrder` も同時に変わる
→ **ランキング行の item が全数別 key になり、LazyColumn が既存スロットを破棄**する。破棄されるものの中に
「今まさに指を受けている `RankingSlotK` の `scrollable`」が含まれ、そのノードが抱えていた
**ドラッグ／スナップの coroutine が道連れに消える**。以後 `currentPageOffsetFraction` は非0のまま誰も据え直さず
（アンカーは `userScrollEnabled=false`・`LaunchedEffect(order)` も `currentPage` 一致で何もしない）、
新しく合成されたスロットの `scrollable` は進行中のポインタを拾えない（`awaitFirstDown` が来ない）
＝**指を上げて再スワイプするまで固まる**。ずれ量が 1/3〜2/3 とばらつくのは、フリングが1フレームで境界を跨ぐ量に
依存して凍結位置が変わるため。

**対処**＝行スロットの同一性を「どの期間の行か」から**座席（何行目か）**へ移した（key の1行）。
期間送りで差し替わるのは中身だけになり、指を受けているノードはページ跨ぎでも生き続けてスナップを完走できる。
位置は `translationX` が期間ごとの座席へ置くので、key で期間を分ける必要は元々なかった。

⚠️ **観測点の教訓**: タブ・`onSelectOrder`・`settledPage` は scroll session が死んでも**正しい値を名乗る**
（`isScrollInProgress=false` になるため）＝**症状は x 位置にしか出ない**。回帰テストは位置で観測すること
（`DiscoveryHomeKRankingTest`＝修正前 x=113〔89px ずれ〕で赤・key を旧式へ戻すと再び赤になることも実測済み）。

**一般化**: `LazyColumn` の `key` に「今どの状態か」を混ぜると、状態が変わった瞬間に**そのスロットが抱えている
進行中のジェスチャ／アニメの coroutine ごと消える**。key は「同一性」＝**座席**を表すべきで、
中身の由来を混ぜてはいけない。

### 修正後の再測（2026-08-14・同条件）＝**率で比べると読み違える**

| | 修正前 | 修正後 | 対照（本棚グリッド縦） |
|---|---|---|---|
| 総描画フレーム（16秒） | 124 | **351** | 383 |
| ジャンク率 | 23.39% | **6.84%** | 3.39% |
| p90 / p95 / p99 | 97 / 113 / 133ms | 53 / 69 / 89ms | 13 / 15 / 29ms |
| 100ms 超 | 10枚 | **2枚** | 0枚 |

**据わり失敗は解消**（縦10回＋横17回の計27回すべて据わり位置へ戻り、端数静止ゼロ・6秒静止の再現もなし）。
タブの期間と行内 pt ラベルの期間も毎回一致＝「タブは新期間・中身は旧位置」の乖離が消えた。

⚠️ **率の差を改善幅として読んではいけない**——分母が 124→351（**2.8倍**）に増えている。
修正前は16秒で124フレーム＝平均 7.8fps しか描けておらず、**フリングが毎回死んでアニメが走っていなかった**
（描かれないフレームはジャンクにも数えられない）。**絶対枚数ではジャンクは 15枚相当→24枚と増えている。**
正しい読みは「率が下がった」ではなく「**送りのアニメが実際に走るようになり、16秒あたりの描画が 2.8倍になった上で、
遅延フレームの比率が対照の2倍程度に収まっている**」。

**残るコスト**: p90 53ms・p95 69ms は対照（13/15ms）比で明確に重い＝**ページ送りアニメ自体のコストは残る**。
⚠️ ただし 08-07 の「Slow UI thread を Perfetto で名指し」へ戻る前に、**この 6.84% が「アニメが走るようになった
状態での初めての正味の計測」**であることを踏まえること——それ以前の計測はすべて、フリングが死んでいた状態を測っていた。

**一般化＝「操作が途中で死ぬ」バグがあるとき、ジャンク率は分母が縮むぶん良く見える。**
率を比べる前に必ず総描画フレーム数を突き合わせること。フレームレート系の指標は、
**測る対象そのものが走っていない**という失敗モードを表現できない。

## 据わり失敗の修正で判明した残件（2026-08-14）＝**①は 2026-08-19 に是正済み・②が残る**

**① アンカーが `contentPadding` を受けていない＝指の位置と覗きの位置がずれる**（**2026-08-19 に是正済み**）

`RankingPagerAnchorK` は LazyColumn の**外**にあり `contentPadding`（左右 S24）を受けないので、
`pageSize`＝画面幅に対し行の実幅は 画面幅−48px。結果、**1ページ送るのに指は行幅の 1.18 倍動かす必要があり、
覗きの溝も S24 でなく S24+48px になる**——`RankingPageSpacing` の KDoc が避けたかった
「指の位置と覗きの位置のずれ」が構造として残っていた。

**直し方（採った形）**: 縦リストの左右マージンを top-level の `DiscoveryListHorizontalMargin` に括り出し、
LazyColumn の `contentPadding` とアンカーの**両方が同じ1値を見る**構造にした。アンカーは `horizontalMargin` を
受けて `padding(horizontal = ...)` 込みで measure される＝`pageSize` が行の実幅と一致する。
`rankingPageStepPx`／`rankingPageOffsetPx` は `pageSize` からの導出なので式は無改変で追従する。
⚠️ **余白を与えているのは意匠でなく採寸のため**（アンカーは高さ0・不可視）＝可視の見た目は不変で golden 影響なし。

**② フリング中に別の指で縦スクロールすると同じ凍結が起こり得る**

当該行が可視域を外れると、key 是正後も同じ経路（スロット破棄→coroutine 道連れ）を踏み得る
（引き金は key ではなく**可視域外れ**）。⚠️ **未実測の推論＝再現は取れていない。**
構造から消せるのは上の「入れ子の反転」だけなので残置している。

## この端末で遷移の jank を測るときの前提（2026-08-19 実測で確認）

- ⚠️ **パネルは120Hz（modeId 6）でもアプリ窓の `FrameInterval` は 16.67ms＝60Hz 稼働**。
  よって jank 境界は 16.67ms で、2026-07-16 の 60Hz ベースラインと同じ土俵で比較してよい。
  **120Hz だと思って 8.3ms 境界で数えると率が跳ね上がる**ので注意。
- **「アニメが走っていない状態を率で比較する」罠は、2つの対照で潰せる**:
  ①**静止対照**＝無操作のまま同じ長さの窓を取り `Total frames rendered: 0` を確認する（分母に無関係フレームが
  混ざっていないことの証明）②**窓の連続性**＝窓の span と vsync 間隔から理論フレーム数を出し、実測枚数と突き合わせる
  （毎 vsync 描けていればアニメは最後まで走っている）。**率だけ見ても罠は見抜けない。**
- **率と尾は別の指標**＝率が低くても尾が重いことがある（本棚→目次は率 13.83% で最大 138.0ms、
  本棚→本文は率 20.77% で最大 56.0ms）。**率だけで比べると重い方を見落とす。**

## 2026-08-26: 真因を名指しした＝「アニメ中の毎フレーム」ではなく**送り1回につき2枚だけ**の全数再合成

上の「次に見るべき手掛かり」（UI スレッドで何が走っているかを名指しする）に決着。
計測は**エミュ AVD `nr_api36`**（API 36・1080x2400・420dpi・60Hz）。⚠️ 絶対値は実機の代用にならないので、
使ったのは**位相分解と対照との比**だけ。

### まず計測法の訂正: このエミュでは gfxinfo の `Number Slow UI thread` を信じてはいけない

エミュは GL passthrough が遅く、**UI スレッドが `postAndWait`（RenderThread 待ち）で毎フレーム 18ms 前後
ブロックする**。gfxinfo の "Slow UI thread" は `SyncQueued - IntendedVsync` 系の判定なので、この**バックプレッシャを
UI スレッドの仕事として数えてしまう**（実測: 遅いドラッグで 203/321 枚が Slow UI thread と出たが、実際の UI
スレッド仕事は p50 4.0ms しかなかった）。
⇒ **エミュでは `framestats` を位相へ分解し、`HandleInputStart → SyncQueued`（＝UI スレッドの自分の仕事）だけを見る。**
`total` も見ない（p50 50ms は横スワイプでも縦スクロールでも同じ＝エミュの GPU 固定費）。

### 対照2本で「アニメが走っているか」を潰した上での結果

- **静止対照**: 無操作16秒で `Total frames rendered: 0`＝窓に無関係フレームは混ざっていない。
- **同じ行の縦スクロール**（ランキング行のまま縦に流す・ページャだけが無い）= 830枚/15.2秒。
- **ランキング横スワイプ** = 333枚/15.9秒。フリック12回×スナップ約450msで理論 324 枚とほぼ一致
  ＝**フリングは死んでいない**（据わり失敗の再発なし）。

| `framestats` 位相（p50 / p90 / p95 / max, ms） | 横スワイプ | 同じ行の縦スクロール |
|---|---|---|
| `uithread`（HandleInput→SyncQueued） | 2.5 / 6.6 / **26.6** / **53.8** | 1.6 / 7.6 / 9.8 / 16.3 |
| `draw/rec`（DrawStart→SyncQueued） | 0.3 / 1.0 / **14.1** / **36.0** | 0.0 / 0.9 / 1.1 / 2.2 |

p50・p90 は**両者ほぼ同じ**で、差は完全に尾にだけ出る。率でなく**枚数の分布**を見ないと見えない形。

### 決定的な対照＝端の期間でフリックすると `Total frames rendered: 0`

新着（最終ページ）で同じ全速フリックを12回打つと、**描画フレームが1枚も出ない**。
このとき指を受けているのは実データの行の `scrollable`（＝機構は全部生きている）が、
`currentPageOffsetFraction` が 0 のままなので**覗きも出ず・ページも変わらない**。
⇒ **`scrollable` / `nestedScroll` 封止 / `PagerDefaults.flingBehavior` / 行ごとの `graphicsLayer`＝コスト 0。**
横スワイプの重さは 100% が「合成が起きる2つの瞬間」に由来する。

### 真因（機序）: 送り1回につき、重いフレームはちょうど2枚

atrace（`-a com.novelreader` + gfx/view/input/sched）で、UI スレッドのフレームを重い/軽いで割ると:

| | 枚数 | frame | postAndWait(エミュGPU) | anim(再合成) | measure&layout | record draw | **`Constructing StaticLayout`/枚** |
|---|---|---|---|---|---|---|---|
| 軽い(≤40ms) | 140 | 22.1 | **18.1** | 2.9 | 0.9 | 0.8 | **0.9** |
| 重い(>40ms) | 9 | 57.4 | 9.7 | 13.2 | **25.8** | **32.7** | **58.2** |

**軽いフレームは UI スレッドの仕事が約3ms＝ページ送りアニメ自体はタダ**（`translationX` の deferred read は効いている）。
重いフレームだけが UI スレッド CPU 律速で、中身は**テキストの合成と計測**。フリック1回ごとに規則正しく2枚:

- **A: 指が動き出した最初のフレーム**（`uithread` 27〜32ms・StaticLayout **42個**）
  ＝`neighborOrderState` が null→非null になり、**覗き用の行が可視行ぶん丸ごと新規合成**される。
  42 ＝ 可視6行 × 1行あたりテキスト7個（順位・題・作者・ジャンル・話数・分・pt）。
- **B: 送りが半ページを越えたフレーム**（`uithread` 50〜54ms・StaticLayout **96個**）
  ＝`PagerState.currentPage` が変わり `pageOrder` が動く。**据わりと覗きは役割だけが入れ替わる**
  （跨ぐ前〈据わり=週間・覗き=月間〉→跨いだ後〈据わり=月間・覗き=週間〉＝**居る期間は同じ2つ**）のに、
  旧実装は枠を役割の順（第1子=据わり・第2子=覗き）で並べ、行へ渡す値（`onOpenDetail`/`onRefresh` の
  null 有無）も役割で変えていた。結果、**同じ枠に別期間の中身が流し込まれて両方が全数再合成**される。

**⇒ 08-07 の「Slow UI thread が残る」の正体は、描画記録でも measure でもなく〈役割の入れ替わりで
composition が作り直される〉こと。** 08-06 の平坦化（可視行だけ合成する）は正しく効いており、
軽いフレームの StaticLayout が 0.9 個/枚であることがその証拠。**同じ道をもう一周する必要はもう無い。**

### 未着手の別案「入れ子の反転」の評価＝**採らない**

`.claude/plans/ranking-pager-flatten-design-2026-08-13.md` は前提が腐っている: 目的として掲げる
「可視行だけ実体化する」は**08-06 の平坦化で既に達成済み**で、根拠にしている `draw/record` 131〜167ms・
1ページ30行の素 `Column` はもう存在しない（現行の軽いフレームは `draw/rec` 0.3ms）。
上の A/B に効くかで見ると、反転は確かに両方を構造的に消せる（ページごとに中身が固定されるので役割の
入れ替わりが無く、`beyondViewportPageCount=1` も高さ固定なら安全に戻せる）が、代償が大きい:
外側 LazyColumn の廃止・`SubcomposeLayout` の新設・ヘッダ折り畳み機構が要り、
**08-07 に入った期間タブの `stickyHeader` と正面から衝突する**（プランは sticky を別便として書いている）。
しかも `DiscoveryHomeInvariantTest`・`DiscoveryHomeKRankingTest` が偽陽性化する（プラン自身の申し送り）。
**B は反転なしで消せる**ことが上の機序から分かったので、費用対効果で採らない。プランは凍結のまま置く。

### 採った対処（2026-08-26・`DiscoveryHomeK.kt`）＝**枠を役割でなく期間 ordinal の偶奇で持つ**

隣り合う期間は ordinal が必ず1違う＝**偶奇が必ず食い違う**ので、行の枠を偶奇2つに固定すると
「どちらの枠にどの期間が入るか」が**役割にも送りの向きにも依存しなくなる**。半ページ地点では両方の枠が
同じ期間を持ち続ける＝composition から見て**何も起きない**（動くのは `translationX` だけ）。

- `RankingSlotK` を〈据わり＋覗き〉から〈偶数枠／奇数枠〉へ。新設 `BoxScope.RankingPageLayerK` が1枠を描く。
- `seated` は**描き方だけ**（高さを決めるか・TalkBack に読ませるか）を切り替える。modifier の差し替えは
  ノードの付け替えで済み、テキストの計測結果は生き残る。
- `RankingSlotBodyK` の導線を非 null 化＝**据わりも覗きも同じ値を受ける**。覗き行を踏ませない目的は
  「送りが走っている間はどの行も飛ばない」（`rankingOpenDetail`／`rankingRefresh`）へ移した
  ＝**元の裁定より範囲が厳しい**（指を離した直後のスナップ中の誤タップも塞がる）。

⚠️ **実測の結果、B は「消えた」のではなく「縮んだ」**（下の実測節が正）。

### 残件: A（覗きの新規合成・42個・27〜32ms）は残る

消すには覗きを**送りの外でも常駐**させる必要がある（`settledPage` を軸にした ±1 の常駐窓が素直）。
ただし常駐は「非表示のページは合成されていない」という前提を壊す＝
`DiscoveryHomeInvariantTest`・`DiscoveryHomeKRankingTest` の観測点を
〈合成されていない〉から〈表示されていない〉へ強化するのが**先**（反転プランの申し送りと同じ関門）。
なお常駐にすると1フリックあたりの総合成量は 138→42 テキストへ減り、その42も**据わった後の静止フレーム**へ移る。

### 実測（2026-08-26 夕・対処を含む APK・同一台/同一手順）＝**B は消えず「縮んだ」。半分の勝ち**

atrace で同じ4フリックを取り、フレームごとに `Constructing StaticLayout` を数えた（**これが denominator を持たない
唯一の指標**＝gfxinfo の率も `total` もエミュの GPU 負荷が走ごとに揺れるので効果量の根拠にしない）:

| 1フリックあたりの重いフレーム | 対処前 | 対処後 |
|---|---|---|
| A（指が動き出す枚）| StaticLayout **42個** / 35〜47ms | StaticLayout **42個** / 41〜50ms（**不変**・想定どおり残る） |
| B（半ページを越える枚）| StaticLayout **96個** / 61〜76ms | StaticLayout **9個** / 33〜35ms |
| 4フリックの StaticLayout 合計 | 554 | **204**（−63%） |
| 最悪フレーム | 76ms | 50ms |

- **狙った所は当たった**＝B のテキスト計測は 96→9 個でほぼ消滅（役割の入れ替わりが composition を作り直さなくなった）。
- **しかし B はスパイクのままで残る**（33〜35ms）。中身は `measureAndLayout` 12.9〜14.8ms で、
  **StaticLayout がほぼ0なのに measure が残る**＝原因はテキストでなく**レイアウトの測り直し**。
  ほぼ確実に `RankingPageLayerK` の `matchParentSize` が役割で入れ替わること（据わりだけが高さを決める）で、
  半ページ地点で両方の枠が remeasure されるため。**次の一手はここ**＝高さの決め方も役割から独立させる。
- `framestats` の `uithread` p95 は 26.6 →(3走) 31.4 / 25.4 / 22.9 ＝**改善は読み取れない（走間のばらつきの内側）**。
  改善が出たのは尾の先端だけ＝`uithread` max 53.8 → 37.4〜46.3。
  ⚠️ gfxinfo の率は 29.7%→11.0% と大きく動いたが、同じ APK の3走で `total` p50 が 33〜48ms と揺れる
  ＝**エミュの GPU 負荷の差であって効果量ではない**。この数字を成果として引用しないこと。
- **1フリックの UI スレッド・スパイク時間は約81ms→約64ms（−21%）**。体感（2026-08-21 の実機ツアー）の
  再判定は実機でしかできない＝**実機ツアーに載せるまで「直った」とは言わない**。
