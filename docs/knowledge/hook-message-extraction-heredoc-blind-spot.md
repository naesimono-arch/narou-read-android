# コミットメッセージを読むフックは `-m` だけ見ると実運用で沈黙する

> 正本コード: `.claude/hooks/remind_task_diary.py`（`_messages()`）・回帰＝`test_remind_task_diary.py`

## 事実（2026-08-07 実測）

`remind_task_diary.py`（知見の置き場 想起）はコミットメッセージを
`-m\s+(['"])(.*?)\1` でしか取り出しておらず、**`git commit -F - <<'MSG' … MSG` の
ヒアドキュメント形式では一度も発火しなかった**。あるラウンドの 18 コミットは全てこの形式で、
想起は終日死んでいた。エラーも警告も出ない。

両形式を実際に流して確認した結果:

| コミット形式 | 旧実装 | 修正後 |
|---|---|---|
| `git commit -m "fix: …"` | 発火 | 発火 |
| `git commit -F - <<MSG … MSG` | **沈黙** | 発火 |
| `git commit -F - <<'MSG' … MSG` | **沈黙** | 発火 |
| `docs:` 接頭辞（対象外） | 沈黙 | 沈黙 |

## なぜ危険か（逆相関）

**長い日本語メッセージを書くほどヒアドキュメントを選ぶ**——`-m` に改行入りの本文を渡すのは
シェル的に扱いづらいため。つまり「why を厚く書いた重要なコミットほど想起が飛ぶ」という
逆相関になっていた。想起が要る場面でこそ黙る設計だったということ。

旧コメントは「heredoc 等で -m が取れない場合は判定不能 → **安全側**（無出力）に倒す」と
書いていた。これは**安全側の取り違え**で、想起フックにおける安全側は「出しすぎ」であって
「黙る」ではない（ブロックしないフックなので誤発火のコストは低い）。

## 対処

`_messages()` で以下を全て拾う: `-m "..."` / `-m '...'` / クォート無し `-m` /
`<<'WORD' … WORD` 形式のヒアドキュメント本体（`-F`・`--file`・`-t` のいずれで渡されても本体は同じ形）。

## 一般化

**フックが「コマンド文字列から意味を取り出す」設計になっている場合、取り出し方の網羅は
陽性コントロールでしか担保できない**。書いた本人は自分が普段使う形式しかテストしないため、
同じ意味の別表記（heredoc・`--file`・環境変数展開・`git -C`）が丸ごと盲点になる。
新設・改修のたびに**実際に使う形式で1回流す**こと。関連する同クラスの失敗＝
`.claude/hooks/` の `task_diary.md` #28（PostToolUse の plain stdout がモデルに届かない）。
