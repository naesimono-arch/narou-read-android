# コンテキスト費をフックで削る2案の実測上限（切り詰め 2.6%・調査Read 判定 76.6%）

★★★ / 2026-08-17 実測

**1行要約**: 読み込み側の2大レバー（Bash 出力の自動切り詰め・調査 Read の自動振り分け）をフックで取りに行けるか実測した結果、
**前者は全体の約 2.6% しか削れず**、**後者は決定時点の情報では上限 76.6%＝機械判定が原理的に成立しない**。
どちらも「規律（人が決める）」側に置くのが正しい。費用構造そのものの正本は `context-cost-breakdown-2026-08-10.md`。

## 1. Bash 出力長の実測分布（再導出＝`tools/measure_bash_output_size.py`）

過去 119 セッション・Bash/PowerShell の tool_result **3,889 件**。数え方は実効寄与＝トークン×そのターン以降に残るターン数。

- 分布（文字数）: **p50=356 / p90=2,141 / p95=3,239 / p97=4,344 / p99=7,882 / 最大 25,245**
- Bash 出力の占有＝全体の **22.3%**（2026-08-10 実測の 20.1% と同水準＝比率は安定）

閾値ごとの介入率と削減率（削減率は Bash 出力の実効寄与に対する比）:

| 閾値 | 介入率（何回に1回触るか） | 削減率 | 全体に対する削減 |
|---|---|---|---|
| 2,000字 | 10.8%（9回に1回） | 24.3% | 約 5.4% |
| 4,000字 | 3.6%（28回に1回） | 11.5% | **約 2.6%** |
| 6,000字 | 1.6% | 6.7% | 約 1.5% |

**分布が p50=356 と極端に軽い方へ寄っている**のがこの案の限界の正体で、閾値を下げないと量は取れないが、
下げると「普通の出力」まで触り始める。**全体の 2.6% と引き換えに監督が見る出力を加工する**釣り合いにならず、凍結（§5）。

## 2. `hookSpecificOutput.updatedToolOutput` は実在するが公式 docs に無い

PostToolUse の plain stdout はモデルに届かない（task_diary #28）ため、当初調査は「切り詰めは不可能」と結論した。
これは**誤り**で、本体バイナリ（Claude Code 2.1.233）には `updatedToolOutput` が実装されている:

- 説明文字列 "Replaces the tool output before it is sent to the model"・パース箇所は `u.updatedToolOutput = e.hookSpecificOutput.updatedToolOutput`
- 返した値は**当該ツールの outputSchema で検証**され、合わなければ**元の出力へ差し戻し**＋可視の `hook_error_during_execution`
  ＝サイレント化はしない（差し替えるときは元 dict の全キーを保ったまま1キーだけ置換するのが最も安全）
- **同梱の公式 docs には未記載**

⚠️ **教訓＝docs 根拠だけで「不可能」と断じない**。ハーネスの機能可否は**バイナリを一次ソースにする**（実際に一次確認前の調査が誤結論を出した）。
逆に、未文書化フィールドへの依存は**いつ壊れてもおかしくない**＝それ自体が採否の減点材料になる（§5）。

## 3. 「調査 Read」を実行時点で機械判定するのは原理的に不可能（再導出＝`tools/measure_read_delegability.py`）

調査 Read（読んだきりで編集しなかった Read）は Read 実効寄与の 41.3% を占めるので、
「PreToolUse で検出してサブへ誘導できないか」が問われた。答えは**できない**:

- 正解ラベルが**後ろ向き**——「その Read **より後に**同じ path が編集されたか」＝ PreToolUse には**未来が見えない**。
- 決定時点で実際に見える特徴（トップディレクトリ・拡張子・部分読みか・当該セッションで既に編集済みか）の
  **全組合せで最良の規則を作っても上限 76.6%**（978 件）。基準線（多数派に倒すだけ）は 60.3%。
  しかも**同一データへの当てはめ＝ホールドアウトではない楽観値**で、実運用はこれより必ず低い。
- 拡張子別は `.md` 50.4%／`.kt` 50.4%＝**コイン投げ**。Read の **31.3% が両義パス**（同じ path が調査にも編集起点にもなる）。
- ⚠️ 決定打＝**このハーネスは Edit が事前 Read を要求する**ので、誤ブロックは編集そのものを不能にする。
  非対称な損失（取り逃しは「削れないだけ」／誤ブロックは「作業が止まる」）＝ADR 0031 決定1「ゲートは fail-open 側へ倒す」と同じ結論。

**帰結**: 調査 Read の委譲は**フックで強制せず CLAUDE.md の規律で運ぶ**（「Read の前にこのターンで自分が編集するかを決める」）。

## 4. 副産物の盲点＝画像は文字数で測ると安く見える

同じ走査で判明: **`.png` の Read が 300 件**あり、**`.output` は 100% が調査 Read**。
画像 Read は**文字数ベースの計測では極小に見えるがトークンでは高い**＝
`tools/measure_*` 系（CH2TOK=4.0 の文字数換算）は**画像を過小評価している**。
画像コストを論点にするときは、この計測群の数字をそのまま使わないこと。

## 5. 裁定（2026-08-17 ユーザー）

切り詰めフックは**凍結**。理由＝削減 約2.6%（介入率 3.6%）に対し、①**未文書化フィールドへの依存**
②**監督が見る出力そのものを加工する監視パイプラインの改変**（ハーネスも self-modification のセキュリティ警告を出した）で釣り合わない。
実装の所在・解凍条件・復元方法＝`docs/backlog-frozen.md`「Bash 出力の自動切り詰めフック」。
