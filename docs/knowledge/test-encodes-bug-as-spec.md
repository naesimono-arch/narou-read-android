# 手書きのテストがバグの挙動を仕様として固定し、修正を赤で妨げる

**開く合図**: **バグを直したら既存のテストが赤くなったとき**。
「壊した」と判断して修正を戻す前に、**そのテストが何を守っているのか**を一度読むこと。

## 何が起きるか

`recordRoborazziDebug` が壊れた描画を無条件に正解として焼き込む問題
（`golden-record-bakes-in-regressions.md`）は**自動生成のオラクル**の話だが、
同じ家系の事故が**人が手で書いたテスト**でも起きる。しかもこちらの方が質が悪い——
自動記録は「誰も意図を述べていない」だけだが、手書きのテストは
**意図を述べた顔をして間違った仕様を主張する**。

赤くなったテストは既定では「自分の変更が壊した」と読む。その既定が正しくない場合があり、
**テストが赤いこと自体が修正の正しさの証拠**ということが起こりうる。

## 実例（2026-09-04）

`TextProcessorTest.fourPagesOrFewerYieldNoParagraphs` は
「総ページ4以下なら抽出結果は段落0件」を assert していた。KDoc には

> 総ページ4以下は固定トリム（先頭3＋末尾1除外）で全ページが落ち、段落0件になる（監査 A3 の機序）。
> この出力を取込が成功で確定しないことは repository 層の章0件ゲートが担う＝ここでは機序だけを固定する。

と書かれていた。つまり**監査で見つかった欠陥を、直さずに「機序」として記録し、
下流のガードで受け止める設計**として合意されていた。テスト名も `...YieldNoParagraphs` で、
「そうなるのが正しい」と読める。

実際には、これは**無作為標本42本中6本（14.3%）で作品の本文が丸ごと失われる**バグだった
（前付けのページ数を定数3で切っていた＝`narou-pdf-structure-survey-2026-09.md` §5）。
真因を直したらこのテストが赤くなり、**赤くなったこと自体が修正が効いた証拠**だった。

## なぜ見抜きにくいか

1. **下流にガードがある**と「握り潰していない」ように見える。この件も「取込が成功で確定しない」ので
   サイレント失敗ではなかった。だが**ユーザーから見れば短い作品が取り込めない**という実害は残る。
2. **監査由来の記録**は権威に見える。「機序を固定する」という言い方は、仕様の主張ではなく
   観察の記録のつもりでも、テストにした瞬間に**変更を妨げる規範**になる。
3. テスト名が挙動をそのまま述べていると、**その挙動が望ましいのか**が名前からは判断できない。

## どうするか

- **バグ修正で赤くなったテストは、直す前に KDoc と名前を読む**。「その挙動は望ましいか」を
  テストの主張とは独立に確かめる（この件では実データの標本が答えを出した）。
- **既知の欠陥をテストで固定するときは、望ましさを名前か KDoc に明示する**。
  「いま こうなる」と「こうあるべき」は別物なので、前者なら**将来直す対象である**と書く。
- 書き換えるときは**旧の主張を消さずに残す**（なぜ覆したかが次の人に要る）。
  この件は経緯を KDoc に残し、修正後の契約を3型のテストへ置き換えた。
