# `HorizontalPager` に隣接ページを常駐させると wrap 高の前提が壊れる

## 機序

`HorizontalPager` の交差軸（縦）サイズは、**測定したページの最大高**で決まる。
既定の `beyondViewportPageCount = 0` では現在ページしか測定しないので、
「ページャの高さ＝現在ページの高さ」という wrap 相当の振る舞いになる。

**`beyondViewportPageCount` を 1 以上にした瞬間、この前提が壊れる。**
隣接ページも測定対象に入るため、ページャは「現在ページと隣接ページのうち最も高いもの」の高さを取る。
現在ページがそれより低ければ、`verticalAlignment = Top` の下に**差分ぶんの空白**が生まれる。

## 実例（2026-07-31・撤回済み）

さがすのランキング期間スワイプが重い（Janky 11.89%・`draw/record` 100.6ms 一点集中）ため、
`TabPagerHost` で実績のある「隣接ページの先行実体化」を `RankingPagerK` にも当てようとした。

- 現在ページ（週間）＝10行の Content ／ 隣の日間・月間＝**未訪問なので骨30行**（`DiscoveryQuery().limit`）
- 結果、ページャは30行ぶんの高さになり、**週間10行の下に20行ぶんの空白**が生まれた
- 実データは全期間30行で揃うため**平時は見えない**。現在期間が Empty/Error（status 1行）へ落ちた瞬間、
  1行の文言の下に30行ぶんの空白が広がる＝**実機の退行**

`RankingPagerK` の KDoc が「高さは wrap＝現在ページ準拠」と明文化していたのが決め手だった。
**壊れた前提がコード内に書いてあった**ので、構造から断定できた。

## 同じ手が効く場所との違い

同じ `beyondViewportPageCount` を既に使っている2箇所は**無罪**で、違いは高さの決まり方にある:

- `TabPagerHost`（本棚⇄さがす⇄設定）＝各ページが `fillMaxSize`。**全ページ同高**なので最大高を取っても変わらない。
- `WardrobeScreen` のカルーセル＝**固定寸のカード**。同上。

⇒ **この手が安全なのは「全ページが同じ高さになる」ページャに限る。**
中身の量でページ高が変わるページャ（一覧・検索結果・可変長コンテンツ）には当ててはいけない。

## ランキングの jank は未解決に戻った

真因は「1ページ＝30行の**素の Column**（lazy でない）が、外側 LazyColumn の単一 item ≈2800dp として
抱かれ、画面外の行まで全数が合成・記録される」こと。常駐化はこれを前倒しするだけの対症で、
しかも上記の副作用を持つ。次に手を入れるなら真因側:

- 行を外側 LazyColumn の item へ**平坦化**して可視行だけ合成する
- ページ高を**現在ページだけから決める**測定に変える

いずれも高さ設計の作り直しとセットになる。
