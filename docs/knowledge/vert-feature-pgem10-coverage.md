# PGEM10(ColorOS) の OpenType "vert" feature は「回転が要る約物」を回さない

★★★ 2026-07-17 — vert は句読点・括弧・小書きには効くが …；− を回さず ‥ は書体割れ＝回転判定を vert に委ねられない

**結論**: `Paint.fontFeatureSettings="vert"` は句読点・括弧・長音・小書き仮名の縦用字形には効くが、
**…(U+2026)・；(U+FF1B)・−(U+2212) には両書体（default/serif）とも効かず、‥(U+2025) は serif のみ効く（書体割れ）**。
＝縦書きで90度回転が必要な文字の判定を vert に委ねてはならない。回転判定は自前の文字クラス表が持ち、
vert の役割は「位置替え・字形差し替え」に限定する。

**なぜ重要か**: 縦書き実装の方式選定（自前オフセット回転経路を最初から持つか）を左右する。
‥ の書体割れは「フォント実体に依存する挙動をランタイム判定やフォント前提で吸収する」設計が
脆いことの実証＝**書体非依存の CharClassifier 主導フォールバック**が必須根拠。

**測り方**: 1文字を fontFeatureSettings 未設定/"vert" の2条件でオフスクリーン Bitmap に描き
ピクセル一致比較（65字×2書体、2026-07-17 実機）。？！・・（中点）・全角英数字は「変化なし」が
縦書き規範上も正解（正立）なので、「効かない＝バグ」ではない点に注意。

**付随の実測**: serif は小書き仮名20字で vert 適用時に advance が 64→65px に変わる
＝グリフ送りの等幅前提は置けない（実測 advance を使う）。

**追加計測（2026-07-17 v2・P0-2bで発見した8字）**:
- **〝〞(U+301D/U+301E)＝vert 有効**（両書体）→ PUNCT_REPOSITION（vert適用経路）
- **―(U+2015)＝vert 無効**（両書体）→ MANUAL_ROTATE_REQUIRED へ追加（――連続の構成字。放置すると横倒れしない）。
  —(U+2014)・‐(U+2010)・–(U+2013) は未計測だが同系のため防御的に自前回転（自前回転は安全側＝vert有効字に使っても視覚等価）
- Ⅳ(U+2163)・ギリシャ αβγΔ＝変化なし（正立が正解＝現分類どおり）。α等は advance 36〜45px のプロポーショナル

生JSONL `android/app/src/test/resources/typeset/vert_probe_pgem10.jsonl`

## 棚卸し 24 字の実測（2026-09-04）— 推定は概ね裏付き、代わりに宿題が 2 群だけ残った

2026-09-03 に「実データに出るのに vert 実機計測が無い」と棚卸しした 24 字を、PGEM10 実機で計測した
（`SpikeActivity` の P1 タブ＝`Probe1FontFeature`。97 コードポイント × default/serif = 194 計測）。
⚠️ **既存 146 計測は値まで 1 件も動いていない**（bounds/advance/changed の全フィールドで一致）＝
今回の追加は上位集合で、旧計測の退行ではないことを機械照合で確認済み。

**結論**: 推定で置いていた分類は概ね実測で裏付けられた。ただし **vert が効くのに vert を適用しない経路に
居る字（`￣ゝヽヾ`）** と、**Tr なのに主段（変形）が出ない字（`“”‘’`）** の 2 群だけ、新しい判断が要る。

| 字 | vert（両書体とも同結果） | 現在の分類 | 実測が言うこと |
|---|---|---|---|
| `〟`U+301F | **有効** | `PUNCT_REPOSITION` | 同族 301D/301E からの推定が裏付いた。実データの主役 593 件がこれで実測済み |
| `￣`U+FFE3 | **有効** | `UPRIGHT` | ⚠️ **縦字形を持つのに使っていない**（`GlyphRenderer` は UPRIGHT に vert を適用しない）。実データ 4 件 |
| `ゝ`U+309D / `ヽ`U+30FD / `ヾ`U+30FE | **有効** | `UPRIGHT` | ⚠️ 同上（繰り返し記号・計 17 件）。「表に無いので既定落ち」だった判断が実測で覆りうる |
| `－`FF0D / `—`2014 / `‐`2010 / `–`2013 | 無効 | `ROTATE` ＋自前回転必須 | 「同系ダッシュだから」の防御的推定が裏付いた＝**自前回転が要る側**で正しい |
| `“”‘’`U+201C/201D/2018/2019 | 無効 | `PUNCT_REPOSITION` | ⚠️ UAX#50 の **Tr の主段（変形）が PGEM10 では出ない**＝いま画面に出ているのは正立。規範どおり fallback 段＝回転へ倒すかは未裁定（実データ 7,319 件） |
| `↑↓`・`‼⁉`・`％℃°′″＃＄` | 無効 | `UPRIGHT`（既定落ち） | 変形しない＝正立のままで版面不変＝**現分類と矛盾しない**（既定落ちだが結果は規範と同じ） |

**読み違えないこと**: 「vert 有効」は「今のままでよい」を意味しない。描画層は
`UPRIGHT` に vert を適用しない（`GlyphRenderer.drawGlyph`＝UPRIGHT だけ `useVert=false`）ので、
**有効と出た字が UPRIGHT に居るなら、持っている縦字形を捨てている**状態になる。

**残った宿題**（実測では決まらない＝実機で見て決める）だった 2 項目
（①`“”‘’` を Tr の fallback 段（自前回転）へ倒すか ②`￣ゝヽヾ` を vert 適用経路へ移すか）は
**2026-09-07 に裁定済み**＝下の「宿題2件の裁定」節。

**測り方**は上の「測り方」節と同じ。実機が要るので `/device-verify` 案件＝**計測できない便で分類だけ
足さないこと**。足すなら「推定である」と分かる形で残す（置き場＝`VertFeatureCoverage.UNMEASURED_IN_VERT_PROBE`
＝2026-09-04 時点は空。`VertProbeUnmeasuredTest` が JSONL と突合して守る）。

## 実機の版面での見え（2026-09-04）— 「計測値」ではなく「読者に見えている絵」

上の節までは `Probe1FontFeature` の**計測値**（vert の有効/無効）。ここは同じ端末で
**実際の読書画面に何が出ているか**を撮って確かめたもの（捨て本 `cf4ee71b` の1章を検証用テキストへ
差し替えて縦書きで表示・撮影後に md5 照合で原本へ復元）。宿題2件の裁定材料はここが正本。

- **`“”‘’`（宿題①）**＝**正立のまま。破綻はしていない**（読めるし字形も崩れない）。ただし縦組みの列に対して
  字が中心よりやや左へ寄り、開き/閉じの区別は「向き」ではなく形だけが担う。
  ∴ **据え置き（版面不変の安全側）を選ぶ根拠は実機の見えにある**——回転へ倒す動機は規範適合であって可読性ではない。
- **`ゝ ヽ ヾ`（宿題②の一部）**＝**正立で自然**。もともと縦書きで使う繰り返し記号なので、
  vert 適用経路へ移す実益は見えにくい（**動機は「持っている縦字形を捨てている」という筋論の側**）。
- **`￣`（宿題②の一部）**＝**横棒のまま**描かれる。縦組みの本文に横棒が1本入るので、
  **漢数字の「一」と紛らわしい**＝この字だけは vert 適用へ移す実益が見える（ただし実データ 4 件）。
- ついでに確かめた同族: **`～`FF5E・`—`2014・`…`2026 は縦向きに描かれる**（自前回転が効いている）。
  ⚠️ **`－`FF0D の見えは未確定**——撮影の切り出し外で、記号列末尾に残った横棒が `―`2015 か FF0D かを
  分離できなかった。上の表の計測（vert 無効・`ROTATE` 分類＋自前回転必須）から**回っているはず**だが、
  見えとしては未確認。確かめるなら1字1段落で並べ直すこと（列が分かれて取り違えようがなくなる）。

**同じ便で確かめた組版の他の2点**（縦書き全般の見え。B-11 と ADR 0041 の実機確認）:
- **句読点のぶら下げ（B-11）は効いている**。版面下端で他の列の最下端が y=2772 のところ、
  ぶら下がった読点だけ y=2783＝**11px** だけ外へ出る（読点のインクが小さいため見た目の突出はごく僅か）。
  旧 Reference の「列が版面から 52px はみ出す」状態とは別物。**閉じ括弧の追い出しも効いている**（列頭に `）` は出ない）。
- **ADR 0041 の副作用は実データでは顕在化していない**。カクヨム取込 `6c726cfe` は 148 行中 142 行、
  PDF 由来 `cf4ee71b` は 71 行中 70 行が字下げ/開き括弧始まり＝**結合対象がほぼ無い**。画面でも段落は分かれたまま。

## 宿題2件の裁定（2026-09-07）— `￣` だけ vert へ移し、`“”‘’ゝヽヾ` は正立で据え置き

裁定の材料は上の「実機の版面での見え」に加えて、**UAX#50 の Vertical_Orientation を一次ソースで引いた**もの
（`https://www.unicode.org/Public/UCD/latest/ucd/VerticalOrientation.txt`）。これで
「vert が効く＝縦字形を持っている」という読みが**字によって成り立たない**ことが分かった。

| 字 | UAX#50 VO | 実測 bounds の変化 | 裁定 |
|---|---|---|---|
| `￣`U+FFE3 | **Tr** | (0,-57)-(64,-53) 64×4 の横棒 → (61,-57)-(64,9) 3×66 の縦棒（中心が右 30.5px・下 31px） | **vert 適用へ移す** |
| `ゝ`U+309D `ヽ`U+30FD `ヾ`U+30FE | **U（正立）** | 差は最大 3px・多くは 1px・字面中心が動かない | 据え置き（正立） |
| `“”‘’` | Tr | 変化なし（主段が出ない） | 据え置き（正立・回転へ倒さない） |

**①`“”‘’` を回転へ倒さない理由**（実装は `CharClass.kt` の `PUNCT_REPOSITION_CHARS` KDoc に同じ 3 点を記録）:
1. `drawManualRotate` は**セル中心 pivot の単純な 90 度回転**だが、Tr の主段は「回転＋隅への位置替え」の合成。
   同族 〝U+301D の実測が字面 18×27 → 27×19（縦横比が入れ替わる）で、さらに `〞`U+301E と `〟`U+301F は
   **2 字とも同一の vert 字形 (1,-55)-(28,-36) へ寄る**＝位置替えを伴う。中心で回した絵は主段の代用にならない。
2. 焼き込むと **vert が効く書体で二重変換**になる（MANUAL_ROTATE_REQUIRED の既存字が安全なのは、
   それらの vert 字形が回転そのものだから。引用符には成り立たない）。
3. 実機の版面で破綻していない＝倒す動機は規範適合であって可読性ではない（実データ 7,319 件）。
∴ 規範から外れているのは**分類ではなくこの端末で出ている絵**。分類（PUNCT_REPOSITION＝vert を要求する側）は
Tr の主段の要求どおりで、変えても書体は応えない。見直す条件＝この 4 字の vert が効く書体で本文を組むようになったとき。

**②`￣` だけ移す理由**: UAX#50 が Tr・実測で主段が実在・実機で横棒が漢数字「一」と紛らわしい、の 3 点が揃う。
実データ 4 件と少数だが誤読を生む側なので直す。`ゝヽヾ` は **UAX#50 が U（正立）と宣言している**＝
そもそも規範から外れておらず、`changed=true` の中身も 1〜3px のヒンティング差で**捨てている縦字形は存在しない**
（棚卸しの「持っている縦字形を捨てている」という読みは、この 3 字については前提が誤りだった）。

**この裁定で分かった一般則**: `vert_probe_pgem10.jsonl` の `changed` は真偽だけでは判断材料にならない。
見るのは **字面ボックスの中心移動と縦横比の変化**（比較の目安＝`～`FF5E は (2,-33)-(62,-15) → (23,-54)-(41,6) で
縦横比が反転する＝本物の縦字形／`ゝ` serif は (22,-35)-(44,-9) → (23,-35)-(42,-10) ＝ヒンティング差）。

**実装**: 向きの分類（`CharClass`）と「書体の縦字形を使うか」は別の軸なので、`￣` を `PUNCT_REPOSITION` へ
移さず、`VertFeatureCoverage.VERT_FORM_REQUIRED_ON_UPRIGHT`（`MANUAL_ROTATE_REQUIRED` と対称の実測リスト）を
新設して `VertGlyphRenderer` の UPRIGHT 分岐が参照する形にした。advance は 64→64 で不変＝**版面は変わらない**。

## 付随: `－`FF0D と `“`201C の JLReq 収録を一次ソースで確定（2026-09-07）

`LineBreaker` の禁則表に類推で入れていた 2 字を、W3C JLReq 付録A（`https://www.w3.org/TR/jlreq/`。
**UCS 欄＝コードポイント宣言**で照合）と UCD で裏取りした。

- **`－`U+FF0D は付録A に不在**。cl-03（ハイフン類）の UCS 欄は `2010` / `301C` / `30A0` / `2013` の 4 字だけで、
  付録A 全体でも FF0D は 0 件（文書全体の文字列検索でも 0 件）。
  ⚠️ **罠**: A.18 演算記号の減算記号の行は**字形セルの実体が FF0D** だが UCS 欄の宣言は `2212`＝
  字形だけ見ると「cl-18 に居る」と誤読する。**コードポイント欄で見ること**。
  Unicode 側も行頭禁則を支持しない（`LineBreak.txt`: `FF0D ; ID`＝表意文字扱いで前後どちらでも分割可／
  `UnicodeData.txt`: 分解が `<wide> 002D`＝ASCII ハイフンの全角互換形）。
  → **温存**。根拠は規範ではなく、この表の運用規則「採否は JLReq 収録でなく実データ出現で決める」
  （2026-09-03 の人間裁定）＝1,874 件出る字を、原文の意図（ハイフン類）に沿って `～`FF5E と同じ扱いへ寄せる。
  ⚠️ 一方 UAX#50 は `FF0D ; R`（回転）＝**`MANUAL_ROTATE_REQUIRED` に入れているのは規範どおり**と確定した。
- **`“`U+201C は cl-01（始め括弧類）に収録あり**（備考「横組で使用」）。対の `”`U+201D も cl-02（終わり括弧類）に、
  `‘`2018 / `’`2019 も同じく収録。縦組用の `〝`301D / `〟`301F は同じ cl-01 / cl-02 の別行。
  → 「`”` と対で出る実測だから」という類推止まりだった根拠が**規範裏付きへ格上げ**。表は変更なし。
