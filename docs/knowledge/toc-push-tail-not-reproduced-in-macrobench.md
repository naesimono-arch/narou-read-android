# 本棚→目次 push の「138ms の尾」は macrobenchmark では再現しなかった（要因未確定）

## 何が食い違っているか

同じ遷移について、2つの計測が**尾の形だけ**大きく食い違う。頭（P50）はよく一致する。

| | 2026-08-19 gfxinfo（12窓） | 2026-08-21 macrobenchmark（5反復×6開閉＝30窓） |
|---|---|---|
| p50 | 11.0ms | 10.0ms |
| p90 | 19.4ms | 28.3ms |
| p95 | 61.6ms | 31.4ms |
| p99 | 90.6ms | 38.8ms |
| 最大 | 138.0ms | 56.1ms |
| 60ms 超 | **12窓中11窓で必ず1枚** | **全5反復で0枚**（1642フレーム中） |

再走行でも同じ（P50 10.3 / P90 28.7 / P99 42.9・60ms 超 0枚）＝**macrobenchmark 側は安定して尾が軽い**。
「アニメが走っていない状態を測った」線は否定できる（1反復あたり 326〜331 フレームが出ており、
開閉6回ぶんの窓が毎回描かれている）。

## 確定していること

- **P90 は macrobenchmark 側が明確に重い**（28.3 vs 19.4）。push 窓が他の面（本棚スクロール・章送りの P90 は
  11〜12ms）より構造的に重いこと自体は両者一致で、`TocPushBudget` の P90 35.0ms はこの実測に由来する。
- **極端な尾（90〜138ms）だけが再現しない。**

## 要因の候補（**未確定**・切り分け未了）

1. **メトリクスの定義差**が最有力。macrobenchmark で見ているのは `frameDurationCpuMs`＝**フレームの CPU 時間**で、
   GPU・キューイングを含まない。gfxinfo のフレーム時間は全パイプライン。CPU 40ms のフレームが
   総時間 138ms になることは原理的にありうる。→ `frameOverrunMs`（実測 P99 30.4ms）や
   Perfetto の実フレーム境界と突き合わせれば決まる。
2. **ビルド種別の差**。macrobenchmark の対象は benchmark ビルド＝**R8 で縮小済み**。08-19 の計測が
   debug ビルドだったなら、Compose の初回組み立てコストは桁で違う。→ 08-19 の計測対象 APK を特定すれば決まる。
3. **初回性の希釈**。macrobenchmark は1反復で同じ本を6回開くため、冷たい初回は 30窓中5窓しかない。
   ただし**その5窓の最大でも 46〜56ms** で 60ms を超えていないので、これ単独では説明できない
   （＝候補としては弱い）。

## 何を見れば決まるか

- 08-19 の計測に使った APK のビルド種別（debug か benchmark か）。
- 同一走行で `frameDurationCpuMs` と総フレーム時間（gfxinfo / Perfetto）を並べて取る。
  片方だけで比べているうちは、この不一致は永遠に解けない。

## 実務上の扱い（今どうしているか）

`TocPushBudget` の **P99 予算 60.0ms** は、この不一致を承知のうえで
「**08-19 の症状が再来したらちょうど落ちる高さ**」に置いてある——30窓で各1枚 60ms 超が出れば
60ms 超が約30枚＝全1642フレームの 1.8%＝P99 が必ず 60 を超える。
つまり**再現しなかったからといって症状を無かったことにはしていない**。ゲートは張ってある。

⚠️ **P90 35.0ms は現状追認であって是認ではない**。目次側の初回組み立てを軽くする改修が入ったら
予算も下げ直すこと（予算は退行検知の天井であって、目標値ではない）。

## 一般化

**率だけでなく尾も見る**（`ranking-pager-jank-slow-ui-thread.md` の「率と尾は別の指標」）に加えて、
**尾は計測系ごと（CPU時間か総時間か・どのビルドか）に別物になりうる**。
別系統の数字を並べるときは、まず**同じものを測っているのか**を確かめること。
