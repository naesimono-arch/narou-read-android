# コンテキスト費の内訳は「読み込み側」に偏る（実測 2026-08-10）

★★★ / 2026-08-10 実測（2026-08-13 に handover から移設）

**1行要約**: `cache_read` の実効寄与（トークン×残ターン＝居座り時間込み）で見ると、費用は **Read・tool_use 引数・Bash 出力**に集中し、
**assistant の応答本文はわずか 4.3%** しかない。応答を短くしても費用はほとんど動かない。

## 計測方法

`tools/` に収録済み（いずれも過去セッションの jsonl を走査する）:

- `measure_read_residency.py` — 実効寄与の全体像（トークン×残ターン）
- `measure_read_kind.py` — Read の委譲可否の二分（編集起点か・調査で読んだきりか）
- `measure_toolinput_and_ledger.py` — tool_use 引数の内訳と台帳ファイルの寄与
- ※ 素の量しか出さない旧 `measure_context_bloat.py` は上記と役目が重なる（統廃合は未判断）

## 実測値

main の `cache_read` 実効寄与 **899M** の内訳:

| 区分 | 割合 |
|---|---|
| Read | 36.3% |
| tool_use 引数 | 31.1% |
| Bash 出力 | 20.1% |
| assistant 出力 | 4.3% |

- **Read 326M の内訳** — 編集起点 58.7% ／ 調査（読んだきり）41.3%。全量読み 76.0%。
  **台帳が 34.1%（111M）**で、うち `handover.md` だけで 80M ＝**単独で全体の 8.9%**（平均 10,864 字・部分読みは 42% どまり）。
- **tool_use 引数 280M の内訳** — Bash command 27.2% ／ Agent prompt 19.8% ／ Write 本文 19.6% ／ Edit 本文 16.9%。
  ＝生成の外部委譲（agy）の射程である Write/Edit 本文は**最大 11.4%**、Edit は break-even 割れなので**実質 6.1%**。

⚠️ **2026-09-02 追記: 上の表の比率と「比率は安定」という記述は誤りだった**（下記「再検証」節）。
結論の向き（assistant 本文は小項目）は生き残るが、**数値と、その数値に与えられていた信用は取り下げる**。

## なぜ重要か（誤りだった旧説の訂正）

CLAUDE.md の応答様式ルールには「応答本文の `cache_read` 実効寄与は約69%」と書かれていたが、
**元計算が ADR 0031 にもコミットにも残っておらず再現不能**＝誤りと確定し **4.3%** へ訂正した（2026-08-10）。

この訂正の帰結:

- **「報告を短く書く」ことの理由はコスト規律ではない**（効かない）。理由は**監督の判断を速くするため**に限られる。
- 効くレバーは読み込み側＝①台帳のサイズ ②Bash 出力量 ③調査 Read のサブ委譲。
- **本知見は「何が費用を占めるか」の構成比だけを見ている**。もう一つの軸＝**セッション長**（累積 `cache_read` は
  ターン数の2乗で効く。同じ総ターン数でも 100 ターン刻みで切れば総量は 54%）は
  `context-cost-superlinear-in-session-length.md` が正本。
- 同じ理由で、**生成だけを外部モデルへ委譲してもコストは約3%しか動かない**（ADR 0031 判断材料6）＝
  委譲の動機はコストではなく〈監督のコンテキスト保護〉と〈独立した第二の目〉に置くべき。

打ち手の採否は `handover.md`「コンテキスト費」項が追跡する。

## 再検証で判明した2つの欠陥（2026-09-02）

同じ `measure_read_residency.py` を再実行したところ、**比率が大きく動いた**——
Read 36.3%→**20.4%**、assistant 4.3%→**7.4%**、tool_use 引数 31.1%→37.7%、Bash 20.1%→25.6%（総額 899M→311M）。
「比率は安定」は 933M→899M ＝**母数が 4% 動いただけの範囲でしか確かめていなかった**。
さらに、動いた理由を追うと集計自体に2つの欠陥があった。

1. **文字→トークン換算が約 4.8 倍ずれている**。`CH2TOK = 4.0` を**除数**に使う＝0.25 トークン/字。
   一方 `measure_turn_increment_breakdown.py` が実データから逆算した比は **1.201 トークン/字**
   （日本語主体なら 1 字 ≈ 1 トークン超が自然で、こちらが妥当）。
   ⚠️ 全区分に同じ係数が掛かるので**区分どうしの比は影響を受けない**。壊れるのは絶対値。

2. **分母が `cache_read` ではない**。集計対象は assistant 本文・thinking・tool_use 引数・tool_result だけで、
   **人間の入力と常設注入（システム＋CLAUDE.md＋memory）を一切数えていない**。
   同一セッション集合で実際の累積コンテキスト（input+cache_read+cache_creation）を測ると **1,988M** で、
   A の申告 311M は**その 15.6%** にすぎない。にもかかわらず出力見出しも本文も「main の cache_read 実効寄与」と書いていた。

⚠️ **当初ここに「合算 1,969M で残差 −0.9%」と書いたが、それは締めすぎだった**（2026-09-02 の独立実装突合で訂正）。
一律 4.8 倍で引き伸ばすと ASCII 主体の内容（シェル出力・ツール引数）を過大に膨らませ、
その過大分がたまたま穴を埋めていた。実測の2クラス係数（下記）で正しく換算し直すと、
内容 ≈56%・常設注入 ≈22%・**未説明 ≈22%** が残る。未説明分の候補はツール定義や system-reminder など
**jsonl の本文ブロックに現れない注入**で、特定は未了。**近似で埋めない**。

### 補正後の値（真の cache_read に対する占有）

| 区分 | 旧記載 | A の申告(部分集合内) | **補正後（真の占有）** |
|---|---|---|---|
| assistant 出力 | 4.3% | 7.4% | **約 5.6%** |
| Read | 36.3% | 20.4% | **約 15.3%** |
| 常設注入（A は未計上） | — | — | **約 24%** |

### 「相互検証」も成立していなかった

`context-cost-optimization-levers-measured.md` は「別方法でも 4.3% ＝完全に一致」と書いていたが、
両者は**分母が違う**（A＝実効寄与の全区分／C＝1ターン増分のみで固定費を含まない）ため、
一致は構造的性質ではない。実際、今日の再測は **7.4% vs 5.2%** で一致しない。

### 何が生き残るか

- **結論は無傷**: assistant 本文は補正後でも 5〜6% の小項目＝「報告を短く書く動機はコストでない」は成立。
- **取り下げるのは**「4.3%」という具体値と、「比率は安定」「二重に確定」という信用の部分。
- ⚠️ `CLAUDE.md` と `AGENTS.md` が「実測 4.3%」を引用している＝**要修正**（本 knowledge の所管外）。
- 打ち手の順位は入れ替わる。今日の実測では最大項が tool_use 引数（37.7%）で、Read は3位。
  加えて A が数えていなかった**常設注入が単独で約 24%**＝固定費の削減は無視できる項ではない。

## 第3の欠陥: 分割イベントが usage を複製する（2026-09-02・独立実装が発見）

1回の API 応答が text / tool_use ごとに**複数の assistant イベント行**へ分割して記録され、
**分割された各行が同じ usage を複製して持つ**。実測で確認: 分割された message.id 151 件すべてで
usage が完全に一致（`(input, cache_read, cache_creation)` が3行とも同値）。イベント/message.id 比は **約2.0〜2.5**。

帰結は広い。「1ターン = assistant イベント1件」で数えると——
- **B・C の総量が約1.95倍に膨らむ**（同じ usage を分割回数ぶん足すため）。実測: 同一スコープで
  event 単位 2,061M → message 単位 **1,036M**。
- **ターン数も約2倍に膨らむ**（10,351 → 5,086）。1ターン単価はほぼ不変（199.5k → 204.6k）＝比は保たれる。
- ⚠️ 本 knowledge の旧記述も、`context-cost-superlinear-in-session-length.md` の「44,280 ターン」も、
  **この膨らんだ単位のまま**である。傾き・単価・反実仮想の比は影響を受けないが、**絶対のターン数と総量は約半分に読む**こと。

⚠️ この定義は当方が仕様文に「1ターン = assistant イベント1件」と**書いて渡したもの**で、独立実装はそれに従いつつ
「その定義だと重複加算になる」と指摘して `--turn-unit message` を用意してきた＝**仕様の誤りを外から見つけた例**。

## 独立実装との突合結果（2026-09-02）

別セッションで仕様文だけから書かれた実装と、同一スコープ（linux 根・novel-reader）で突合した。

**構成比は一致した**（既存 A vs 独立 A・利用者入力を除いて分母を揃えた場合）:
Read 20.4% vs 22.5% ／ ツール引数 37.7% vs 38.3% ／ シェル出力 25.6% vs 23.4% ／
assistant 7.4% vs 9.8% ／ その他ツール結果 7.8% vs 6.0% ＝**全区分で 2.4pt 以内**。
B もほぼ一致（長さ帯別の1ターン単価 52.6/74.8/86.6/141.0/215.7/330.2k vs 既存 57.0/74.8/93.7/139.1/213.5/322.8k、
反実仮想 K=60 で 42.3% vs 44%）。C-3 の実測換算比も **1.2905 vs 1.201** で一致。

**構成比は3つの欠陥すべてに対して頑健**だった（実証）: 換算係数を実測値へ差し替えても総額は 2.11 倍になるが
各区分の比は **0.5pt 以内**しか動かず、message 単位へ替えても総額は 1.95 分の1になるが比はやはり動かない。
＝**壊れているのは一貫して絶対値だけで、「何が費用を占めるか」の順位は当初から正しかった**。

### 文字→トークン換算の正しい値（実測・2クラス最小二乗）

| | ASCII | 非ASCII |
|---|---|---|
| 実測 | **0.4735 tok/字** | **1.5487 tok/字** |
| 既存 A（`CH2TOK=4.0` 一律） | 0.25（1.9倍の過小） | 0.25（**6.2倍の過小**） |
| 独立 A（ASCII/4.0＋非ASCII/1.5） | 0.25（1.9倍の過小） | 0.667（2.3倍の過小） |

**「4文字=1トークン」は両実装が独立に踏んだ共通の罠**（ASCII 側は完全に同値）。
独立側は「日本語は別係数が要る」という構造には自力で到達したが、選んだ定数はなお 2.3 倍低い。
＝**この近似は誰が書いても外す性質**で、正解は定数を当てにいくことではなく、
**独立側が実際にそうしたように、換算比を実データから測る計測を別に持つこと**。
