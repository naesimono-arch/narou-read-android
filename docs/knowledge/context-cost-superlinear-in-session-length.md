# main のコンテキスト費はセッション長の2乗で効く（実測 2026-08-26）

★★★ / 2026-08-26 実測（同日、全ログ横断で母数を 3.7 倍にして再確認）

**1行要約**: 1ターンのコンテキスト長はターン位置に**線形**で伸びる（0.5〜1.5k/ターン）ため、
セッション全体の累積 `cache_read` は **O(n²)**。同じ総ターン数でも 100 ターンごとに切っていれば総量は **実測の 54%** だった。
これは**プロジェクトにも OS にも依存しない**（下記3）＝作法の産物ではなくハーネスの構造。
「委譲は監督のコンテキスト保護のため」（ADR 0031）と言うときの保護効果には、この2次項の回避という**定量的なコスト削減成分**が含まれる。

## 計測方法

- `tools/measure_session_length_cost.py` — **両OS・全プロジェクト横断**（本知見の主データ）
- `tools/measure_orchestration_leak.py` — novel-reader の特定 slug に固定（過去実測との比較可能性を守るため）
- 母数: main **282 本 / 44,280 ターン**（5ターン未満は除外）。初出時は novel-reader 単独 76 本 / 12,858 ターンで、
  下記1・2の数値は母数を 3.7 倍にしてもほぼ動かなかった。

⚠️ **母数を数えるときの罠**: `~/.claude/projects/-home-qingj-wt-*`（worktree 用 slug）は canonical への **symlink**、
Windows 側の `C:\Users\qingj` も `naesimono` への symlink（2026-08-23 のユーザー名移行）。
`realpath` で重複排除しないと同じログを何重にも数える——見かけ上4つの slug が揃って 396 件で並ぶ、という形で実際に踏んだ。

## 実測値

### 1. 長さ自体が線形に伸びる（＝累積は2乗）

| ターン位置 | 平均コンテキスト長 | 直前帯からの傾き |
|---|---|---|
| 1–25 | 64.0k | — |
| 51–100 | 145.3k | 1.17k/ターン |
| 101–200 | 218.6k | 0.98k/ターン |
| 201–400 | 324.5k | 0.71k/ターン |
| 401–800 | 485.1k | 0.54k/ターン |

傾きはほぼ一定（むしろ逓減）＝**長さは n に線形**。各ターンがその時点の全長を `cache_read` するので、
セッションの総額は Σ ≈ **O(n²)**。頭打ちは観測されない（1M コンテキストのため）。

### 2. 同じ1ターンの仕事が、長いセッションでは6倍高い

| セッション長 n | 本数 | 1ターン単価 |
|---|---|---|
| 5–25 | 51 | 53.0k |
| 51–100 | 52 | 99.2k |
| 201–400 | 75 | 213.2k |
| 401+ | 14 | 317.5k |

### 3. プロジェクトにも OS にも依存しない

| side | 本数 | ターン | 1ターン単価 | 中央セッション長 |
|---|---|---|---|---|
| WIN | 206 | 31,362 | 199.8k | 118 |
| LNX | 76 | 12,918 | 205.8k | 117 |

**作法が大きく違う（Windows は PowerShell 経由・Gradle ビルド不可）のに単価が 3% しか違わない**。
プロジェクト別に見ても単価は 110k〜254k の帯に収まり、n 別カーブの形は共通。
＝これは特定プロジェクトの運用の癖ではなく、会話が伸びれば毎ターン全長を読み直すという**ハーネスの構造**。

### 4. 自動圧縮はあてにならない

100k 超から 30% 以上縮んだ点は **76 本中 1 本・1 箇所**だけ（novel-reader 単独での観測）。
1M コンテキストでは自動 compact がほぼ発火しない＝**切るかどうかは全面的にこちら側の判断に依存**する。

### 5. 反実仮想（総ターン数を変えずに切っていたら）

実測の位置別カーブで積分し直すと、総量 8,925M に対し —
60 ターン刻み **43%** ／ 100 ターン刻み **54%** ／ 150 ターン刻み **64%** ／ 200 ターン刻み **73%**。

## 損益分岐（切る側の代償を差し引いても十分残る）

切れば引き継ぎ（台帳の再読み・所在の再探索）で**ターン数が増える**。増えた分も2次で効くが、序盤は安い（1–25 帯で 64.0k）。
100 ターン刻みの節約 4,136M に対し、追加ターンが **総ターン数の 30% 増**（＋13,284 ターン）でも増分は約 850M ＝**なお大幅に得**。

⚠️ **測れていない代償**: 文脈を失ったことによる**手戻り**（同じ判断のやり直し・見落とし）はこの計算に入っていない。
反実仮想も「切った後のセッションが実測の序盤カーブに従う」＝引き継ぎ Read で序盤が重くならない、と仮定している。

## なぜ重要か

- **「101 ターン目以降が総量の 76.4%」は超線形の証拠にならない**（ターン数の分布次第で、長さが一定でも同じ数字が出る）。
  証拠になるのは上記1の**傾きが正で一定**であること。この取り違えのまま結論だけを引用しないこと。
- **ADR 0031 判断材料6 はこの軸を測っていない**。あちらは side 別（main／sub＝**誰が払うか**）の内訳で、
  「生成だけ移しても約3%」はその軸の中での話。**セッションを切る／委譲で main のターン数を抑える**という軸は射程外。
- したがって「委譲はコスト削減にならない」と縮めて引用すると誤り。委譲が main の n を1回のターンに畳むこと自体が、
  2次項の分母を叩いている。ADR 0031 の結論（動機はコンテキスト保護に置く）は変わらないが、
  **その保護は同時にコスト削減でもある**。
- 既存規範との関係: `/orchestration` §0 の「~30 ターンの谷」は**子エージェント**の較正値で、**main 側の谷は未較正**。
  CLAUDE.md の「実行見込み ~10 ターン超は fresh セッションで」・同 §6「最大の節約レバーは親メインの担ぎ賃＝
  フェーズ境界 fresh」は方向として本実測と整合するが、数値の根拠は本知見が初出。

⚠️ **子の走行長と混ぜないこと**: `/orchestration` §0 の較正値の指標は **`tool_uses`**（集計＝`tools/measure_subagent_run_length.py`）。
本知見の「ターン」は assistant イベント数で、**別の指標**。混同すると子の走行長を過大評価する（2026-08-26 に実際に踏んだ）。
