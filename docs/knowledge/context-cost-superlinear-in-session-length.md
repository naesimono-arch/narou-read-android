# main のコンテキスト費はセッション長の2乗で効く（実測 2026-08-26）

★★★ / 2026-08-26 実測

**1行要約**: 1ターンのコンテキスト長はターン位置に**線形**で伸びる（0.6〜1.4k/ターン）ため、
セッション全体の累積 `cache_read` は **O(n²)**。同じ総ターン数でも 100 ターンごとに切っていれば総量は **実測の 52%** だった。
「委譲は監督のコンテキスト保護のため」（ADR 0031）と言うときの保護効果には、この2次項の回避という**定量的なコスト削減成分**が含まれる。

## 計測方法

- `tools/measure_orchestration_leak.py`（既存）— side 別 tool_result・ターン位置別コンテキスト長
- 追試（本知見のために書き捨て）— 位置別の**傾き**・セッション長 n 別の1ターン単価・途中リセットの有無・切った場合の反実仮想
- 母数: main セッション 76 本 / 12,858 ターン（サブは別置きのため除外）

※ 走査するたびに母数（＝過去セッションの jsonl）が増減するので絶対値は数 M 単位で揺れる。**比率は安定**している。

## 実測値

### 1. 長さ自体が線形に伸びる（＝累積は2乗）

| ターン位置 | 平均コンテキスト長 | 直前帯からの傾き |
|---|---|---|
| 1–25 | 67.7k | — |
| 51–75 | 128.3k | 1.0k/ターン |
| 101–150 | 186.0k | 0.85k/ターン |
| 201–300 | 291.6k | 0.83k/ターン |
| 401–600 | 461.2k | 0.63k/ターン |

傾きはほぼ一定（むしろ逓減）＝**長さは n に線形**。各ターンがその時点の全長を `cache_read` するので、
セッションの総額は Σ ≈ **O(n²)**。頭打ちは観測されない（1M コンテキストのため）。

### 2. 同じ1ターンの仕事が、長いセッションでは3倍高い

| セッション長 n | 本数 | 1ターン単価 |
|---|---|---|
| 51–100 | 17 | 97.8k |
| 201–400 | 18 | 211.9k |
| 401+ | 5 | 322.2k |

### 3. 自動圧縮はあてにならない

100k 超から 30% 以上縮んだ点は **76 本中 1 本・1 箇所**だけ。
1M コンテキストでは自動 compact がほぼ発火しない＝**切るかどうかは全面的にこちら側の判断に依存**する。

### 4. 反実仮想（総ターン数を変えずに切っていたら）

実測の位置別カーブで積分し直すと、総量 2,653M に対し —
60 ターン刻み **43%** ／ 100 ターン刻み **52%** ／ 150 ターン刻み **61%** ／ 200 ターン刻み **69%**。

## 損益分岐（切る側の代償を差し引いても十分残る）

切れば引き継ぎ（台帳の再読み・所在の再探索）で**ターン数が増える**。増えた分も2次で効くが、序盤は安い（1–25 帯で 67.7k）。
100 ターン刻みの節約 1,262M に対し、追加ターンが **総ターン数の 30% 増**（＋3,857 ターン）でも増分は約 261M ＝**なお大幅に得**。
1本あたりで見ても、100 ターンの仕事で浮く 11.4M（節約 114k/ターン × 100）は序盤ターン **168 回分**に相当する。

⚠️ **測れていない代償**: 文脈を失ったことによる**手戻り**（同じ判断のやり直し・見落とし）はこの計算に入っていない。
反実仮想も「切った後のセッションが実測の序盤カーブに従う」＝引き継ぎ Read で序盤が重くならない、と仮定している。

## なぜ重要か

- **「101 ターン目以降が総量の 76.4%」は超線形の証拠にならない**（ターン数の分布次第で、長さが一定でも同じ数字が出る）。
  証拠になるのは上記1の**傾きが正で一定**であること。この取り違えのまま結論だけを引用しないこと。
- **ADR 0031 判断材料6 はこの軸を測っていない**。あちらは side 別（main／sub＝**誰が払うか**）の内訳で、
  「生成だけ移しても約3%」はその軸の中での話。**セッションを切る／委譲で main のターン数を抑える**という軸は射程外。
- したがって「委譲はコスト削減にならない」と縮めて引用すると誤り。委譲が main の n を1回のターンに畳むこと自体が、
  2次項の分母を叩いている。ADR 0031 の結論（動機はコンテキスト保護に置く）は変わらないが、
  **その保護は同時にコスト削減でもある**。
- 既存規範との関係: `/orchestration` §0 の「~30 ターンの谷」は**子エージェント**の実測較正（2026-08-06・n=96）であり、
  **main 側の谷は未較正**。CLAUDE.md の「実行見込み ~10 ターン超は fresh セッションで」・
  同 §6「最大の節約レバーは親メインの担ぎ賃＝フェーズ境界 fresh」は方向として本実測と整合するが、
  数値の根拠は本知見が初出。
