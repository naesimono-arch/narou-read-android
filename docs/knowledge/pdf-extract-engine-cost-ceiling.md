# PDF 抽出の高速化には天井がある（engine の約 55% は PDFBox 内部）

★★ / 2026-08-17 / `Extract#engine` の 2/3 は `loadPages`、その 85〜91% は PDFBox 内部＝こちらから動かせない。**単一スレッドで攻める限り**可動域は engine の約 45% しかない（並列化だけが例外＝後述）。

## 症状（というより、着手前に知っておくこと）

「取込が遅い」を C++ 系の最適化論（ホット/コールド分離・アロケーション削減・データレイアウト）で
攻めようとすると、支配区間を外した箇所に労力を払うことになる。

## 実測（JVM プロファイラ `ExtractPhaseProfileTest`・N6169DZ 8.9MB/8,668ページ/338万グリフ）

engine の内訳（比率は中編 N2959KI 799ページでもほぼ同一＝**規模を9倍にしても動かない**）:

| フェーズ | engine 比 |
|---|---|
| `loadPages`（グリフ収集） | 66〜70% |
| `DetectedRules.detect` | 18〜22% |
| `TextProcessor.processPages` | 12〜13% |

`loadPages` をさらに分離すると、**PDFBox のパース+TextPosition 生成が 85〜91%**、
自前（`normalizeGlyphUnicode` + `CharBox` 生成）は 9〜15%。

`processPages` の中では `groupCharsByLine` が内部比 27〜30% あるが、**engine 全体では 3〜4%**。
`associateRuby` の二重ネストループは engine の 0.2% 未満。

## 対処（どこを触る価値があるか）

- **可動域は engine の約 45%**（detect 約20% + processPages 約13% + CharBox 生成約10%）。
  全部ゼロにしても engine は 2 倍未満。実機の取込 24 秒が理論下限で 13 秒。
- 費用対効果が最も良かったのは `detect` の**重複した仕事**の除去。`lineStepX` と `rubyOffsetX` が
  ページごとに同じ `filter`+`groupCharsByLine` を2周していたのを1周に畳んで、その列復元ブロックを
  42% 削減（＝detect 約27%減・engine 5〜6%減）。挙動は `body_sha256` で不変を確認済み。
- 次に効いたのも `detect` の、今度は**無駄な一時確保**の除去。bodySize のヒストグラム1本のために
  `flatten()` で全グリフのコピーリストを作り、さらに `map { it.size }` で boxed Double のリストを
  作っていた（338万グリフで概算100MB超・どちらもここでしか使われていなかった）。ページ配列を直接
  バケットカウンタへ積む形へ畳んで**同一走行比 −55.0%**＝detect −29%・engine −2.7%。
  detect の engine 比は上表の 18〜22% から **15.5%** へ下がった。挙動不変は `body_sha256`
  （`JvmGoldenRegressionTest`）と `DetectedRulesTest` で確認済み。
- `groupCharsByLine` の線形走査（許容誤差つき近傍一致）と `associateRuby` の二重ネストは、
  **形は悪いが量が無い**。厳密に同じ列を選ぶ索引を設計するコストに見合わない。

## 測って落としたもの（Why-not）

- **表紙メタの全ページ反復**: `loadFirstPage` は `endPage=1` を設定していても `getText(doc)` 経由で
  `processPage` が 8,668/8,668 回呼ばれる。⚠️ ページ範囲の判定は `processPages` ではなく
  **`processPage` の先頭**にある（`javap -c` で確認）ので、範囲外ページは入口で即 return する＝実費が小さい。
  範囲だけを回す形へ変えても N6169DZ で 10.8→7.9ms＝**2.9ms**しか縮まず、N2959KI では符号が反転して
  ノイズ以下だった。`loadPages` 5.4 秒に対し 0.05% ＝**本番は無変更のまま**にした。

## 並列化だけが天井の外側にある（2026-08-18 スパイク実測）

冒頭の「可動域 45%」は**単一スレッドでチューニングする限り**の話。支配区間が PDFBox 内部でも、
**ページ範囲で分割して複数スレッドへ載せる**ことはできる（スレッドごとに同一ファイルから `PDDocument` を開く）。
JVM プロファイラ `profileParallelLoadPages` の同一走行内実測（`availableProcessors=8`）:

| | 単一 | K=2 | K=3 | K=4 |
|---|---|---|---|---|
| N6169DZ 8,668ページ | 5,406ms | 4,032ms (1.3x) | 3,541ms (1.5x) | 3,539ms (1.5x) |
| N2959KI 799ページ | 632ms | 412ms (1.5x) | 293ms (2.2x) | 259ms (2.4x) |

- **等価性は全 K で完全一致**（中編＝全フィールド厳密比較・長編＝全フィールドを畳んだ 64bit
  フィンガープリント＋ページ別文字数）。ページ順に連結する限り結果は決定的＝`body_sha256` を動かさずに載る。
- スレッド安全性の異常（例外・値の化け）はゼロ。ただし条件が2つ＝**各スレッドが自前の `PDDocument` を開く**、
  **並列区間の前に単一スレッドで1ページ処理して静的キャッシュ（PDFBoxResourceLoader/CMap/glyphlist）を温める**。
- **長編は K=3 で 1.5x 頭打ち**（短編は K=4 で 2.4x まで伸びる）。残る律速はスレッド共通の
  アロケーション/GC と読み出しと見られる。`loadPages` は engine の 72.9% なので、採用時の engine 短縮は
  JVM 換算で約 25%。
- ⚠️ **実機で同じ比が出るかは未確認**。JVM 8スレッドと端末の big.LITTLE＋サーマルは別物で、
  絶対値の正本は実機 Macrobenchmark のまま。

## 実機ではヒープ天井が並列利得の上限を決める（2026-08-19 PGEM10 実測）

JVM の比は端末でも出る。**長編 N6169DZ 全8,668ページで K=3 は 2.1x**（単一 60,574.6ms → 29,018.4ms）、
4,000ページ切詰めで 2.3x、中編 N2959KI で 2.7x。等価性は全走行で一致（長編は全ページを64bit指紋へ畳んで照合）。
**長編ほど比が下がる＝ヒープ圧が並列利得を食う。**

⚠️ **採否を決めるのは速度比でなくヒープ**。同一文書・同一1セットでも、単一のピーク 276.1〜313.4MB に対し
**K=3 は 360.5MB**（+47〜84MB）。K 個の `PDDocument` が同時に開き、各スレッドのパース済み COS が重なるため。
この端末は `dalvik.vm.heapgrowthlimit=384m`（`largeHeap` 無しでこの値＝大きめ）なので**残余は 23.5MB しかない**。
**192〜256MB が上限の端末では単一ですら危うく、K=3 は確実に越える**。緩和するなら K を `maxMemory()` から動的に決める形。

### スパイクが2度 kill された機序（ハーネス固有・本番では起きない）

計測ループが `Timed`（CharBox 列そのもの）をループ局所変数へ受けており、**代入は呼び出しの戻り後**なので
走行 N の全結果が走行 N+1 の確保中ずっと到達可能だった＝**常に2セットが同時に生存**。1セットが 276.1MB なので
384MB には物理的に入らない。結果は GC スラッシュ（約26秒の窓のうち約24秒が GC）→ **前面のまま ColorOS が `o-kill(109)`**。
⚠️ `OutOfMemoryError` は 0件＝**ART は投げず OEM が先に殺す**ので、OOM を探しても真因に当たらない。
本番は1セットしか持たないのでこの形は起きない（**並列化自体のヒープ増は本番でも起きる**＝上の段が本題）。

### 実機で測るときの作法

- 走行結果は**計測停止後に指紋へ畳んでから返す**（畳んだ時点で CharBox 列が到達不能になる）。走行間に明示 `System.gc()`。
  効いていることは各走行の直前使用量が基底で平坦（25.3 / 19.4 / 19.5 / 19.5 MB）であることで確かめる。
- **`am instrument` は対象プロセスを再起動する**ので、先に打った `monkey` の前面化は無効化される
  （これで685秒フリーズした）。正しい順は `am instrument` をバックグラウンド起動 → その後 `monkey` で前面化。

## なぜそうなるか / 再計測の作法

支配区間がサードパーティのパーサなので、自前コードをいくら整えても天井が動かない。
元ネタの C++ 事例（88〜200倍）は対象が全部自前カーネル＝可動域 100% だった点が決定的に違う。

再計測するときは:

- **走行をまたいだ絶対値比較をしない**。同じコードのまま `loadPages` が 3.5s→5.8s、
  `processPages` が 0.7s→1.0s に振れた走行を実測している（機械側の負荷・drvfs・GC）。
  変更の効果は**同一走行内で旧形状と新形状を並べて比で読む**（`probeColsOldShape` /
  `probeColsMergedShape` がその対照群）。
- プローブは本体のコピーなので、本体を変えたら追従させる。被覆率が 100% に届かないのは正常
  （段落縫合を測っていない＋JIT 差）。**上回ったら**追従漏れか計測破損。
- 絶対値の正本は実機 Macrobenchmark（`PdfImportBenchmark` + `ImportBudget`）のまま。
  JVM の値は比率と相対比較にだけ使う。
