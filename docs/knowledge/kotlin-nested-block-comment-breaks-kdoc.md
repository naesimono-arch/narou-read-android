# KDoc にワイルドカードパスを書くとビルドが落ちる（Kotlin のブロックコメントはネストする）

**重要度**: ★★
**確定日**: 2026-07-30（Kotlin 1.9.22・kspDebugKotlin が実際に失敗）
**一行要約**: KDoc 内の `foo/*.json` の `/*` が内側コメントの開始として数えられ、閉じ `*/` が KDoc の終端を食う。エラーはファイル末尾を指すため原因から遠い。

**Kotlin のブロックコメントは Java と違ってネストできる。** つまり `/*` はコメントの中でも
「内側コメントの開始」として数えられ、対応する `*/` はその内側を閉じるのに使われる。

その結果、KDoc の中に **`foo/*.json` のようなワイルドカード付きパス**を書くと壊れる:

```kotlin
/**
 * - 本文抽出の結果 … `ab-review/golden_regression/*.pdf.json` ＋ JvmGoldenRegressionTest
 */                                              // ← この */ は上の /* を閉じてしまう
object PdfBookExtractor {                        // ← KDoc が閉じないまま以降を飲み込む
```

## 何が厄介か

エラーが**原因から遠い**。コンパイラは

```
e: .../PdfBookExtractor.kt:169:1 Unclosed comment
```

と **ファイル末尾の行**を指す（そこまで飲み込んで初めて終端が無いと分かるため）。実際の犯人は
100行以上前の1文字で、しかも「コメントを書き足しただけ」なのでビルドが落ちる心当たりが持ちにくい。

## 実際に踏んだ経緯（2026-07-30）

撤去済み Python 経路への参照コメントを整理する作業で、受入条件の正本を指すために
`ab-review/golden_regression/*.pdf.json` と書いた。ドキュメント整備の副作用としてビルドが落ちる
典型で、**同じ作業は今後も繰り返す**（正本のパスを KDoc に書くのは正しい習慣）ため知見化する。

## 回避

ワイルドカードを書かない。ディレクトリと拡張子を分けて述べれば意味は通る:

```kotlin
 * - 本文抽出の結果 … `ab-review/golden_regression/` 配下の `.pdf.json`
```

バッククォートで囲んでも**無効**（Kotlin のレキサはコメント内の Markdown を解釈しない）。

## 検出

```bash
# KDoc の継続行（* で始まる）に /* があり、同じ行で閉じていないもの
grep -rnE '^\s*\*.*/\*' --include=*.kt android/app/src | grep -v '\*/'
```

なお「ファイル全体で `/*` と `*/` の数を数える」方式は使えない——`//` 行コメントの中や文字列
リテラルの中の `/*` を拾って誤検出する（実際に誤検出した）。**判定できるのはコンパイラだけ**なので、
コメントを大量に編集したら素直にビルドを通すのが早い。
