# pdfminer↔PDFBox はグリフ CID→Unicode の割り当てが食い違う——ゴールデン照合前に正規化が要る

★★ Important（2026-06-20 実測・Chaquopy→Kotlin(PDFBox) 移植プロト A/B 評価時）

**症状**: 同一 PDF を抽出しても、一部の字が pdfminer（現行 Python 抽出）と PDFBox（Kotlin 移植）で**別のコードポイントに割れる**。代表的な対:
- 波ダッシュ: `〜`(U+301C) ↔ `～`(U+FF5E)
- 罫線／EM ダッシュ: `―`(U+2015) ↔ `—`(U+2014)
- ハイフン系: `－`(U+FF0D) ↔ `−`(U+2212)

その結果、長編での対 pdfminer 一致は**行 92.95%・ルビ P/R ≈ 81% が上限**になり、これ以上は詰められない。素朴にゴールデン（Python 基準値）と生バイト比較すると、この差分がすべて「不一致」として検出され、移植ロジックのバグに見えてしまう。

**真因**: 両エンジンはフォントの CID（グリフ ID）を Unicode に解決する経路が異なる。CMap／ToUnicode の解釈や、同一字形に複数のコードポイントが存在する記号（全角/半角・互換文字）でどちらを選ぶかが実装依存で、**どちらも「正しい」抽出**でありながら出力コードポイントが割れる。移植ロジックの誤りではなく**エンジン差**。

**対処**: ゴールデン比較時は、上記の割れる字を**正規化してから突合する**（例: 波ダッシュ・ダッシュ・ハイフンの各対を片側へ寄せる）。生のコードポイント一致を追わない。92.95%／81% という上限はエンジン差由来（ロジック誤りではない）——これを大きく下回るとき初めて移植ロジックを疑う。

**なぜそうなるか**: なろう系 PDF が使うフォントには、視覚的に同一の記号に対して複数の Unicode コードポイント（正規形と互換形、全角と半角）が対応づく。CID→Unicode 解決の分岐点で pdfminer と PDFBox が別々の妥当な選択をするため、意味は等価でもバイト列が一致しない。文字の等価性は「正規化後の一致」で判定するのが正しく、生一致は過剰に厳しい基準になる。
