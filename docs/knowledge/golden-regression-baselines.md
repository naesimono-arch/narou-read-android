# 旧 Python 抽出エンジンのゴールデン回帰基準値と N2959KI ルビ0 確定

★★ Important（基準値確立 2026-06-20／N2959KI ルビ0 切り分け 2026-06-21）

**症状／目的**: Kotlin+PDFBox 移植の「正解」を固定する必要がある。現行 Python エンジン（pdf_extractor + chapter_processor）の実 PDF 抽出結果をスナップショット化し、移植版が同じ段落数・章数・ルビ数を再現するか回帰チェックしたい。

**確立した基準値（2026-06-20、sample_pdfs 3 本）**:

| 作品 | 段落数 | 章数 | ルビ数 | 所要時間 |
|---|---|---|---|---|
| N1453LW | 75 | 3 | 0 | 0.3s |
| N2959KI | 9,786 | 131 | **0** | 約 15〜22s |
| N6169DZ（8.9MB） | 116,645 | 951 | 11,308 | 約 165〜200s（移植のベンチ目標） |

**2 回 run で段落／章／ルビ／本文 SHA256 が完全一致＝決定論性を実証済み**（elapsed_sec のみ比較除外）。

**N2959KI ルビ0 は「真にルビ無し」で確定（取りこぼしバグではない）**: submission-B（PDFBox/Kotlin）の `--dump`（フォントサイズヒストグラム）で切り分けた。N2959KI.pdf に存在するフォントサイズは **4 種のみ**——14.0pt（本文/題名, 377,837 字）・12.0pt（ページ番号, 2,398 字）・20.0pt（49 字）・11.0pt（34 字）。**7.0pt 付近の小フォントは皆無**（最小でも 11.0pt）。したがって「ルビフォントが 7.0pt でマッチせず取りこぼした」説は否定され、このPDFは真にルビ無し。現行 Python エンジンと PDFBox 移植がともに ルビ0 で一致＝両エンジンとも正しい。

**再検証コマンド**:
```
cd ab-review/submission-B && ./gradlew run --args="../sample_pdfs/N2959KI.pdf --dump" -q
```

**対処／運用**: 回帰チェックは `cd ab-review && python golden_regression.py`（差分時 exit 1）、基準更新は `UPDATE_GOLDEN=1 python golden_regression.py`。ハーネス本体（`ab-review/golden_regression.py`）と基準 JSON（`ab-review/golden_regression/*.json`）は**git 未追跡のローカルスクラッチ領域 `ab-review/` にある**——このファイルは値と確定事実の記録が主目的で、コマンドはスクラッチ側が正本。

**なぜそうなるか**: 抽出は決定論的（同一入力→同一出力）なので、段落/章/ルビ数と本文 SHA256 をスナップショットとして固定でき、移植版の一致で「挙動を保存した」と機械判定できる。N2959KI のルビ0 はフォントサイズの物理的分布（小フォント不在）から導かれる不変の事実であり、抽出パラメータに依存しない。

**注意**: 単話作品（N2959KI）の章分割挙動には未確定の疑義があり（handover.md 参照）、基準自体がその挙動を「正」として固定している可能性がある。基準更新はその調査とセットで判断すること。
