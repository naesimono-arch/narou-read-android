# 0043. 取込元PDF の永続 URI 権限は**本の生存中は保持する**（即時解放をやめる）

- 状態: 採用（2026-09-03 ユーザー裁定）。**実装済み（2026-09-03・下「実装の着地」節）**。
- 関連: 実証の証跡＝`docs/verification-shots/source-pdf-delete-2026-09-02/`（エミュ実測）／
  真因のコード＝`PendingJobStore.settlePendingJob` の `releasePersistableUriPermission`・`releaseOrphanedPermissions` の keepUris ②

## 背景 — 「取込元PDFを削除」がアプリを閉じた後は必ず失敗する

取込元PDF の削除は「取り込んだアクティビティが生きている間だけ」効き、アプリを閉じると以後**必ず失敗する**。
しかも失敗の見え方が悪く、**DB の行だけ消えて `/sdcard/Download` の実体が残る**。
真因は `settlePendingJob` が取り込み完了時点で永続 URI 権限を即座に解放していること。

## 決定

**解放を遅らせ、本が生存している間は権限を保持する。**
`releaseOrphanedPermissions` の keepUris ② が既に「本が持っている URI は残す」前提で書かれているので、**実装をその前提へ合わせる**。

**併せて失敗文言を直す**（どちらへ倒しても必要だった項目）＝現在の「移動/削除済みか、削除に対応しない保存先の可能性」は
真因と違うことを言っている。

⚠️ **代償＝端末の永続 URI 権限枠を長く占有する**。上限に当たる兆候が出たら「古い本から解放する」等の追い出し規則を別途要する。

## 実装の着地（2026-09-03 追記・決定そのものは上のまま）

**解放点を2つに集約した。** 取込の確定経路（成功／重複／失敗）は永続 URI 権限を一切解放せず、解放するのは
①**本の死**＝`LibraryDeleter.deleteBook`（取込元削除の要否に関わらず必ず返す）②**起動時の孤児回収**＝
`PendingJobStore.releaseOrphanedPermissions`（keepUris＝現在の pending_jobs ∪ books.sourceUri）だけ。

なぜ確定経路で判定しないか: `PendingJobStore` は books を見ないため、確定した URI が「生きている本の取込元」か
どうかを**原理的に判定できない**。判定材料（keepUris）を持てるのは起動時掃除だけなので、そこへ寄せた。
`remove`（再開不能ジョブ）・`clearAll`（明示停止）も同じ理由で解放をやめた——特に `clearAll` は、欠落本の
一括再取込が `books.sourceUri` をそのまま再投入する経路があるため、停止操作が無関係な蔵書の取込元権限を
巻き添えで壊していた。代償は「解放が次回起動まで遅れる」ことで、これは上の⚠️で受け入れた代償の範囲。

**`deleteRowKeepingPermission` は `settleJob` へ統合した。** 旧実装ではこの2つが「権限を返すか否か」で
分かれており、失敗経路だけが権限を残す例外だった。本決定で「返さない」が全経路の既定になった結果、
2つは完全に同義になったため、同義のメソッドを2本残さず1本にした（M7 再試行の成立という当初の狙いは
既定側へ吸収された＝失敗経路のコメントに機序を残してある）。

**失敗文言（`BookshelfViewModel.deleteBooks` の Snackbar）は表現の是正に留めた。** 旧文が挙げていた要因は
推測形で、当時の支配的な真因（＝取込時の即時解放による権限失効）はそこに挙がっていなかった。本実装で
その真因自体が消えたため、残る要因は〈実体が既に移動/削除された〉〈削除に対応しないプロバイダ〉の2つに
絞られる。よって要因の書き換えではなく、推測形をやめて残った2要因を断定形で言う形へ直した
（「取込元PDFを削除できませんでした（N件・ファイルが移動/削除済みか、この保存先が削除に対応していません）」）。
⚠️ 版面が変わるため golden `ShelfSnackbarK` の deleteFail 系は撮り直しが要る。

**派生して直した別バグ（同便）**: 復元後の なろう縦書きPDF取込本が③`PickPdfNoRecord` へ落ち、
「PDFのある場所から探す／自分で選ぶ」という**実行不能な提案**を受け取っていた（その PDF はアプリ cache に
しか存在せず、cache は Auto Backup 対象外＝復元後はユーザーの手元に無い）。`ReimportPlan.PickPdfNoRecord` に
`narouNcode` を持たせ、棚の再取込ダイアログに分岐③'「なろうで作り直す」を新設して既存ルート
`discovery/detail/{ncode}/import` へ送る。自動復旧の群には入れない（なろうの生成フローは CSRF＋ワンタイム
トークン制で直 URL の機械 DL が不可・規約でも不可＝ADR 0011）。併せてこの群はフォルダ走査の対象から外した
（指紋は持つが探す先が無く、走査群に数えると一括復旧の CTA が守れない冊数を約束するため）。
正本モックの逆同期＝`docs/design-candidates/bookshelf-reimport-badge-D.html` の分岐③'。

## Why-not

- **② 即時解放を仕様と認め、UI の選択肢そのものを消す（＝閉じた後は選ばせない）**: 実装は軽いが、
  「容量を空けたい」という需要は取り込み直後より**後から**来る。その時に手段が無くなる方を損と見た。
