# 0040. 本文の遷移骨＝横は「段落の呼吸まで」・縦は専用骨を新設（2026-07-29「縦書き専用骨は作らない」の覆し）／骨の濃さは保留

- 状態: 採用（2026-08-26 ユーザー裁定）。実装＝`ui/TransitionSkeletons.kt`・`ui/NativeReadingScreen.kt`、
  正本モック＝`docs/design-candidates/transition-skeleton-D.html`（同日更新）。
- 関連: ADR 0019（遷移 slide push 250ms）／ADR 0014（デザイン原則・§C 禁止則「静謐」）／
  ADR 0020（縦書き＝右→左 連続横スクロール）／ADR 0005（HTMLモックが正本）
- 一次情報: `.claude/plans/skeleton-norms-from-teardown-2026-08-26.md`（他社13本の逆解析から抜いた規範）／
  裁定用ドラフト `docs/design-candidates/candidates/transition-skeleton-body-{horizontal,vertical}-candidates.html`

## 背景 — 骨の「型」は決まっていたが「粒度」と「版面」が詰まっていなかった

2026-07-29 に骨の**型**（案A 構造プレースホルダ）を裁定して実装したが、同じ日に
「**縦書き専用骨は作らない＝骨は横書き汎形1種**」も裁定していた。その後の点検で3つの穴が出た。

1. **縦書きで紙面が90度変わる**。縦書き設定で読んでいても横棒の骨が出て、着地の瞬間に右→左の列組へ変わる。
2. **骨が実本文のクリアランスを持っていなかった**。上下バーはオーバーレイ描画（Scaffold の
   `contentWindowInsets=0`）で版面を1dpも削らないため、実本文は `contentPadding` で自分でバーを避けている。
   骨は `fillMaxSize()`＋左右 padding だけで、**章見出しの骨がステータスバー／トップバーの裏に隠れ**、
   着地で実見出しが約2行ぶん下から現れて跳ねていた。
   ⚠️ **正本モックがこのズレを描いていなかった**（上下バーを「レイアウトを食う flex の兄弟」として描いていたので、
   骨がクリアランスを持たなくても揃って見えた）＝**モック検分でも素通りする形の欠落**だった。
3. **骨の粒度が「面の上 2/3 で尽きる棒列」のまま**で、実本文の文章らしさ（段落の長短・章題の折り返し）を予告できていない。

## 決定

| 軸 | 決定 |
|---|---|
| 横書きの粒度 | **案3「段落の呼吸まで」**＝①章題は2行折り返し前提で骨も2本 ②段落の行数を1〜4行でばらす ③段落末の余りを毎回ちがう長さに ④短い会話行を混ぜる ⑤面の下端まで埋める |
| 縦書きの粒度 | **案V2「段落の切れ目まで」**＝**縦書き専用骨を新設**（2026-07-29 の裁定を覆す）。列送り・列高・左右余白・見出しの積み方を実本文と揃えたうえで、字下げ・列末の余り・短い会話列を骨でも見せる |
| クリアランス | **横書きは骨が自分で持つ**（上＝statusBars inset＋`Insets.ReadingBodyTopExtra` 64dp／下＝navigationBars inset＋`ReadingBodyBottomExtra` 80dp＝実本文 `ChapterContent` の `contentPadding` と同値）。**縦書きは足さない**（後述） |
| 骨の濃さ（コントラスト） | **保留＝現行値のまま。色は1ビットも触らない**（後述の撤回） |
| shimmer / パルス | **入れない**（ADR 0014 §C 禁止則「静謐」＝装飾アニメ・自動ループの禁止と衝突。骨は窓 0〜250ms のあいだ1ピクセルも動かない） |
| 骨の型・語彙・差し替え点 | **据え置き**（案A／棒11dp・角丸2dp・2値塗り／settle+0ms） |

## なぜ 2026-07-29「縦書き専用骨は作らない」を覆したか

当時の理屈は「250ms の場所取りに組方向の忠実さより〈1種で全設定に成立する汎形〉を優先」だった。
覆した理由は2つ。

1. **取引の対価が骨の目的と正面から反する**。骨の目的は着地先の予告＝跳ねを消すことなのに、
   縦書き利用者にだけ「着地の瞬間に紙面が90度回る」という**骨がないより大きい段差**を見せていた。
2. **分岐の実装コストが小さい**。骨の分岐（`NativeReadingScreen.kt`）と `verticalMode` は同じ composable の
   スコープ内で、`if (verticalMode)` を1つ足すだけ。**差し替え点は縦横分岐の上流のまま動かさない**＝
   変わるのは「窓の中に何を描くか」だけで、遷移の骨格には触れない。

## 縦書きだけクリアランスを足さない理由（横書きと非対称にする根拠）

縦組みでは上下が**交差軸**になる。横書きの 64/80dp をそのまま持ち込むと、
`contentPadding` の top/bottom が**全列の列高から恒久的に差し引かれ**、横画面（視野高 360dp）では
**列高が約4割まで潰れる**（2026-07-17 実機実測）。実本文 `VerticalChapterContent` が同じ理由で足していないので、
骨だけ足すと差し替えで列の上端・下端が動く。**列はバーの下を素通りする**＝横書きが本文行のバー下通過を
許容しているのと同じ取引を、縦書きは全列に対して結んでいる。

## 骨の濃さ（コントラスト）を保留にした経緯 ＝ 一度出した裁定の撤回

他社13本（競合5＋模範8）の逆解析から「骨↔地色の**収束帯**はライト CR 1.27〜1.44 / ダーク 1.59〜2.09 で、
我々の現在値はその**下**＝薄すぎる」と読み、**一度は「帯へ寄せる」と裁定した**。
精査でこれを取り下げた。理由は**帯が比較不能な値の混成**だったこと:

| 出所 | 実際に測っていたもの |
|---|---|
| X の 1.435 / 2.088 / 1.618 | **骨↔背景** |
| Photos の 1.290 / 1.977 | **base↔highlight**（shimmer の振れ幅の両端） |
| カクヨムの 1.274 / 1.585 | **lerp の両端**（単色矩形の2色フェード） |

**統一した測り方**（骨↔地色）に揃えると X は **1.116 / 1.275 / 1.210** で、
現行 SkinD（LIGHT 1.093・1.243／DARK 1.087・1.336）と**大差ない**。
よって「帯の下＝薄すぎる」という結論は根拠を失い、**色は触らない**。
濃さを動かすなら**同じ定義で測り直してから**改めて裁定する。

⚠️ **逆解析の成果物を単独で信じない**という一般則も、この件から確定した。
元資料 `08-startup-profile-and-ui-constants.md` は精査で **CONTRADICTED 10件・UNSUPPORTED 5件**
（`book-api-analysis/_work/review/08-audit-2026-08-26.md` が正本＝08 を引くなら必ず併読）。
とくに `dexfp.py` 由来の「無い」は**「マーカーが当たらなかった」と読む**（`androidx.paging`・Glide が
偽陰性で全称否定に化けていた）。

## 先例ゼロで決めた記録（縦書きの骨は借りる先が存在しない）

13本のうち**1本も縦書き本文の骨を持たない**。否定の根拠は2段:

1. 縦書き本文を実装している3本（tscsoft・sampleb3・なろう公式）は**そもそも骨を持たない**
   （不定 ProgressBar／全画面スクリム＋ProgressBar／Flutter スピナー）。
2. 骨を持つ8本（カクヨム・X・Google 製6）の骨は**すべて横組み**。

したがって案V1〜V3 の判断材料は他社から一切供給されない。**この形は借りずに決めた**。
横書きの骨から移せたのは**組方向に依存しない原理**だけで、それも読み替えの妥当性自体は先例で裏付けられない:

- 「幅を全部変える」（Gmail＝8本が 121/313/210/237/179/210/146/263dp と全部違う）→ 列末の余りへ
- 「最終行だけ 0.55〜0.7 に短く」（X）→ 段落末の列が下端で余る、へ
- 「行高＝置換するテキストの `lineHeight`」（カクヨム）→ 列送り＝実本文の columnAdvance、へ

## Why-not

**横書き**

- **案1「位置だけ直す」**＝クリアランスだけ直して骨の形は現状のまま。他社にも同粒度の実在例はある
  （Maps＝バー2本／カクヨム＝1アイテムぶん）が、**面の下 1/3 が地色のまま**で「文章が来る」予告にならない。
  ※案1が直すクリアランスは**案3 に含まれている**＝落としたのは粒度だけ。
- **案2「面を埋める」**＝行数だけ版面いっぱいに伸ばす。最多数派の粒度（YouTube・YT Music の同一カード反復）だが、
  **行送りが一様で機械的に見える**。案3 との差は4操作ぶんで、実装コストはほぼ同じ。
- **案4「紙面まるごと」**＝前書きブロックの板・ルビの粒・シーン区切りまで写す。Photos に先例はある
  （実ウィジェットを tint して骨にする）が、**Photos の手口は実データが既にあることが前提**で、
  遷移窓 250ms の骨は本文未取得の時点で描くため**構造的に適用できない**。
  加えて前書き・ルビ・区切りの有無は**章ごとに変わる**＝無い章では着地の瞬間に板や粒が消える＝**骨が嘘をつく**
  （現行裁定「内容非依存の汎形」との衝突）。描画要素も3〜4倍に増え、骨を軽くするという元の目的と逆を向く。

**縦書き**

- **案V1「列に立てる」**＝90度立てるだけ。組方向の一致は取れるが**全列が同じ長さ＝定規を並べたように見える**。
- **案V3「紙面まるごと」**＝横の案4 と同じ内部衝突（内容依存・描画量）。

**他社から借りなかったもの（規範との衝突が確定しているもの）**

- **shimmer / pulse の一切**（X 800+1500=2300ms・カクヨム 800ms 往復・Photos 3500ms・Maps 1000ms・
  zyunto Lottie 708ms）＝すべて `infiniteRepeatable` / `lottie_loop=true` の**自動ループ**で、
  ADR 0014 §C「motion はフィードバックのみ・装飾アニメと自動ループは無し」と衝突。
  Photos の 3500ms は禁止則①（duration ≤350ms）の10倍でもある。
- **Gmail の遅延閾値 750ms / 最低表示 500ms**＝原則との衝突ではなく**前提の不一致**。
  我々の骨は不定長のロード待ちではなく**尺の決まった遷移窓 250ms**に出るので、750ms 遅延では骨が一度も出ず、
  最低表示 500ms では骨が窓を超えて残る（差し替え点が動く）。
- **YouTube 現行の角丸 6〜8dp / Photos のカード 24dp**＝実 `.block` の角丸は 2px なので、
  骨だけ 6〜8dp にすると**差し替えの瞬間に角丸が変わる**。借りられるのはカクヨム／YT Music の 2dp 側だけで、
  これは偶然こちらの実装値と一致している。

## 検証と注意

- **golden は増えない**。遷移骨を撮る Roborazzi テストは存在せず（`ReadingBodySkeleton` を描く
  screenshot テストは0件）、既存 golden にも骨は写り込まない。回帰は `TransitionSkeletonTest`（差し替え契約）が担う。
- **モックと実装の模型を揃えた**。正本モックの採用紙面は上下バーを**オーバーレイ**として描き、
  クリアランスは版面（`.clr`）が自分で持つ形に改めた。旧模型のままだと同じ欠落がまた素通りする。
- 実機での確認軸は〈①横書きで章見出しの骨がバーに隠れないか ②縦書きで着地の瞬間に紙面が回らないか
  ③縦書きで列高が潰れていないか（とくに横画面）〉の3点。
