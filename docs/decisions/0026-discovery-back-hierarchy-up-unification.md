# 0026. 発見サブツリーの戻り規則＝階層 up 一本化（「D 統一 2026-07-12」二本立ての改訂）

- 状態: 採用（2026-07-29 ユーザー裁定「わかりやすく」＝読書側と同じ規則へ）
- 関連: ADR 0022 追記 2026-07-24（タブ層 Back 契約）・追記 2026-07-27（popToTab 一般化＝ルート名リテラル封鎖）／
  読書側の階層 up 統一＝`.claude/plans/back-unification-design-2026-07-23.md`（2026-07-19 裁定・07-23 実装）／
  実装 `MainActivity.kt`（BackHandler 配線・`upFromDiscoveryDetail`）・契約テスト `DiscoveryUpNavigationTest`

## 背景 — 改訂前の決定「D 統一（2026-07-12）」の記録（過去の決定は消さず、ここに正式記録する）

発見サブツリー（結果一覧・作品詳細）の戻り操作は 2026-07-12 の裁定（通称「D 統一」）以来、二本立てだった:

- **左上 ←＝経路に依らず発見ホームへの固定 Up**（検索/ジャンル/結果一覧経由のどこから来ても一発でホーム）
- **システム Back＝履歴 pop**（実経路の逆再生。結果一覧の Back は検索/ジャンル画面へ落ちる）

意図は「← は予測可能な脱出口・履歴逆走は端末 Back に委ねる」という Android 従来の Up/Back 区別。
ただし当時 ADR は未起票で、一次記録はコード内コメント（`MainActivity.kt`・`NovelDetailScreen.kt` の
「D 統一（2026-07-12）」）と UX 監査 F-D（公理1）のみだった。本 ADR が初の正式記録を兼ねる。

一方、読書側は 2026-07-19 裁定→07-23 実装で「← も Back も階層を1段上がる」（章→目次→本棚）へ統一済み。
07-23 設計書 §③ は「発見への拡張は D 統一の撤回を要する別件」として保留し、アプリ内に2つの戻り規則が併存していた。

## 決定（2026-07-29 ユーザー裁定「わかりやすく」）

**アプリ全体で「← もシステム Back も階層を1段上がる」の一規則に統一する。発見の Back＝履歴 pop を廃止。**

発見の階層と遷移表（←・Back 同一）:

| 画面 | ←・システム Back の着地 | 実装 |
|---|---|---|
| 作品詳細 | **直近の結果一覧**（結果一覧経由）／発見ホーム（ホーム直行入場＝直下がタブ層） | `upFromDiscoveryDetail`（1 pop or `popToTab`） |
| 結果一覧 | **発見ホーム**（検索/ジャンル経由でも飛ばして畳む） | `popToTab(DISCOVER)` |
| 発見ホーム（さがすタブ） | タブの既定挙動（→本棚ページ→アプリ退出＝ADR 0022 追記 2026-07-24） | TabPagerHost の BackHandler |

- **検索/ジャンル画面は結果一覧の「親」ではなく「条件編集の横道」**（条件フォーム＝場所でなく操作）。
  up はそれらを飛ばす。検索画面へ戻る導線は「条件を変更/調整」（`onEditConditions`・SEARCH 発のみ表示）が明示的に担う。
  ＝コールバックも旧名 `onBack` から用途名 `onEditConditions` へ改名（「Back の受け口」との誤読・再配線を封じる）。
- **再検索の重なりは同じ「結果一覧」段**（up は履歴を全部は遡らない）: 詳細のキーワードタップは
  `popUpTo(TAB_HOST_ROUTE)` で [tabs, result] へ畳んでから積む（2026-07-27 確立の契約④）ため、
  結果一覧・詳細は多段に重ならず「詳細の直下は必ず〈結果一覧 or タブ層〉」が機構的に保たれる。
  この不変条件が `upFromDiscoveryDetail` の「1 pop＝常に一段上」を保証する。
- **BackHandler は MainActivity のルート配線に置く**（画面側でなく nav 配線と同居・← と同じ up 関数を叩く
  単一点＝全スキン（D/C/M/P/J）を一括被覆）。popToTab 一般化（ADR 0022 追記 2026-07-27・リテラル封鎖）は
  そのまま土台として維持し、「タブ層直上か」の判定も `TAB_HOST_ROUTE` 定数比較で行う。
- **対象外**: PDF 取込・web-reader（WebView 面）は従来どおり（Back は WebView ページ内履歴を先に戻す）。
  ページ内履歴は画面階層でなく画面内状態であり、本規則（画面階層の up）と衝突しない。

可視変化（意図された変更）: 結果一覧で Back →（旧）検索画面 →（新）発見ホーム／作品詳細で ← →
（旧）発見ホーム直行 →（新）結果一覧経由の2段。

## 却下した代替案

- **二本立て維持（Android 従来の Up/Back 区別）**: 規則が2つあること自体が学習コスト。実測（07-23 設計書 §①B）でも
  結果一覧・詳細で ←/Back の着地が割れ「どちらを押すと何が起きるか」が予測不能だった。ユーザー裁定「わかりやすく」に反する。
- **← を Back（既定 pop）へ寄せる一本化**（07-23 設計書 §③ の当初示唆）: 既定 pop だと結果一覧の戻り先が
  検索/ジャンル/ホームと経路で割れ、ホームまでの段数も経路依存＝予測可能性が回復しない。
  「上がったつもりが条件フォームに出る」のは階層感覚とも合わない（検索画面は親でなく横道）。
- **履歴全遡り（再検索の重なりを Back で全部遡る）**: 同一段（結果一覧）内の往復に Back 連打を要求し
  「1段=1操作」の期待を裏切る。そもそも [tabs, result] へ畳む契約（2026-07-27）が多段化を既に禁じており、
  全遡りを選ぶにはその契約の撤回まで必要＝コスト超過。

## 検証

- JVM 契約テスト `DiscoveryUpNavigationTest`（全面改訂）: 契約①〜⑤（up の着地・Back ディスパッチ＝← 同一・
  リテラル pop 黙殺の機序・[tabs, result] 畳み）。
- 実機目視: 検索→結果一覧→詳細で〈←・横スワイプ Back〉とも 詳細→結果一覧→ホーム→（タブ既定）の順に上がること／
  ホーム直行の詳細から一発でホームへ戻ること／「条件を変更」だけが検索画面へ戻ること。
