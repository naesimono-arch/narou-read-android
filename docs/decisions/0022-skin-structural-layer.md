# 0022. スキン第二層＝画面構造の切替（M星図・Pカートリッジ・Jポータル実装の前提裁定）

- 状態: 採用（2026-07-17・`ui/skin-framework`。ADR 0021 追記2「二層拡張が必要」の設計裁定）
- 関連: ADR 0021（トークン束スキン＝第一層）・ADR 0014（原則5箇条・静謐則・ヘアライン家系裁定）・
  プラン `.claude/plans/skin-compose-implementation-2026-07-17.md`／モック正本 `docs/design-candidates/skins/{bookshelf,reading,toc,settings,discovery}-{M,P,J}.html`

## 背景

M/P/J は本棚〜各画面の構造ごと別物の**構造スキン**であり、SkinTokens（トークン束）だけでは表現できない
（ADR 0021 追記2 で「二層化が必要」とだけ裁定し、設計は本 ADR へ送られた）。
モック全数読解（2026-07-17・5画面×3スキン）で判明した、プラン前提と食い違う事実2点も本 ADR で裁定する:
①P モックにテーマ変種の実体が無い（settings-P の3択はスウォッチ見本のみ・モック自身が「変種数は裁定事項」と明記）
②J の3テーマは読書画面のみ（本棚/目次/発見/設定は固定ダーク森面）。

## 決定

### 1. 二層化＝「画面入口の薄いルーター」で分岐（早すぎる抽象化の禁止）

- **画面丸ごと分岐**（`when(skin)` で SkinX 専用 Composable へ委譲・分岐先は `com.novelreader.ui.skins.m/.p/.j` に1画面=1ファイル）:
  **本棚・目次・発見ホーム・発見結果一覧**。既存 D/C 実装は default 分岐として無改変温存。
- **共通骨格＋スキン別部品**（画面を複製しない）:
  - **読書**: 本文エンジン（組版・ページング・章送り・キャッシュ・タップトグル・状態機械）は単一のまま。
    スキンで替わるのはクローム部品のみ（進捗表示・章扉・上下バー・没入ヒント）＝部品単位の when(skin)。
    **本文組版の規格層（明朝・行間・ルビ 1/2・和文 letterSpacing 0）は全スキン不可侵**（モック3種とも明記済み）。
  - **設定シート**: ロジック（テーマ択・スライダー・永続化）は共有、シート意匠（面・つまみ・値表示）のみスキン分岐。
- **モックの無い画面は構造を発明しない**: 発見の検索/ジャンル/詳細等は Material トークン追従のみ
  （ADR 0021「D 構造へトークン写像」の原則は未モック画面に対して存続）。
- **共通化の抽出は3スキン実装後**（分岐先が2つ以下の抽象を先に作らない＝ADR 0021 却下案の原則踏襲）。

### 2. supportedThemes（変種軸の裁定・モック実態準拠）

| スキン | supportedThemes | 根拠 |
|---|---|---|
| M 星図 | `[DARK]`（夜の相・固定1変種） | settings-M がテーマ固定表示（C と同型）を明示 |
| J ポータル | `[DARK, LIGHT, SEPIA]`（既定=DARK） | reading-J に `.t-dark/.t-light/.t-sepia` の13変数一式。**変種が作用するのは読書系トークンのみ**＝material/shelf は theme 非依存の固定ダーク森面（モック実態。設定チップの扉プレビューは reading 値と連動） |
| P カートリッジ | **`[LIGHT]` で開始**→追補モック承認後に3テーマ化 | モックに変種の実体なし。プラン前提「P=3面」は事実誤認と確定。無根拠のセピア/ダーク値をコードへ発明せず、reading-P へテーマ変種を**追補モック**として起こし人間承認を経てから追加（ユーザーは追加モック作成を許可済み・2026-07-17） |

**追記 2026-07-17**: 上表 P 行の予告どおり、ユーザーがテーマ3変種の追補ドラフトを承認したため
**P = `[LIGHT, SEPIA, DARK]`（既定=LIGHT）へ拡張**した。値の出自＝`docs/design-candidates/skins/candidates/reading-P-themes-draft.html`
（承認後に正本 `reading-P.html` の `.t-light/.t-sepia/.t-dark` へ統合・ドラフトは candidates/ に一次情報として残置）。
SEPIA/DARK の地色は settings-P スウォッチ実値（#e4d2a4／#2a2d24）の正本値昇格で、無根拠の発明ではない（§2 の要件を充足）。
**J と同型で変種が作用するのは読書系トークンのみ**＝material/shelf/shiori は theme 非依存の固定筐体面（プラ筐体・緑LCD・
HUD/コンソールは P の署名＝テーマ不変）。派生値（placeholder/hr/blockBg＝rgba 焼き込み）は SkinP.reading にインライン集約・
骨格色は Color.kt Cartridge 節に3テーマ分登録。checker（check_design_tokens.py）の READING_ORDER_P も3テーマへ更新済み。

### 3. モーション裁定（ADR 0014 原則5・静謐則との突合）

- **「現在地の脈動」類型を承認**: M 本棚の hero 結線先端星（sin 周期・reduce で固定輝度静止）・M 目次の現在章ドット
  （CSS pulse 2.8s・reduce で animation なし）・M 目次 canvas 先端星。これらは装飾ループではなく
  **「ここから続く」という現在地のフィードバック**＝原則5の許容目的（読了印・進行類型に続く第3の正当化例外）。
  制約: ①脈動は正本モックにある箇所のみ・新設禁止 ②**reduce-motion で完全静止（モック規定の固定値）を必須**
  ③振幅・周期はモック値を正とする。**読書画面 M はモーションゼロ**（モックの意図＝読書の静けさ）を守る。
- **P/J はモックにモーションが存在しない**（keyframes/transition/JS ゼロ）＝**静止で実装開始**。
  スワイプ・遷移・シート等の機能モーションは既存 `Motion.kt` スロットを流用し、スキン固有の演出新設は
  実機後詰め層（ADR 0005 §B）へ送る。ProcessingBanner 等の既存フィードバックは共通機構のまま。

### 4. トークン正規化（モック間の同名変数食い違いの扱い）

- **画面家系で値が分かれるものは家系トークンへ分離**（ADR 0014 ヘアライン裁定と同型）:
  例 J `--page` #0C0E0B（本棚/発見）と #0F1712（読書/目次/設定）は「回廊の外殻」と「森の内側」の2トークン。
  P `--line` 3値は shelf/reading 系・シート・発見系のスロットへ各々振る。
- **同一役割の知覚下微差は多数値へ正規化**し、正規化の事実を Color.kt の該当 val コメントに記録
  （例 M `--line` α .20/.22 → .20 へ、J `--soft` α .62/.60 → 家系ごとに1値）。個別の採否は C1 の1:1対応表が正本。

### 5. 識別色・ambient パレットは SkinTokens にスロットを切らない

M の学名ドット `--id` 4色・P のラベル/ジャンル色 w1-w4/g1-g6・J の ambient グラデ群は、
**スキン専用の構造画面だけが使うデータ駆動パレット**＝トークン束（全画面共有の窓口）に載せず、
当該スキンの構造画面が `Color.kt` の系統別 val を直接参照する（ADR 0021「栞型軸はスロットを切らず必要時に足す」と同じ倹約則。
直書き禁止は Color.kt 命名 val 経由で担保）。

### 6. enum 値名

`SEIZU_M`（星図）・`CARTRIDGE_P`（カートリッジ）・`PORTAL_J`（ポータル）。追加は SkinX.kt 実装と同一コミット
（ADR 0021 規約）。displayName/tagline は装いの間カードの表示文言＝コミット時に人間検収。

## 却下した代替案

- **SkinTokens へ画面ファクトリ（Composable スロット）を足す**: 束 interface が画面実装へ肥大し、
  トークン層（値）と構造層（描画）の役割分離が崩れる。ルーターの when は画面側に置く方が薄い。
- **読書画面の丸ごと複製（ReadingScreenM 等)**: 本文エンジン（ページング・章キャッシュ・位置永続化）の
  三重複製＝回帰の温床。クロームだけがスキンの署名でありエンジンは共有できる。
- **P を最初から3テーマで実装**: モックに変種値が存在せず「翻訳」でなく「発明」になる（/visual-language
  の自己判断禁止に抵触）。追補モック→人間承認→実装の順を守る。
- **食い違い値の機械的な単一値統一**: ADR 0014 ヘアライン裁定が示した通り、画面家系での値分岐は意図的な
  較正であり得る。家系トークン分離で顕在化させ、真の微差のみ正規化する。

## 追記（2026-07-17・その2）: 「一覧=D構造フォールバック」の格下げ

ユーザー原則「栞（D標準）もUIの一つ・**各UIは装いの間でのみ接続する**」（memory `feedback-ui-connect-only-via-wardrobe`）により、
§1 の倹約策〔スキン内の一覧トグル先を D構造フォールバックで担保〕は**恒久解から過渡措置へ格下げ**。
スキン内トグルで D構造（栞書影）が現れるのは、装いの間を経ない別UIへの接続＝世界観の同一性を壊すため是正対象。

- 是正の形: 一覧ビューは**各スキン自身の意匠**で実装（P=bookshelf-P の `.li` 面・J=bookshelf-J のグリッド面＝モック既存。
  M=モックに一覧意匠が無いため**モック追補が先**）。D構造が担っていた機能（選択削除・Webカード操作・取込確認等）は各スキン一覧が引き継ぐ。
- 新スキン実装時も「Dフォールバックで済ます」を恒久解にしない（初期実装の足場としては可・是正まで台帳に残す）。

## 追記（2026-07-19）: 画面ルーターの網羅性は exhaustive when で機械化する

スキンは今後も追加する方針（ユーザー宣言）に対し、没入型スキンの画面ルーターが `if (skin == X) { …; return }`
連鎖（7ファイル約30分岐・すべて無音Dフォールバック）だったため、**新スキン追加時に1箇所書き忘れると
「新スキンの色×Dの構造」が compile もテストも通ったまま無音表示される**構造穴があった（2026-07-18 構造レビューで特定）。

- **採用**: ルーター分岐を `else` 無しの exhaustive `when` へ（skin 軸を when・表示モード等の他条件は分岐内 if）。
  enum 追加で全ルーターが compile error になり「自スキン画面を出すか D 既定へ落とすか」を接点ごとに明示判断させる。
  composable 本体は一切共通化しない＝「各スキン=別世界」の意匠独立性を温存し、**接続の網羅性だけ**を機械化する。
- **却下: 画面×スキンのレジストリ化**（`Map<Screen, Map<Skin, @Composable>>` に1箇所登録）: 編集集約の利点はあるが
  indirection と型付けの初期コストがあり、スキン数5では費用対効果が薄い。**増設が2桁に向かったら再検討**。
- **却下: 画面スロットの sealed interface 化**: 型安全最大だが現状の薄いルーターより重い。同上の理由で非採用。
- **残存リスク（対象外と裁定）**: `NativeReadingScreen`・`ReadingSettingsSheet` のスキン差分は多分岐ルーターでなく
  「加算的クローム/値選択」（bool フラグで単一スキンの装飾を足す形）＝when 化の対象外。新スキンが読書クローム無し・
  Dシート色を無音取得する穴は残る。是正するなら SkinTokens 化（シート色等を束へ昇格）など別機構＝将来課題として台帳へ。
- なお色のみ型スキン（C 夜行が実証）は enum＋トークン束＋検査期待表の3接点で完結し、`Skin.tokens` の when が
  従前から exhaustive＝既に定型。本追記は没入型（画面丸ごと差し替え）の接続だけを対象とする。

## 追記（2026-07-24）: タブ層の恒常枠を「スロット契約」として固定（Pager 化）

ユーザー要望「確定している形を固定化し、その枠の上で中身だけ入れ替え可能に」＋「タブを横スワイプで
シームレスに移動」への構造回答。タブ3面（本棚/さがす/設定）を NavHost の3ルートから **単一ルート
`"tabs"` ＋ `TabPagerHost`（HorizontalPager）** へ移行し、恒常枠を次の契約で固定する（`ui/tabs/TabPagerHost.kt`）:

- **枠（固定 API）** ＝〈恒常ボトムナビ（KBottomNav・NavHost 外静止）＋ TabPagerHost〉。**枠にはスキン分岐を
  持ち込まない**——スキン意匠は各スロット（BookshelfScreen 等の exhaustive when＝追記 2026-07-19）だけが担う。
  今後モック・デザインを増やすときは、この枠の上でスロットの中身だけを滑らせる。
- **スロット** ＝ `pages: List<@Composable () -> Unit>`（index = KTab.ordinal）。深い画面（読書・目次・発見詳細等）は
  従来どおり NavHost ルートとしてタブ層の上へ push される（Pager はタブ層のみ）。
- **ジェスチャー裁定**: タブ横スワイプは UX18-C3 の4問審査を全問通過（毎セッション級頻度／ボトムナビの空間配列
  からの導出／可視代替＝ナビ自体／Pager は端の戻るジェスチャと共存する標準挙動）。
- **旧 crossfade（MotionDurationKTabSwitch）は廃止**: スワイプ追従（指と同期して滑る）とタップ切替の運動言語を
  一致させるため、タップも同トークン長のページスライドへ。**M星図の「タブ間 crossfade」例外も同時に消滅**——
  固定天球 backdrop は NavHost 外に常駐しページだけが滑るため「空ごと動く」問題（ADR 0019 追記の懸念）は起きない。
- **navigateKTab 退役**: タブがナビゲーションでなくなり、currentBackStackEntryAsState の DROP_OLDEST レース
  （2026-07-23 防御的是正の対象）は土壌ごと消滅。同一タブ再タップの no-op は animateScrollToPage の標準挙動で成立。
- **Back 契約**: タブ層の Back＝階層 up＝本棚（page 0）へ。page 0 では消費せずアプリ退出へ委ねる
  （旧 `popUpTo("bookshelf")` 流儀の継承。契約テスト＝KTabNavigationTest）。
- **却下: タブごとの独立バックスタック温存（rememberSaveable 付き NavHost 多重化）**: Pager と saveState/restoreState の
  二重状態管理になり、枠の単純さ（スロット契約）を壊す。タブ状態は Pager のページ保持（rememberPagerState 内蔵 Saver）で足りる。
- **深い画面 → タブへの Up は `popToTab(nav, pager, KTab)` 一択**（`MainActivity.kt`・追記 2026-07-27）:
  この Pager 化で消えた旧ルート名 `"bookshelf"`/`"discovery"` への `popBackStack(route, …)` は**例外を投げず
  false を返して黙殺される**ため、押しても何も起きない ← ボタンがコンパイルもテストも通ってしまう
  （07-25「目次に幽閉」・07-27「検索→作品詳細の ← 無反応」は同一機序の連続発生）。タブ層への pop 先は
  ルート名リテラルで書けない形（`KTab` enum ＋ `TAB_HOST_ROUTE` 定数）へ閉じる。契約テスト＝
  `ReadingEscapeNavigationTest`（読書側）／`DiscoveryUpNavigationTest`（発見側）。
  **改訂の注記（2026-07-29・ADR 0026）**: 上記のうち発見側の Up 先の意味論（「経路非依存で発見ホームへ固定 Up」）は
  階層 up 一本化で改訂＝作品詳細の一段上は「直近の結果一覧」になり、← とシステム Back は同一の up 関数を通る。
  ただし**本追記の機構規律は不変**——タブ層へ pop する経路はすべて `popToTab` を通し、ルート名リテラル封鎖・
  「タブ層直上か」の判定も `TAB_HOST_ROUTE` 定数で行う（`upFromDiscoveryDetail` 参照）。
