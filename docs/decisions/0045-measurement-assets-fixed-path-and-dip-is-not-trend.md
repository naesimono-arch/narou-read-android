# 0045. 計測資産は slug でなく固定パスへ置き、一過性のくぼみを趨勢と読まない

- 状態: 採用（2026-09-07・`/stale-check` の裁定待ち項目①の決着）
- 関連: `docs/knowledge/windows-username-change-splits-project-slug.md`（旧対処に取消線＋理由を追記済み）／
  `/orchestration` §0（谷 ~30 の規範＝結論の正本）／`.claude/hooks/count_delegation_turns.py`（`base_dir`）／
  `tools/measure_subagent_run_length.py`（測るだけ・規範を持たない）

## 背景: 較正データが3日間、無症状で2つに割れていた

委譲ターン計測フックは、子の完走ごとに `delegation-stats.jsonl` へ1行追記する。
置き場は `~/.claude/projects/<slug>/` 配下に**直書き**されていた。

2026-09-04 のプロジェクト再編でリポジトリが
`project/novel-reader_andloid` → `project/android-make/novel-reader` へ動いた。
slug は **cwd のパス文字列**から作られるので、これは別 slug になる。
再編スクリプトは `~/.claude/projects/<旧slug>` を新 slug へリネームし、memory も履歴も引き継いだ。
**フックだけが旧 slug 文字列を直書きしたまま**だった。

結果、フックは消えたはずの旧 slug ディレクトリを**作り直して**そこへ書き続け、
較正データは 3,642 行（新 slug 側・07-25〜09-03）と 1,067 行（旧 slug 側・09-04〜09-07）に割れた。
フックは fail-open 設計なので**エラーは一切出ない**。集計ツールも同じ旧 slug を直書きしていたため、
この間の測定は**新しい少数サンプルだけ**を見ており、`/orchestration` の較正値と食い違う数字を返していた。

## 決定1: 書き手が1つしかない計測資産は、slug でなく固定パスへ置く

置き場を `~/.claude/delegation-meter/` へ移した。cwd が何であれ動かない。
分裂していた 4,709 行は `agent_id` の重複ゼロを確認したうえで ts 順に1本へ統合し、
原本は `.migrated-20260907` へ改名した（読み手が `delegation-stats.jsonl` として拾わないようにする）。

### 捨てた案: 「実 slug へ追従させる」

これは旧知見が示していた対処であり、2026-08-23 の Windows ユーザー名移行（qingj→naesimono）では
実際にそう直した。**同じ事故が 09-04 に再発した**のが、この案を捨てる理由である。

追従は「移動のたびに人が気づいて直す」ことを前提にする。しかし
**気づけないこと自体が本知見の主題**（fail-open ＝ 無症状 ＝ 誰も報告しない）なので、
前提が知見自身に否定されている。1回目の再発までは偶然と読めたが、2回目は構造である。

### 一般化: 同じ罠を踏む資産の見分け方

次の3条件が揃った資産は、置き場を cwd 由来の識別子に紐づけてはいけない。

1. **書き手が1つ**（フック・デーモンなど、置き場を自分で決める単一の書き手）
2. **読み手が後から集計する**（書いた直後に読まないので、書き先の誤りが即座に現れない）
3. **fail-open**（失敗しても本務を止めない＝異常が症状として出ない）

3条件が揃うと、書き先が変わっても**誰も気づかないまま記録だけが分岐する**。
逆に、書き手が複数いる／過去値が複数の場所に散っている資産は事情が違う——
`tools/measure_*.py` が新旧 slug を両走査して realpath で畳んでいるのは正しく、
そちらは要件が違うので固定パス化しない。

## 決定2: 一過性のくぼみを趨勢と読まない

`/orchestration` §0 が持っていた「**中央値34へ縮んだ＝『30 で再考』の運用が効いている証拠**」という
主張を取り下げた。

統合後のデータ（指標＝`tool_uses`・`agent_id` 重複除去後）で見ると:

| 窓 | n | 中央値 | p90 | max |
|---|---|---|---|---|
| 〜08-06 | 169 | 47 | 97 | 199 |
| 08-07〜08-25（旧記載が見ていた窓） | 103 | **34** | 75 | 146 |
| 08-26〜 | 83 | **44** | 121 | 259 |
| 全期間 | 355 | 43 | 94 | 259 |

旧記載の 34/75/146 は**同じ窓・同じ方法で正確に再現する**。誤りは数字ではなく読み方だった。
08-26 以降は 44/121/259 へ戻り、週別でも 51→49→30→32.5→58→42→54 と方向を持たない。
`30超` は全窓で 60〜78%（全期間 70.1%）＝**30 を超えるのが常態**である。
∴ 30 は「守られている閾値」ではなく再考の合図であり、**超過それ自体を逸脱と読んではいけない**。

### 谷 ~30 を維持した理由（ここが混同されやすい）

谷の根拠は **EOQ 型の費用構造**（起動固定費と長走行の超線形コストが釣り合う点）であって、
実測分布ではない。**分布は「実際どう走ったか」の行動の記録**で、費用最適点の測定ではない。
両者を同一視すると、実測が動くたびに規範が揺れる——今回まさに、
くぼみを「効いている証拠」と読んだ結果、次の窓で戻ったときに規範の足場が崩れかけた。
実測分布は谷を否定も肯定もしないので、**谷を動かす根拠は依然として無い**。

### 谷を一律に当てはめない

08-26 以降を agent_type 別に見ると桁が違う: `device-verify` 中央値83（max 259）／
`general-purpose` 中央値46／`Explore` 中央値31。
「必読が重いタスクは大きい側へ」は実測で裏づいた＝**実機系に 30 を当てるのは誤用**である。

### 結論の正本は skill 側だけに置く

同じ数を2箇所に書いた結果、再較正の閾値が skill「~550」対ツール「~200」で食い違ったまま残っていた。
`tools/measure_subagent_run_length.py` から較正値の要約文を削り、**測るだけ**にした。
規範（谷の値・再較正の要否）は `/orchestration` §0 が持つ。

## 再検討する条件

- **決定1**: 上記3条件を満たさない資産へ固定パス化を広げたくなったとき（要件が違うので個別に判断する）。
- **決定2**: 累計 n が倍増（~550件）したとき＝現在 355 なので未達。
  そのとき見るのは「くぼみが出たか」ではなく**複数窓にまたがって方向が持続したか**であり、
  谷を動かすなら根拠は分布ではなく費用構造の側（固定費・可変費の実測）から出す。
