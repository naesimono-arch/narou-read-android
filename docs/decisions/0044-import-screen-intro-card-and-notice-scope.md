# 0044. PDF取り込み画面の操作説明＝**層① 教示カード1枚（組D）**／ADR 0042 の告知は**そちらへ置かない**（境界の告知は一方に寄せる）

- 状態: 採用（2026-09-04 ユーザー裁定）。**実装済み**。
- 関連: 意匠の正本＝`docs/design-candidates/tutorial-onboarding-K.html`（§2 判定・§3 入口表と組D の絵・§4 の7枚目・§8 のフラグ表）／
  覆す対象＝同ファイル §2・§8 の旧判定「PDF取り込みへの層① 教示は**置かない**」／
  範囲を狭める対象＝**ADR 0042**（なろうの面の一度きりダイアログ）／規約線＝ADR 0010・0011（注入 JS はビューポート移動のみ）

> **この ADR は意匠を持たない。** カードの文言・図版・寸法は上記モックが正本で、ここには写さない
> （写すと2箇所になり、片方を直したときにもう片方が黙って腐る）。ここが持つのは
> **モックに書けない2つの境界判断**——〈ADR 0042 との重複をどちらに寄せたか〉と〈出す契機がどこまでを担保するか〉。

## 背景 — 「置かない」と決めていた面が、実機で反証された

取り込み画面のアプリ側の文言は題「縦書きPDFを取り込む」**だけ**で、あとはなろうの目次ページが全面
（`PdfImportScreen.kt`）。2026-09-04 の実機所感＝「取り込む際の…操作の仕方の説明がありません。
ページ遷移した後に、何をどうすればいいのかという説明が欲しい」。

旧判定は「PDF取り込み＝**目的を持って押して来る画面**」＝押した動機が説明の代わりになる、と見ていた。
反証は**動機は「取り込みたい」までしか運ばず、〈この面で自分が何を押すのか〉は運ばない**こと——
旧判定はこの2つを同一視していた。

**旧判定にはもう1つ穴があった**（2026-09-04 に発見）。旧行は「PDF取り込み」の1語で
〈なろうの取り込み画面〉と〈手元のPDFファイルを足す操作〉を**束ねて**いた。層③ で受けたと書いた
「組C の1行」は **「PDF は本棚の ［PDFを追加］」＝後者だけ**。
**前者はどの層にも受け皿が無いまま「規則3 で送った」ことになっていた**＝落としたつもりの項目が、
実は落としてすらいなかった。

## 決定

### 1. 器＝**層① 教示カード1枚（組D）**。既存の列に1枚足すだけで、新しい仕組みは作らない

覆した梃子は正本の中に既にあった規則1b〈**見えていても、それが何を決めているか推測できるか**〉。
自動スクロールで ［縦書きPDF］ の枠は**見えて**いるが、それが**アプリの続きではなく、なろう側の
生成フォームだ**とは読めない。**この画面のボタンはすべてなろうのもので、アプリのものは題と戻るだけ**。

▶ **組C（検索範囲チップ）を「置かない→置く」に反転させたのと、規則も取りこぼしの型も同じ**。
規則1（壊れて見えるか）では両方とも「いいえ」で落ち、拾えるのは規則1b だけ——
**組C だけ拾って取り込みを落とすと、同じ規則が画面ごとに違う答えを出す**ことになる。

代償は隠さない: 自動で出る割り込みが通算 **3回・6枚 → 4回・7枚**に増える。
ただし取り込み画面は「取り込む」を押した**直後**＝割り込みの原価が最も安い面で、
正本が「割り込みのコストが最も高い」と書いた読書中とは事情が違う。しかも**初回だけ**（2冊目以降は0画素）。

### 2. **ADR 0042 の告知は取り込みルートに置かない**——境界を名乗るのは組D の1項目目1つだけ

ADR 0042 のダイアログ（`NarouExternalPageNoticeHost`）の呼び手は `WebReaderScreen` の1箇所＝
**web-reader ルート専用**。取り込み画面も等しくなろうの面なのに、境界を名乗るものが無かった。

**選択肢は2つあり、どちらか一方にしか倒せない**——両方入れると初回だけダイアログとカードが連続する。
採ったのは **①組D の1項目目で受ける**（1枚で2つの穴を塞ぐ）。
②取り込み画面にも Host を置く、は**採らない**（採るなら組D の1項目目は重複するので落とす＝同じことを2回言わない）。

- **①を採った理由**: カードは元より出す面・出す条件・再訪導線を持っており、**追加の仕掛けがゼロ**。
  ②は器が1つ増えるうえ、初回に「ダイアログを閉じる→カードを閉じる」の2手を強いる。
- **腐らせない縛り**: 組D の1項目目は `NarouExternalPageNotice.BODY` の**第1文と1字同一**。
  `IntroOverlayContentTest` が定数から導いた文字列で照合するので、**どちらを直しても落ちる**。

⚠️ **ADR 0042 の「全数確認」の範囲を狭める記録**（この ADR の最重要点）。
`NarouExternalPageNoticeHost` の KDoc は「**アプリ内 WebView へはただ1つのルートを通ってしか入れない**
（`MainActivity` の grep で全数確認）」と書いていたが、これは**主語が広すぎた**——
数えた対象は〈**なろうで読む**〉の入口であって、〈アプリ内 WebView で開くなろうの面〉ではない。
当時の確認が誤りだったのではなく、**数えた対象が違う**（取り込み画面は勘定に入っていなかった）。
▶ **3つ目のなろう面を足すときは、上の2択をその場で決めること**——既定では覆われていない。

### 3. 出す契機＝`onPageCommitVisible` かつ目次 URL 一致。**担保できないことを明記して、それ以上は踏み込まない**

正本 §8 の「置きかた」は**背景が描き切ってから出す**を要件にしているが、**この画面には対応する信号が無い**。
WebView の自動送り（`scrollIntoView`）が終わったことを Kotlin 側は知らない
（`evaluateJavascript` の結果を受けていない）。

- **担保できる**: ①なろうの目次に着いた後にしか出ない ②白紙の上には載らない（初描画の後）。
- **担保できない**: **カードが載る瞬間、背後がまだ目次の上の方でありうる**。
  カードの文言「開いた位置にある ［縦書きPDF］ の枠から」は**閉じた後の状態**を指しており、
  スクロールはカードの下で進むので実害は出ない**想定**。⚠️ **モックでは確かめられない**＝実機の二段検分で見る。
- **それ以上は踏み込まない**: JS からコールバックを返せば「寄せ終わった」を取れるが、それは
  **注入 JS の役割を〈ビューポート移動のみ〉から広げる**話＝**ADR 0010/0011 の線に触れる**。踏み込むなら別 ADR。

### 4. 通しで「点の無い回」が2つ続くのは**受け入れる**（組C と組D は統合しない）

設定＞操作の説明の通しは 組A 3枚 → 組B 2枚 → 組C 1枚 → 組D 1枚 となり、点は ●○○ → ●○ → なし → なし。
正本 §3 の「**点の不在がそのまま『これで終わり』の合図**」が終盤で**1回鈍る**。
▶ **何もしない**＝終端ボタンが ［とじる］ に変わるので押す直前には分かる。
組C と組D を1組にまとめる案は、**出す条件が別画面**（検索画面／取り込み画面）で
「組＝出す単位」という §3 の定義に反するため採らない。

## Why-not

- **B 常設バナー1行（TopAppBar 直下）** — 層① の定義（割り込んでその場で言う・**恒常表示しない**）にも、
  層②（**文言を持たない**）にも入らない＝**3層のどこにも席が無い**。さらにこの画面は
  **作品ごとに毎回通る**ので、却下 C-3「恒常的に見え続けるものは、理解した後にコストへ変わる」が
  最も多く起きる面。字数も足りず、1行25字に収めると〈ここはなろうのページ〉と〈アプリが引き取る〉の
  2つが落ちる（＝決定2 の穴が塞がらない）。
- **C 初回だけの帯（操作で消える）** — 恒常でないので層① には入るが、弱点が2つ。
  ①**再訪の受け皿が無い**（帯に `.later` 相当を置く余白が無く、消えた後どこにも読み返せない＝規則3・4 が立たない）。
  ②**消す契機に新しい規則を1本増やす**——時間で消すと T4 の轍（見た保証が無いのに焼いて教育の機会を失う）に当たり、
  しかもこの画面は**読み込みが重く目を離しやすい**＝時間の推定が最も当てにならない面。
- **現状維持（何も置かない）** — 実機所感がそのまま症状。規則1b で置くべきものが置かれていない状態。
- **取り込み画面にも `NarouExternalPageNoticeHost` を置く** — 決定2 のとおり。器が増え、初回の手数も増える。

## 波及（実装の形）

列は1本のまま7要素になり、増えたのは**呼び出し側1箇所**だけ（正本 §3/§8 の芯がそのまま効いた）。
`IntroGroup`／`IntroFigure` に各1値・`IntroDeck` に1カード・`PrefKeys` に1キー・
`introPrefKey` に1分岐（`when` が enum 網羅＝**追従漏れはコンパイルで赤くなる**）・`PdfImportScreen` に契機。

- **図版は新規1点**（`IntroFigure.IMPORT`）。`TWO_WAYS` の使い回しは**不可**＝あちらは2つの面を
  **並べて分ける**図で、こちらは**片方からもう片方へ運ぶ**図（`ORIENTATION` のときと同じ理由）。
- **ベンチのシード契約では `intro_import_shown` は neutral**（`LibrarySeedReceiver` は固定しない）＝
  組D を出す入口が取り込み画面1箇所しかなく、ベンチはそこへ入らない（3タブと読書画面しか歩かない・
  播く本は `ncode=null`・`PdfImportBenchmark` は broadcast で Service を直に叩き画面を通らない）。
  ⚠️ **取り込み画面や作品詳細を歩くベンチを足したら mustPin へ移すこと**。
- ⚠️ **版面の実測**: 組D は組C より1行ぶん高く（3項目目が3行に折り返す）、360×640dp・既定フォントでは
  ［とじる］ が折り返しの下に入る。**この器の既知の性質**で退行ではない（縦スクロール器＝
  `IntroOverlayContentTest` が組C でも「スクロールで必ず到達できる」ことを見ており、組D にも同じ検査を足した）。
  詰めるなら**文言ではなく器の側**——文言は裁定済みなので実装側で言い換えない。
