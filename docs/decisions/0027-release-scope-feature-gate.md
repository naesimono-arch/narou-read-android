# 0027. 初回公開のスコープ機能ゲート＝スキン機能ごと隠す（明快K 単独公開）

- 状態: **Accepted（2026-07-29 ユーザー裁定）— 実装は未着手（裁定の記録）**
- 関連: ADR 0021（UIスキン機構）・0022（スキン構造層）・0023（高負荷スカイ）・0025（採番規約）／`handover.md`「Google Play 公開準備 — 技術トラック」／`android/app/src/main/java/com/novelreader/ui/theme/Skin.kt`・`MainActivity.kt`・`ui/WardrobeScreen.kt`・`android/app/build.gradle`

## 背景（要求と制約）

2026-07-19 の公開方針に「スキン M/P/J は初回リリースに含めず、課金実装後のアップデートの目玉に温存」があるが、**実装側にそれを実現する仕掛けが1つも無い**（release ビルドでも `Skin` enum 6種が装いの間から全部選べる）。方針とコードが乖離したまま初回アップロードへ進むと、温存するはずの目玉がそのまま無料で出る。

2026-07-29 のユーザー裁定でスコープが拡大した: **公開するのは明快K のみ。D/C/M/P/J に加えてスキン機能（装いの間）そのものを隠す**。

裁定を支える事情:

- **C 夜行は未完成**: 「人間の実機目視で『これが夜行だ』と確認できた事実はまだ一度もない」（handover A2 節）＝色層だけで構造・演出層が無く、D ダークと区別がつかない状態。
- **M/P/J には未消化の意匠課題が残る**（取込バナーの Web 0%凍結・復旧バッジの翻訳未裁定・要裁定の色相偏り等＝handover「スキン後回し枠」）。
- D 和モダンは完成度が高いが、**D を出す＝スキン選択機能を出すこと**であり、機能ごと隠す裁定に道連れとなる。

## 制約（2026-07-29 コード実測）

適用点の設計は、以下の実測を前提とする。

- `Skin` enum は6種（K/D/C/M/P/J）。**プロダクションコードで `Skin.entries` を列挙するのは `WardrobeScreen.kt:86` の1箇所のみ**（他2箇所は `src/test`）。
- スキン軸が外へ出る経路は3つ:
  1. 設定タブ「きせかえ」行 → `MainActivity.kt:540` の `navigate("wardrobe")`
  2. `composable("wardrobe")`（同 549）＝装いの間の画面そのもの
  3. `skinFromName()`（`Skin.kt:47`）＝ SharedPreferences `"app_skin"` からの復元
- M の本棚（`BookshelfLogM`/`BookshelfSkyM`）に装い入口が残存している（撤去実装済み・実機目視待ち）が、M 自体が到達不能になるため公開影響はない。
- **enum から値を削る案は構造的に不成立**: `when (skin)` 分岐が5ファイル、`Skin.tokens` は exhaustive when、`DiscoveryHomeInvariantCoverageTest` は `Skin.entries` 全数の登録を要求する。削れば全部落ちるうえ、「温存＝コードは残す」方針とも矛盾する。
- `buildConfigField` の機構は**現状ゼロ**（`buildTypes` は release / benchmark のみ・benchmark は `initWith release`）。
- **テーマ軸（`ReadingTheme` ライト/セピア/ダーク＋「システムに従う」）は Skin と独立**（`SettingsScreenK.kt:236`・`ReadingSettingsSheet.kt:367`）＝本ゲートの対象外。公開ビルドでも残す（明快K は複数変種を持つため、ここまで消すとダークモードが失われて明確な後退になる）。

## 決定

1. **単一フラグ `Features.skinSwitchingEnabled`** を新設する。値の出所は `build.gradle` の `buildConfigField`（debug=true / release=false・benchmark は `initWith release` で自動継承＝計測が公開構成と一致する）。
2. **適用点は次の3つだけ**（ここを増やさないことが本 ADR の眼目）:
   - 設定「きせかえ」行を出さない
   - `composable("wardrobe")` をそもそも登録しない
   - `skinFromName()` が `MEIKAI_K` へクランプする
3. **prefs の保存値は消さない**。読み替えるだけにする。理由: ①解禁時にその端末の選択が自然に戻る ②公開ビルドがユーザーデータを破壊的に書き換えない。
4. **判定は「フラグを引数で受ける純粋関数」に切り出す**。`BuildConfig` を適用点へ直参照すると、JVM テストは debug の BuildConfig しか見ないため **off 側の経路をテストで固定できない**（緑のまま公開ビルドだけ壊れるクラス）。
5. `Features` は**中身だけ差し替わる一枚板**にする。今はビルド時定数を読むが、課金実装後は購入状態を読む実行時判定になる——そのとき**適用点3つは不変**であることを設計の目的とする。

### なぜ「入口を消す」だけでは足りないか

`skinFromName()` は不正な文字列しか弾かない（`valueOf` の失敗のみ捕捉）。`SEIZU_M` のような**正当な値は素通りする**ため、入口だけ塞ぐと次が穴になる:

- すでに D や M を選んである端末（＝開発者の検証機）は、公開ビルドを入れてもその装いのまま起動する
- Auto Backup 復元（ADR 0015 で prefs はバックアップ対象）でも同じ
- 将来「解禁 → 再封鎖」したときに再発する

**一覧・ルート・復元は必ず1セット**で塞ぐ。

## 却下案

### 案B: enum から D/C/M/P/J を削る／productFlavor でソースセット分離

ビルドから物理的に消えるためサイズも減り、露出も原理的にゼロ。**却下理由**: exhaustive when と不変条件テストが enum 全数を要求するため大規模改修になり、「温存＝コードは残す」方針とも矛盾する。モック・テストの二重管理コストが公開までの期間に見合わない。

### 案C: `BuildConfig.DEBUG` を適用点へ直書き（最小差分）

**却下理由**: ①課金導入時に同じ箇所をまた開けて回ることになる（フラグの意味が「デバッグか」から「購入したか」へ変わるため）②JVM テストで off 経路を踏めない。

### 案D: release にも隠し入口を置く（設定の版数7回タップ等）

release 版でスキンの実機回帰をいつでも回せる利点があるが、**却下（2026-07-29 ユーザー裁定「不要・解禁時に回帰」）**。理由: 将来の有料スキンを無料解放する裏口になる。release でのスキン確認は、解禁コミット時の R8 実機回帰で担保する（回帰はどのみち必須）。

### 案E: 内部検証専用の buildType を新設（release 相当＋フラグ on）

裏口なしで R8 回帰が回せるが、**Play へ上げる物とは別バイナリ**になり「検証した物 ≠ 出荷物」が生じる。同じく却下。

## 帰結

- 公開ビルドの装いは**明快K 固定**。テーマ選択（ライト/セピア/ダーク/システムに従う）は残る。
- **隠してもAPKサイズは減らない見込み**: `skinFromName` の `valueOf` が実行時文字列駆動のため、R8 は D/C/M/P/J を到達不能と証明できず、enum も各 `SkinX` トークンも APK に残る。**要実測**（`shrinkResources` がスキン専用リソースだけ落とす可能性も同時に見る＝落ちていると解禁時に初めて気づく）。
- 高負荷スカイモード（ADR 0023）は M スキン限定のため二重に無効化される。既存の `BuildConfig.DEBUG` ガードはそのまま残す（撤去しない＝解禁後も debug 限定であるべき）。
- **検証機の見え方が変わる**: 保存値が D/M のままの端末に公開ビルドを入れると明快K で起動する（prefs は温存＝debug ビルドに戻せば元の装いに復帰）。
- **解禁時は「フラグ反転＋R8 実機回帰」が1セット**。release を初めて通る塊なので、回帰を省略しない。
- **初回公開のブロッカーが縮む**: handover の「スキン後回し枠」（M/P/J の取込バナー Web 0%凍結・復旧バッジの M/P/J 翻訳・要裁定の意匠差）は公開ブロッカーから外れ、課金アップデート便へ送れる。
- ストア掲載スクリーンショットは明快K で撮る（handover [素材] 項）。

## 追記（2026-07-30）: 隠す対象の**保守スコープも凍結**する

上の決定は「公開ビルドから何を隠すか」だけを定めており、**隠したものを作り続けてよいか**を書いていなかった。
結果として、出荷しないコードの意匠を詰める作業（M/P/J の未完了項目）が backlog に残り続け、
**出荷物に一切影響しない作業の保守コストを初回公開前に払う**構図になっていた。これを閉じる。

### 追認する既決の事実

本追記は新しい判断ではなく、既に下りている裁定の明文化である。

- **2026-07-29 ユーザー指示「公開に必要なそれではない」＝スキン系裁定は全て後回し**（`.claude/plans/handover-sweep-2026-07-29.md`）。
- 上の「帰結」— スキン後回し枠は初回公開のブロッカーから外れ、**課金アップデート便へ送れる**。
- `handover.md` 冒頭 —「豪奢スキン（M/P/J）は**否定しない＝温存**。ただし優先度は A/B の下」。既存 backlog は消さず保持。

### 決定

**初回公開までの間、M/P/J（および D/C）の意匠差分・未完了項目には新規着手しない。**

- **既存実装は削除しない**（却下案B のとおり「温存＝コードは残す」）。凍結であって撤去ではない。
- **解禁は課金アップデート便と同時**＝上の「解禁時はフラグ反転＋R8 実機回帰が1セット」と同じタイミング。
  意匠の作り込みと裁定取りはそこでまとめて再開する。
- backlog の該当項目は**消さずに「凍結中」として保持**する（優先度を下げるのであって、忘れるのではない）。

### 凍結の対象（新規着手しない）

`handover.md` の「スキン後回し枠」に集約されている類:

- M `SkyProcessingBanner` / P `WritingBanner` の Web 0%凍結（各1行の出し分け）
- 蔵書復旧バッジの M/P/J 翻訳（モック未裁定）
- 2026-07-18 スキン検分ラウンドの**要裁定の意匠差群**（色相偏り・スロット意味のスキン間割れ 等）
- M「迎える」/ J ⋮ の FAB 置換など、スキン固有意匠の裁定取りとモック起こし
- M/P/J 専用のリッチ化（高負荷スカイの横展開＝ADR 0023 は M 限定のため二重に凍結）

### 凍結の**対象外**（線引き）

ここを誤ると K の開発が止まるので、境界を明示する。**「M/P/J に触れたか」ではなく「M/P/J のために着手したか」で判定する。**

1. **共通実装の変更が M/P/J にも自動的に及ぶケースは凍結対象外。**
   route 層（`MainActivity` のルーター・ダイアログ動線）・共有 Composable・共通トークン層・データ配布（`source` フィールド等）は、
   K のために変えれば全スキンへ及ぶ。**それを避けるために K 側の変更を歪めてはならない。**
   先例: 蔵書復旧の「**ダイアログ動線自体は route 層差し替えで全スキン有効**」（バッジの M/P/J 意匠だけが後回し枠）。
2. **コンパイルと不変条件テストを通すための最小の受け皿は凍結対象外。**
   `when (skin)` は exhaustive で、`DiscoveryHomeInvariantCoverageTest` は `Skin.entries` 全数の登録を要求する（上の「制約」参照）。
   新画面・新トークンを足せば M/P/J の分岐も**書かざるを得ない**＝ここで手を止めることはできない。
   **ただし K からの機械的な最小翻訳で止める**。見た目を詰める・差分を裁定に上げるのは解禁便へ持ち越す——これが本追記の眼目。
3. **クラッシュ・データ破損クラスの不具合は凍結対象外**（出荷しなくても debug ビルドでの実機検証を壊すため）。
   意匠の不備（色が沈む・余白が揃わない）は凍結対象。
