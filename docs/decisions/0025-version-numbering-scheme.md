# 0025. versionCode/versionName 採番規約（内部→オープン→製品トラック運用）

- 状態: **Proposed（ユーザー裁定待ち・2026-07-29）**
- 関連: `android/app/build.gradle`（現在値 `versionCode 1` / `versionName "1.0"`）・`handover.md`「Google Play 公開準備」[運用] 項・完全フロー資料 §3/§6（`/mnt/c/Users/qingj/Desktop/project/アプリ公開戦略/`）

## 背景（要求と制約）

初回公開を内部テスト→オープンテスト→製品トラックの順で進める方針（組織アカウント＝クローズドテスト 12人×14日は免除）。採番を場当たりにすると「どのビルドがどのトラックに居るか」が追えなくなるため、公開前に規約を固定する。

Google Play 側の制約（採番の自由度を規定する外部事実）:

- **versionCode はアップロードごとに一意・単調増加**が必須。上限 2100000000。
- **一度アップロードした versionCode は再利用不可**（リリースを破棄・却下されても番号は消費される）。
- **トラック間の昇格（内部→オープン→製品）は同一 AAB をそのまま昇格**でき、versionCode を消費しない＝「トラックごとに番号帯を分ける」必要はそもそも無い。
- versionName は自由文字列で、ストア表示・ユーザー向け表現にのみ使われる（Play は解釈しない）。

内部条件: 個人開発・リリースは手動（CI 自動リリースなし）・単一 AAB（ABI 分割なし＝Play App Signing + AAB）。

## 選択肢

### 案A: versionCode＝通し連番＋versionName＝semver 風（推奨）

- **versionCode**: Play へアップロードする AAB を作るたびに +1。**意味を持たせない**（ただのアップロード通し番号）。
- **versionName**: `MAJOR.MINOR.PATCH`。意味はこちらだけが持つ。
  - MAJOR: 大規模刷新（体験が別物になる級）
  - MINOR: 機能追加（例: 装いの間の課金投入・新対応サイト）
  - PATCH: 修正のみ
- 初回製品公開＝`1.0.0`（現在の `"1.0"` は初回アップロード前に `1.0.0` へ揃える）。
- テストトラック用ビルドも**次期リリースの versionName をそのまま使う**（suffix なし）。ビルド個体の識別は versionCode と Play Console のトラック表示で足りる。
- 審査却下・差し戻しで再ビルドする場合: versionCode だけ +1、versionName は据え置き（ユーザー向けの意味が変わらないため）。

### 案B: 日付ベース versionCode（例 `2026072901`）

- 利点: 番号からビルド日が読める。
- 難点: 個人開発・手動リリースでは日付情報は git log で足りる。上限 2100000000 に対し 20260729xx は既に 96% を消費した位置＝残り空間が細い。同日複数アップロードの桁繰り・「versionCode に意味を持たせる」こと自体が案Aの単純さに劣る。

### 案C: versionName 導出 versionCode（例 `1.2.3` → `1002003`）

- 利点: 両者が機械的に対応し、ズレが起きない。
- 難点: **同一 versionName のまま再アップロードできない**（却下→修正再提出・署名やり直し等で、ユーザー向け版数が変わらないのに PATCH を上げるか、第4桁「ビルド番号」を導入して複雑化するかの二択になる）。単一 AAB・手動運用ではこの硬さに見合う利得がない。

## 決定案（案A）— 運用手順まで含めて

1. **アップロード直前に** `android/app/build.gradle` の `versionCode` を +1（初回アップロード＝`2` ではなく**現在値 1 のまま初回に使ってよい**。未アップロードのため消費されていない）。versionName は上記規約で設定。
2. 採番変更は**それを含むリリース準備の論理変更と同じコミット**に同梱し、件名に versionName を書く（例: `feat: 1.1.0 装いの間を投入`）。完了履歴は git log が正本＝台帳へ採番表を作らない（CLAUDE.md 規約に従う）。
3. トラック昇格は Play Console 上の昇格操作のみ＝リポジトリ側の変更なし。
4. versionCode の現在値は build.gradle が唯一の正本（他所へ転記しない）。

## ユーザー裁定が要る点

- 案Aの採否（および初回公開を `1.0.0` とする表記）。
- テストトラックの versionName に `-beta` 等の suffix を付けたいか（案Aは「付けない」を既定とした。オープンテストはストアに露出するため、付けるなら見え方の好みの問題＝意匠でなく表記の裁定）。

## 帰結（案A採用時）

- build.gradle の diff が最小（2行）で、リリースのたびの判断が「versionName をどう上げるか」だけに収束する。
- versionCode は情報を持たないため、逆引き（番号→何の便か）は git log と Play Console のリリース履歴で行う。
