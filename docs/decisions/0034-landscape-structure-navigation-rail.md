## 背景 — 横向きでは書影カードが1枚も収まらない

2026-07-30 に実機（OPPO PGEM10）で発見し、**2026-08-14 に実機で現状も再現を確認**した。

| | 値 | 内訳 |
|---|---|---|
| 実効ビューポート | **~133〜141dp** | ボトムナビ 65dp ＋ ヘッダ ~68dp ＋ 状態チップ行 ~46dp ＋ システムバー |
| カード実高（5列） | **~206〜212dp** | セル幅 124.8dp → 書影 3:4 で 166.4dp ＋ キャプション |

**＝構造的に入らない**（縮めば入る、ではない）。さらに末尾までスクロールすると画面の 2/3 が空白になる。

**本棚だけの問題ではない。** 2026-08-14 の実機で、**さがす（ランキング）でも横向きでは一覧の可視高さが
ナビバー直上 ~180px しかなく実質1行しか読めない**ことを確認した。
同型の原因＝**縦向け前提の固定分（ヘッダ・状態チップ行・ボトムナビ）が、横向きの少ない縦を食い尽くす**。
つまりこれは本棚のグリッド設計の問題ではなく、**横向きの画面構造の問題**である。

`Insets.ScrollBottomForFab = 96dp` は真因ではない（`contentPadding` はビューポート高を食わない）。
ただし「1枚も入らない画面の末尾に 96dp の空白」は体感を悪くするので、向き応答化は副次的に有効。

## 決定（2026-08-14 ユーザー裁定）

**横向きのときだけ、ボトムナビを NavigationRail（左端縦置き）へ切り替える。**

採用理由の骨子＝**横向きでは幅が余って高さが枯れている**。
ならば固定分は、枯れている軸（高さ）から**余っている軸（幅）へ逃がす**のが構造的に正しい。
ボトムナビの 65dp ＋ nav インセットが縦方向から消え、同時に横方向は元々余っているので損をしない。
Material の canonical な compact-height 対応でもある。

**この ADR が確定させたのは「横向きの構造を Rail にする」という一点だけ**である。

## 却下した代替案

- **(a) ヘッダ＋状態チップ行（固定 ~114dp）をグリッドの span item へ移し、スクロールで抜けさせる**:
  実効 ~250dp となりカード1枚＋次行の頭が見える。**意匠改変は最小**で、K の「全画面に明示タイトル」とも両立する
  （スクロールで消えるだけ）。**却下理由＝固定分を縦から追い出すだけで、ボトムナビの横帯は残る。**
  症状は軽くなるが、縦を食う固定分という構造そのものは手つかずのまま残る。
- **(c) カード実高を下げる**（列数 5→7 で書影 80dp なら計算上は収まる）:
  **却下理由＝裁定「書影の肥大回避」の逆方向へ行き過ぎる。** 収まりのために書影を潰すと、
  本棚が本棚に見えなくなる（横向きのためだけに本棚の主役を削ることになる）。

## 未確定として残すもの（意匠は未裁定）

**NavigationRail は新規 UI 要素**であり、規約どおり **HTMLモック先行 → 人間裁定 → Compose 翻訳**の順で進行中である。
次はいずれも**まだ決まっていない**:

- Rail の幅
- ラベルの有無（アイコンのみか、アイコン＋ラベルか）
- FAB の置き場（Rail 頭部に載せるか、本文側に残すか）
- ヘッダ圧縮をどこまで踏み込むか（Rail を入れてもヘッダ ~68dp ＋ 状態チップ行 ~46dp は残るため、
  (a) 案の考え方を併用するかは別途）

## ⚠️ この破綻は golden に写らない（回帰で守れない）

Robolectric の window insets は全て 0 で、`@Config(qualifiers)` にインセット修飾子が存在しない。
合成インセットを流すことは可能だが、**その値は端末ごとの推測値＝推測を回帰の基準線に焼き込む**ことになるので採っていない。

**横向きの検証は実機が唯一の手段。** Rail 導入後も同じで、緑のゴールデンは横向きの健全性を何も保証しない。
