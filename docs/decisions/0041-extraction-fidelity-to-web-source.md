# 0041. 抽出の忠実性＝web 原文へ寄せる（字種写像は全面撤去・行→段落結合は撤回・寸法自動検出は維持）

- 状態: 採用（2026-09-03 ユーザー裁定）→ **同日 3 決定とも実装済み**（着地は末尾「着地」節。裁定本文は当時のまま）。
- 関連: 材料＝`docs/knowledge/extraction-charmap-diverges-from-web-source.md`・`naro-source-is-line-oriented.md`・
  `dimension-autodetect-was-preventive.md`（いずれも 2026-09-02 の独立再実装実験 S2b の裁定材料）／
  影響先＝golden 一式・`pdf/CharClass.kt`・`pdf/DetectedRules.kt`・`ParserRules.kt`

## 背景 — 独立再実装との突合で「現行が何に合わせているか」が露出した

第二実装（`~/naro-pdf-engine/`）との全話突合で、現行の抽出結果は照合できた字種**6種すべて**で web 原文と食い違い、
第二実装は6種すべてで一致した。原因は1箇所ではなく**2系統**ある＝①字種の写像が pdfminer（既に使っていない旧経路）の
振る舞いを追従したまま ②行→段落の結合が原文に無い構造を作っている。
どちらも「バグ」ではなく**過去に意図して入れた変換**で、合わせている相手（pdfminer・読み味）が現在は正当化しにくい。

## 決定

### 1. 字種写像の pdfminer 追従は**全面撤去**し、web 原文一致へ寄せる

6種（波ダッシュ・二重引用符・縦書き括弧・ダッシュ・矢印・マイナス）すべてを第二実装と同じ写像へ。
決め手は**波ダッシュ**＝PDF は `～`FF5E と `〜`301C を作品ごとに撃ち分けて保持しているのに、
現行は一律 301C へ潰している＝**情報の復元ではなく破壊**であり、作品題3本が web と一致しなくなっている。

⚠️ **golden の全再採取と `CharClass` の改訂が道連れ**になる（避けられない＝本決定の一部として受け入れる）。

### 2. 行→段落結合は**撤回**し、抽出は行を保持する（結合は表示側の責務へ）

なろうの web 原文は **原文1行 = `<p id="L…">` 1つ**でサーバ側に「段落」という単位が存在しない（空行も要素として実在）。
現行は行境界の約1/3・空行の約半分を結合で失っており、`N0833HI` は本文空行が 0/9,823 ＝全滅している。
抽出は原文の行と空行をそのまま持ち、**読み味のための結合が要るなら表示側で行う**。

⚠️ 現行の段落誤り率は**測れていない**まま裁定した（ルビのインライン記法 `|親《読み》` が本文の `《》` と分離できず、
比較可能な話が 1.8% に落ちる）。**「誤り率が低いから維持」という反証は出せない**状態での決定であることを記録する
——裁定の根拠は誤り率ではなく「原文に無い構造を抽出段で作らない」という層の切り分けの側にある。

### 3. 寸法自動検出（`DetectedRules`）は**維持**する。ただし予防的措置と明記する

導入は実際に揺れる文書を観測して入れたものではなく、導入後に検出が挙動を救った証拠は0件（変更3件はすべて性能・メモリ最適化）。
それでも**撤去しない**＝既に動いており最適化も済んだものを剥がす動機が、将来なろう公式の生成器が寸法を微調整したときの
全滅リスクを上回らない。**「予防であって実測に基づかない」ことを当該コードのコメントに明記する**のが本決定の実体。

## Why-not

- **段階的に直す（破壊系＝波ダッシュ・二重引用符・マイナスだけ先に）**: golden 再採取は結局2回発生する。
  変更面が小さいという利点は、採り直しを二度やる費用に見合わない。
- **現行維持（pdfminer 追従を仕様と認める）**: 合わせている相手が既に使われていない実装＝**死んだオラクル**。
  仕様として明文化しても、次に誰かが web と突合したときに同じ調査が再発する。
- **寸法自動検出の撤去**: コード量と分岐は減るが、元々の動機（生成側の寸法微調整で全滅する脆さ）は消えていない。

## 着地（2026-09-03 実装）

裁定本文は変えていない。以下は実装の結果と、裁定時には分かっていなかった事実の記録。

### 決定1 — 真因は「写像」ではなく**参照する層**だった

6 系統のうち撤去で直るのは 2 つ（FF5E→301C・FF0D→2212）だけで、残る 4 つ（縦書き括弧・二重引用符・
ダッシュ・矢印）は `PdfExtractor` に写像が存在しなかった＝**ToUnicode CMap（縦組みグリフ→Unicode の逆引き）
が返していた**。逆引きは縦組み専用の表示形（FE47/FE48）や CID 共有による別字（301E）へ写り、`—`2014 は
U+0336 結合長打消線という**独立字ですらないもの**になっていた。なろうの PDF は `…-UniJIS-UTF16-V/H` CMap＝
**文字コードが UTF-16 符号単位そのもの**なので、字はコードから決めれば 4 系統とも原文どおりに出る。
実装は `PdfExtractor.GlyphDecoder`（コード優先・UTF16 CMap のフォントに限定・ToUnicode はフォールバック）。
副産物として ToUnicode の穴（U+FFFD）対策の特別扱いが不要になり、同経路へ吸収された。

**7 つ目の系統を実装中に発見**: `‾`203E → `￣`FFE3（上線。N3957FQ に 2 件）。知見の表には無く、
全グリフの新旧差分を取って初めて出た＝**表の 6 系統は網羅ではなかった**。

**検証**: 旧経路と新経路で全グリフを二重復号して差分を数えた結果、変化は 8 種・すべて 1:1
（N6169DZ 1,904 件・N2959KI 8 件・他 2 本 0 件）。字数は 1 文字も増減していない。
sample_pdfs **全 10 本**について 21 コードポイントの出現数が第二実装（web 原文検証済み）と**完全一致**
——git 追跡外の 6 本を含み、追跡 4 本には出現しない `〝`301D / `〟`301F（N8809BK に各 593 件）も確認済み。
FE47・FE48・0336・2212・203E は全 10 本で 0 件。

### 決定2 — 「行を保持する」は**列→行の復元を実装すること**だった

PDF の列（1 列 30 字で折り返される版面の単位）は原文の行ではない。抽出が行を持つには
`~/naro-pdf-engine/design.md` §1.3 の復元規則（容量・ぶら下がり・widow 回避・経験則 2 つ）が要る。
`TextProcessor.ParagraphStreamer` を **`LineStreamer` へ置き換え**、字下げ/開き括弧だけを見ていた
段落判定を捨てて規則を実装した。結合の移設先は **`ui/ChapterContent.kt` の `splitIntoParagraphs()`**
（横書き `ChapterContent` と縦書き `VerticalChapterContent` が共有する唯一の段落定義点＝保存物
`chap_N.html` は行のまま残り、PDF 取込と Web 取込が同じ規則で読める）。移した判定字は旧実装と同じ 4 字。

**結果**: 非空行数が 4 文書 **79,546 行すべてでオラクルと完全一致**（153 / 6,522 / 146 / 72,725）。
ページ抜き fixture は行の長さ列が 232 行完全一致。

**残った穴（凍結・過小側にしか外れない）**: 空行 88 件（N6169DZ・0.13%）ほか計 90 件が復元できない。
機序は 2 つで、いずれも**本決定で生じたものではない**（空行の数え方は変えていない）＝
①見出しページは本文列の原点がずれるため、ページ跨ぎ空行の絶対座標の引き算が端数になり round で消える
②見出しページ内の先頭空行は「見出しの版面が占める空き」と区別できない（区別を試みると偽の空行が湧く）。

### 決定3 — 明記に加えて「新しい寸法をどう入れるか」を決めた

`DetectedRules` の KDoc に予防的措置である旨（導入時に揺れの観測なし・救った実績 0 件・OOM 寄与と
検出が固定値より悪化した実例あり）を明記。あわせて、決定2 で新たに要った寸法
`ParserRules.COLUMN_CAPACITY`（列の容量 30 字）は**検出機構へ足さず固定定数＋全数検証**にした
（`TextProcessorColumnCapacityTest` が実 PDF 4 本で「最長列＝容量+1・最頻列長＝容量」を毎回確かめる）。
理由は同 KDoc に記録＝揺れが実測されていない項目を検出へ足すのは、誤検出の面を新設するだけになるため。
