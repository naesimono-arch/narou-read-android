# 0007. 検索UXの共通言語＝3原則（実機フィードバック×競合実機調査からの導出）

- ステータス: Accepted

## Context（背景）

api-lab-ai ブランチで実装した発見・検索機能（C1〜C4・D1〜D5）に対し、ユーザーが実機で触った最初のフィードバックが出た。個別の不満は次の6点:

1. 結果画面の「ファンタジー／週間順」見出しを**直接押してその場で変更したい**（可変式）。
2. 「最強」で検索するとタイトルにも作者名にも「最強」が無い作品が上位に出る＝**どこから情報を引っ張ったのか不透明**。「皆さんは基本的にタイトルのみで検索する」。あらすじ単品の検索は実用性が薄い（削除までは求めない）。
3. 作品詳細のキーワードを**タップしてそのままキーワード検索に移行したい**。
4. 絞り込みの「期間」が**何の期間か伝わらない**。
5. 「属性」の選択肢が**あまりにも少ない**。複数選択できればより幅広い需要に応えられる。
6. 文字数・読了時間の**10万字以降が粗すぎる**（50万・100万の枠組み、または自分で数値を変更したい）。キーワードは異世界・転生など**UIのどこかで具体的かつ詳細に選択**できるようにしてほしい。

同日に行った競合5アプリ（なろう公式/カクヨム/なろうリーダ/なろうブック/Web小説リーダー）の実機調査（`05` レポート）と突き合わせると、これらの個別不満は**3つの設計原則の欠落**として一般化できた。この3原則を今後の検索UX実装・レビューの共通言語として固定する。

## Decision — 検索UXの3原則

### 原則1「見えている条件は、その場で変えられる」

画面に表示された条件（結果画面の文脈見出し・条件チップ・作品詳細のキーワード）は**説明の飾りではなく操作点**。条件を変えるために画面を往復させない。

- ユーザーの声: 上記 1・3。
- 競合の裏付け: 「結果画面に常駐するソート切替」は検索UIを持つ4アプリ中3アプリの定石（公式=下部フローティングバー・なろうブック=上部ドロップダウン・カクヨム=下部フローティング＋適用中条件チップ「転生 ×」）。公式は「条件を変更」1タップ復帰もセットで持つ。
- 実装時の含意: 条件チップのうち可変にできるもの（並び順・ジャンル）はタップ→その場切替→即再検索。詳細画面のキーワードチップはタップ→キーワード検索。検索発の結果には「条件を変更」で検索画面へ1タップ復帰（ドラフトは VM 保持済みで往復に耐える）。

### 原則2「検索の仕組みを隠さない」

なぜこの作品が出たのかがユーザーに説明できる状態を保つ。**検索範囲の既定はタイトル**（体感と一致する最小範囲）とし、範囲を広げるのは明示操作。ラベルは API 語彙の直訳ではなく生活語で書く。

- ユーザーの声: 上記 2・4。
- 根本原因（実装事実）: 範囲チップ4種が全て未選択のまま検索すると、なろうAPI仕様により**全項目（タイトル・あらすじ・キーワード・作者名）が対象**になる。「最強」→「お嬢様」作品はあらすじ or キーワードにマッチしていた。UI はこの暗黙の全域検索を一切表示していなかった。「期間」の正体は `lastup`（最終掲載日＝最新話の投稿時期）。
- 実装時の含意: 範囲の既定=タイトルON・全解除は許さない（全解除=暗黙の全域検索が再発するため、最後の1つは外せない）。「期間」→「更新された時期」など意味が閉じる語へ。誤解を生む選択肢（「今週」=日曜0時起点）は生活感覚に合う「7日以内」（`sevenday`）へ置き換える。

### 原則3「語彙を知らなくても絞り込める」

なろうの検索語彙（作者が付けるキーワード・属性フラグ・文字数の相場観）を知らないユーザーでも条件が組めるよう、**UIが具体的な選択肢を先回りして提示**する。

- ユーザーの声: 上記 5・6。
- 競合の裏付け: カクヨムのキュレーションタグ（「地位・称号」「職業」等のカテゴリ別チップ提示）が5アプリ中最リッチな検索UXの核。「タグを知らなくても検索条件が組める」への回答であり、なろうのキーワード検索へそのまま適用できる差別化候補（`05` 示唆7）。
- 実装時の含意: 属性は API が提供する全6軸（転生・転移・R15・BL・GL・残酷描写）を「含める/除外する」の両方向で複数選択可能に。文字数・読了時間は対数的な上位刻み（〜50万・〜100万）＋カスタム数値入力の逃げ道。頻出キーワードをカテゴリ別チップで提示（キュレーション）。

## 適用対応表（フィードバック→原則→実装）

| フィードバック | 原則 | 実装 |
|---|---|---|
| 1 見出しをその場で変更 | 1 | 結果画面の並び順チップ・ジャンルチップをタップ可変化（ドロップダウン→即再検索）＋検索発は「条件を変更」1タップ復帰 |
| 2 「最強」→出所不明 | 2 | 検索範囲の既定=タイトルON・全解除禁止・チップ並びをタイトル/キーワード/作者名/あらすじへ（あらすじは末尾降格） |
| 3 キーワードタップ検索 | 1 | 詳細画面キーワードチップに clickable → keyword 範囲の検索として結果画面へ |
| 4 「期間」不明瞭 | 2 | セクション名「更新された時期」・選択肢「7日以内/今月/先月」（thisweek→sevenday 置換） |
| 5 属性が少ない・複数選択 | 3 | 属性6軸×含める/除外の複数選択（`Set<NarouAttr>`）。転生＋転移同時は istt 振替を維持 |
| 6 文字数/読了時間の枠・キーワード選択UI | 3 | 上位刻み（10万〜50万/50万〜100万/100万〜等）＋カスタム数値入力／カテゴリ別キュレーションキーワードチップ |

## Why-not（採らなかった選択肢）

- **マッチ理由バッジ**（「あらすじに一致」等を結果行に表示）: 一覧取得の `of` から `story` を意図的に外している（転送量マナー）ため判定素材が無い。範囲既定=タイトル化で不透明の根本を絶つ方を選んだ。
- **範囲の「すべて」チップ追加**: 4チップ全ONで表現できるため冗長。既定タイトル＋明示的な拡張で足りる。
- **あらすじ検索の削除**: ユーザー自身「削除しろとまでは言わない」。末尾へ降格して残す（除外ワードと同様、使う人は使う）。
- **文字数を線形スライダーへ**: ダイナミックレンジが広すぎ実用に耐えない（Phase 2 の段階チップ翻訳判断を維持・STATUS-api-lab §2）。
- **属性の3状態チップ**（無指定→含む→除外をタップで巡回）: 状態が発見しづらく誤操作しやすい。カクヨム式に「含める」「除外する」を別グループで並べる明示型を採った。

## 検証

この3原則は今後の発見系UI変更のレビュー観点として使う: 新しい条件表示を足すときは「タップで変えられるか（原則1）」「意味が閉じた言葉か（原則2）」「選択肢を先回り提示できるか（原則3）」を通す。
