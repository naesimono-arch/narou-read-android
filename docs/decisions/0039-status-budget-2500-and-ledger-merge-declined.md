# 0039. STATUS の上限を 2,500 字へ引き直し、台帳の統合は見送る

- 状態: 採用（2026-08-25 ユーザー裁定「統合はいいや。2500 で行こう」）
- 関連: ADR 0017（完了履歴は git log）／ADR 0028（台帳を待ちの種類で二分）／
  CLAUDE.md「管理ドキュメントの体系」／`.claude/hooks/remind_ledger_sync.py`（消化の合図）

## 背景1: 上限が「症状の追認」から引かれていた

台帳の字数上限は 2026-08-13 に導入されたが、そのときの実サイズはこうだった。

| 台帳 | 導入時の実サイズ | 設定された上限 |
|---|---|---|
| STATUS.md | 5,542 | 6,000 |
| handover.md | 11,170 | 8,000 |
| awaiting-human.md | 13,105 | 12,000 |

**上限は「台帳に何が要るか」ではなく「そのとき何字あったか」から引かれている。**
STATUS に至っては現状＋8% の余白でしかない。上限が既存の肥大を追認しているので、
「消化の合図」として働かないのは構造的に当然だった（実際 STATUS は 2026-07-23 に上限の 1.4 倍へ達し、
圧縮で収めたあと1か月で再び上限へ戻っている＝規約の言い換えだけでは機構が変わらなかった）。

## 背景2: 肥大の正体は台帳ごとに違う（実測）

2026-08-25 に3本とも消化した結果:

- **STATUS.md 5,955 → 1,876**。消したのは機能カタログ・ゲートの内訳・完了履歴＝**現在値でない文章**。
  削除49行を独立エージェントが全件追跡し、**知識の消失はゼロ**（正本はコード・ADR・モック・CI 定義に実在）。
- **handover.md 7,894 → 7,632**（項目数 17 → 17）。**着地済みで消せる「やること」は1件も無かった**。
- **awaiting-human.md 9,502 → 7,747**。決着済みの再掲だけが落ちた。

**STATUS の肥大は文章、残る2本の肥大は本当に残っている仕事。**
後者を字数で縛っても、できるのは規約が禁じた圧縮だけになる。効くのは仕事を減らすことで、
その一歩＝エミュレータ導入で「実機でしか見られない」前提が崩れた6項目（ADR 参照先は `awaiting-human.md`）。

## 決定1: STATUS の上限を 6,000 → 2,500

実測 1,876 に、現在値が1つ増えるぶんの余白を足した値。**実サイズの追認ではなく、
「削って何も失わなかった」事実からの逆算**である点が従来と違う。

同期先は4つ（1つでも取り残すと機械と規約が食い違う）:
`CLAUDE.md`「管理ドキュメントの体系」／`STATUS.md` 冒頭の凡例／
`.claude/hooks/remind_ledger_sync.py` の `LEDGER_LIMITS`／
`.claude/skills/stale-check/check_machine.py` の `LEDGER_BUDGETS`。

handover / awaiting-human の上限は**据え置く**。実測で「消せる項目が無い」と分かった以上、
下げれば圧縮を強いるだけになる。**下げてよいのは項目を消化した後**。

## 決定2: 台帳の統合（handover ＋ awaiting-human を1本へ）は見送る

### 統合を検討した理由（＝分割の代償が実測で出た）

ADR 0028 の分割は正味の削減を伴っていた（42,247 → 21,208 ＋ 9,366 ＝ 11,673 字は実際に消えた）ので、
「圧縮のための移設」ではなかった。しかし2026-08-25 に**分割固有の腐敗**が3件出た:

1. `awaiting-human` §1-7 が**人間待ちでない項目のアンカー**として残り、`handover` の実体項目がそこを指していた（空見出しは同ファイルの凡例どおりの参照先＝それ自体は仕様。問題は `awaiting-human-machine-decidable-triage.md` が「機械で決まる＝人間待ちではない」と分類済みだったのに、**人間待ち台帳に居場所を持ち続けた**こと）。
2. `awaiting-human` が「翻訳は handover のやること」と、**着地済みの作業**を指していた。
3. STATUS の削減が `handover` の依存していた plans 一覧を壊した（別便で復旧）。

根はひとつで、**項目は両面を持つ**（例: 教示「はじめに」＝golden 未追加は機械作業・初見の分かりやすさは目視）。
ファイルで割ると片方が相方を指すポインタになり、そのポインタが腐る。

### 見送った理由

ADR 0028 が挙げた症状2（人間待ちが地の文に溶けて**動ける項目が読み取れない**）は実在し、
統合はこれを再発させうる。項目ごとの担い手タグ（`[C]`/`[H]`）＋ `inject_handover_digest.py` の
地図注入をタグ別にすれば理論上は両立するが、**統合しても字数は減らない**（減るのはポインタの腐敗と同期の手間だけ）。
採択済み ADR の差し替え・約26項目の再タグ付け・フック改修という費用に対し、
いま得られるものが「腐敗の予防」だけなので、**費用が先に立つ**と判断した。

### 再検討する条件

- 上記の腐敗（誤った台帳への居座り・失効ポインタ・他台帳の削減で切れた依存）が**再び3件以上**出たとき。予防でなく実害の再発を根拠にする。
- または項目数が減って統合後の1本が現実的な大きさ（目安 8,000 字）に収まる見込みが立ったとき。
