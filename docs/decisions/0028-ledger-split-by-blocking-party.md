# 0028. やること台帳を「待ちの種類」で二分＝`handover.md`（Claude が動ける）／`awaiting-human.md`（人間待ち）

- 状態: 採用（2026-07-30 ユーザー裁定「待ちの種類で分ける」）
- 関連: ADR 0017（管理ドキュメント体系の再編＝完了履歴は git log・handover はやることのみ）／
  CLAUDE.md「管理ドキュメントの体系」／`handover.md`・`awaiting-human.md` 冒頭の凡例／
  stale-check `check_size_budgets`・`check_referenced_files`

## 背景（実測した3症状）

ADR 0017 で「handover ＝やることのみ・完了は消す」と定めたが、2026-07-30 時点の `handover.md` は
**304行・約33,000トークン**まで肥大し、「悩んだらまず見る」台帳としての用を成さなくなっていた。原因は3つ:

1. **完了情報の残留**。「完了したら消す」規約は打ち消し線を禁じたが、**「実装済み・残は実機目視のみ」**という形で
   完了経緯（真因・裁定の経過・PASS した検証）が本文に残り続けた。打ち消し線ではないので機械の番人
   （`check_size_budgets` は打ち消し線を数える）にも掛からない。
2. **人間待ちが地の文に溶けている**。「実機目視」16箇所・「要裁定/裁定待ち」13箇所・「保留」13箇所が
   各項目の末尾に埋もれ、**Claude が今すぐ動ける項目はどれかが読み取れない**。台帳を開いた側（Claude も人間も）が
   毎回このフィルタを頭の中でやり直していた。
3. **1行が平均112トークンと長大**で拾い読みができない（一次情報を畳まず本文に展開していた）。

症状1と3は刈り込みで減らせるが、**症状2は1ファイルのままでは消えない**——同じ項目に「実装は済んだ／目視が要る」の
両面が同居する以上、どう並べ替えても「動けるものだけを見る」ことができない。

## 決定

**やること台帳を「誰待ちか」で2ファイルに分ける。**

| ファイル | 置くもの | いつ開くか |
|---|---|---|
| `handover.md` | **Claude が今すぐ着手できるやること**（実装残・調査残・計測・ドキュメント作業・思いつき） | 次に何をやろうか悩んだとき（従来どおり） |
| `awaiting-human.md` | **人間待ち**（実機目視・意匠/方針の裁定・外部手続き＝ブランド名・鍵・Play Console・第三者） | 端末を手に取るとき・何かを決めるとき |

- **`awaiting-human.md` の各項目には「何を見れば決まるか」を必ず書く**——実機目視なら〈どの画面で・何を見て・
  何が見えたら OK か〉、意匠裁定なら〈選択肢は何と何か・それぞれ何が変わるか・判断材料の在処〉、
  外部手続きなら〈何が確定すれば次へ進めるか〉。**これが書けない項目はここに置かない**＝材料を揃える作業が先で、
  それは handover 側のやること。この一行が分離の眼目で、無いと「人間待ち」は単なる棚上げ置き場になる。
- **目視項目は実機ツアーとして上から順に消化できる並び**（画面ごと・依存順）にする。
  バラバラの箇条書きは端末を持ったときに使えない。依存順の実例＝**削除警告の確認は蔵書復旧より先**
  （復旧すると警告が出る条件〔欠落本〕が消える）。
- **裁定項目には「放置した場合の帰結」を一言添える**（これが決まらないと公開できない／決めなくても困らない）。
  優先度は項目の性質でなく帰結で決まる。
- **どちらに置くか迷ったら `handover.md` 側へ置く。** 非対称だからである——handover は毎回開くので誤配置は
  すぐ気づいて移せるが、awaiting-human は端末を触るときしか開かないので、動けるものを入れると長く埋もれる。
- **「完了したら打ち消し線で残さず消す」運用は両ファイルとも不変**（完了の正本は git log＝ADR 0017 決定1・2 を継承）。
  ADR 0017 の他の決定（完了履歴は git log／STATUS は現在値のみ／CLAUDE.md はルーター／知見は 1知見1ファイル）も不変。

## なぜ分ける軸が「主題」でなく「待ちの種類」なのか

主題（画面別・機能別）で割るのは自然に見えるが、**症状2を全く解決しない**——「本棚」ファイルを作っても、
その中に本棚の実装残と本棚の目視残が同居し続けるからである。分割はコストなので、症状を消す軸でなければ払う意味がない。

より一般に、**台帳を開く動機は主題でなく状況**である。Claude が開くのは「次に何をやろうか」の状況、
人間が開くのは「端末を触る」「決める」の状況。読み手と場面で割ると、開いた瞬間に**全行が自分宛て**になり、
毎回のフィルタリングが不要になる。主題は目次（節見出し）で足りる粒度であって、ファイル分割の軸には強すぎない。

副次効果として、症状1（完了情報の残留）にも効く: 「実装済み・残は実機目視のみ」という項目は、
分割時に**目視部分だけが awaiting-human へ移り、完了経緯は行ごと消える**（正本は git log・機序は knowledge/ADR）。
「残っているのは経緯だけ」という状態が構造的に見つかりやすくなる。

## 却下した代替案

- **`STATUS.md` へ人間待ちを寄せる**: STATUS は「現在値のみ・目安60行」の現況台帳（ADR 0017 決定2）で役割が別。
  やること（未完了の action）を現況へ混ぜると、STATUS の 60行予算を壊すうえ「現在値」と「宿題」が再び同居する。
- **`handover.md` の中に「人間待ち」節を作る**: 節は地の文へ溶ける（今回まさに、各項目の末尾に溶けた結果が症状2）。
  加えてファイルを開くトークンコストが変わらないため症状3にも効かない。**節の規律より、ファイルの物理境界の方が強い。**
- **主題別（画面別・機能別）分割**: 上記のとおり症状2が残る。
- **完了情報だけ刈って1ファイルを維持**: 症状1・3は軽くなるが症状2は残る。今回の裁定の主目的は
  「Claude が今すぐ動ける項目がどれか読み取れない」の解消なので、これでは足りない。
- **人間待ちを `.claude/plans/` の実機ツアー チェックリストで代用**: プランは過去の一次情報（役目を終えたら
  `archive/` へ）であって、更新され続ける台帳ではない。実際、既存のツアー チェックリストは
  その後の実装（2026-07-30 の削除警告）を含んでおらず、単独では最新でない。

## 番人（着地済み・2026-07-31 追記）

**この節は当初「未整備＝宿題」として、`check_machine.py` の対象リストへ `awaiting-human.md` を足す作業を
handover に登録すると書いていた。それは書いた時点で既に事実と違っていた**——列挙5箇所（`MANAGED_PREFIXES`・
conflict markers・`check_referenced_files`・打ち消し線・「完了＋残＝」型）への追加は、本 ADR を採択した
コミットそのものに含まれていた。宿題として1日近く handover に居座り、実装しようとして初めて気づいた。
**教訓＝「宿題を書く」と「宿題を実装する」が同じコミットに同居すると、台帳側だけが未完のまま化石化する。**

実際に空いていた穴は別で、**数値予算が `handover.md` にも `awaiting-human.md` にも1つも無かった**
（`STATUS.md`=60行・`CLAUDE.md`=16KB のみ存在）。2026-07-31 に台帳2枚の**合計文字数**予算を入れて塞いだ:

- **主判定は per-file でなく合計**（high=42,000字）。片方の溢れをもう片方へ移すと per-file 予算では両方緑になり、
  総量が1文字も減らないため。二分した台帳では「移し替えによる見かけの解消」が構造的に起きうる。
- 42,000 は発明値ではなく、**本 ADR が肥大の実測として記録した分割前 `handover.md` の実サイズ**。
- 単位は「字」（記録が字。日本語台帳はバイトが約2倍＝取り違えると予算が黙って2倍に緩む）。
