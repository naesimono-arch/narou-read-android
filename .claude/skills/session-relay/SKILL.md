# /session-relay — セッションを畳んで引き継ぐ

## なぜ切るのか（判断の根拠）

1ターンの費用は**その時点のコンテキスト長そのもの**（毎ターン全長を `cache_read` で読み直す）。
長さはターン位置に線形で伸びるので、セッションの累積は **O(n²)**。実測では同じ 1 ターンの仕事が
n=51-100 で 99.2k、n=401+ で 317.5k ＝**3 倍高い**。総ターン数を変えずに 100 ターンで切っていれば
総量は **54%**（-46pt）だった。数値と機序＝`docs/knowledge/context-cost-optimization-levers-measured.md`。

⚠️ `🧠 17%` は「枠が 83% 空いている」ではなく「**1 ターンごとに 175k 払っている**」と読む。
1M 枠は余裕を大きく見せるので、枠の使用率として読むと切りどきを逃す。

## 手順

### 1. 先にコミットする

引き継ぎ先は**別プロセス**で、作業ツリーの状態は引き継がれない。未コミットの変更があるなら
先に済ませる（`git status --porcelain` が空になるまで）。コミットできない中途半端な状態なら、
**そのことを引き継ぎ文書に書く**。

### 2. 引き継ぎ文書を書く

`.claude/plans/relay-<YYYY-MM-DD-HHMM>.md` に書く。**これは機械には書けない部分**＝
何が終わって何が途中か、次の一手は何かの要約であり、このセッションにしか書けない。

含めるもの（無いものは省く。埋める作業ではない）:

- **ブランチ名**と、直前のコミットが何をしたか（SHA は書かない＝`git log` が正本）
- **今どこまで来ているか** — 完了したもの、途中のもの、検証が済んでいないもの
- **次の一手** — 引き継ぎ先が最初に打つべき具体的な行動
- **踏んだ罠** — 同じ失敗を繰り返させないためのもの。台帳や knowledge に既に書いたなら**そのパスだけ**
- **ユーザーとの約束** — 保留にした判断、待っている返答

含めないもの: 会話の経緯、捨てた選択肢、既に台帳・ADR・knowledge にあるものの再掲。
**引き継ぎ文書が長いほど、引き継ぎ先の序盤コストが上がる**（それ自体が n·F に乗る）。

### 3. 新しいセッションを立てる

```bash
powershell.exe -NoProfile -File 'C:\Users\naesimono\.claude\scripts\claude-launch.ps1' \
  nr '.claude/plans/relay-<...>.md を読んで作業を続けること。' -Name <名前>
```

- プロジェクトの指定・WSL/Windows の別・オプションは `/mnt/c/Users/naesimono/.claude/skills/launch/SKILL.md` が正本。
  NovelReader は `nr` で WSL 側に立つ。
- 最終行の `LAUNCH_OK name=<セッション名>` を確認する。この名前が `ListAgents` に出る識別子。
- RC 登録に数秒かかる。`ListAgents` の確認は**一度だけ**（ポーリングで待たない）。

### 4. ユーザーに報告する

**セッション名を必ず含める**（スマホの一覧でそれを探すことになる）。引き継ぎ文書のパスも添える。

### 5. このセッションをどうするか（**強制しない・各セッションの判断**）

終了する手段は存在する:

```bash
powershell.exe -NoProfile -File 'C:\Users\naesimono\.claude\scripts\claude-launch.ps1' -Stop <自分の名前>
```

⚠️ ただし `-Stop` は `~/.claude/launched-sessions.jsonl` の起動記録から pid を引く。
**launch 経由で起動したセッションしか止められない**（手動起動のセッションには記録が無い）。

判断材料を正確に置く。**どちらを選んでもよい**:

- **残しても費用は増えない。** コストはターンを回したときにだけ発生し、アイドルのセッションは
  トークンを消費しない。プロンプトキャッシュも TTL で自然に失効する。
  ＝**「効率のために自分を終了する」という理由は、実測上は成り立たない。**
- 終了して得られるのは費用ではなく**整理**。`ListAgents` とセッション一覧から消えるので、
  次に誰かが宛先を選ぶときの取り違えが減る。同名・同目的のセッションが並んでいるときは効く。
- 終了して失うのは**まだ使えたかもしれない文脈**。引き継ぎ文書に書き落としがあっても、
  生きていれば `SendMessage` で聞き直せる。死んでいれば聞けない。
- ユーザーが**外出先から見ている**ときは、勝手に消えたセッションは事故と区別がつかない。

**迷ったら残す。** 残す側の損失は実測でゼロで、消す側の損失は取り返せない。
終了を選ぶなら、**ユーザーへの報告を先に済ませてから**行う（報告前に死ぬと、何が起きたか伝わらない）。

## 通告について

`check_context_budget.py` が Stop で 175k 超過を検知して 1 セッション 1 回だけ通告する。
**無視して続行してもよい**——閾値は上限規約ではなく再考のトリガーで、
「いま切ると仕掛かりが壊れる」ときに続けるのは正当な判断。ただしその場合、
費用は 2 次で伸び続けている（同じ仕事が 3 倍高くなる領域に既に入っている）ことは把握しておく。
