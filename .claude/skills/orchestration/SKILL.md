# /orchestration — 司令塔モード

> 出自: 2026-07-19 リッチ化ラウンド。実測値の正本＝memory `feedback-subagent-context-hygiene`。

## 開始前に裁定点を確定させる（走り出す前に AskUserQuestion）

**派遣を1体でも始める前に、次の3点を `AskUserQuestion` で確定する**（2026-08-06 ユーザー指示）:
①**スコープ**（どこまでやるか・今回やらないと決めるもの）②**成果物の形式**（コミットまでか・提案止まりか・
モック裁定を挟むか）③**実機確認の分担**（誰がいつ端末を触るか・目視裁定は人間か）。

**Why**: この3点は走り出してからでは戻せない——スコープはエージェントの仕様に焼き込まれ、成果物の形式は
コミット粒度を決め、実機分担は端末の可用性に依存する。実際 2026-08-06 の一挙消化ラウンドでは
「実機接続済み」の前提で走り切った終盤に端末が adb から見えず、検証だけが宙に浮いた。
**判断が要る分岐を後から人間へ差し込むのは、監督が勝手に決めて進むのと同じくらい高くつく**。

例外は「ユーザーが既にその3点を明示している」場合のみ（明示された内容を確定事項として仕様へ書き写す）。
迷ったら聞く側に倒す＝§1 の「曖昧語は質問で止めず仮説分解」は**走行中の細部**の話であって、開始前の
裁定点には適用しない。

## 大原則: 監督の文脈に入れてよいのは「レポートと統計」だけ

監督は判断（仕様の翻訳・裁定の受け渡し・検収・台帳）に徹し、読む・作るはエージェントへ。
迷ったら「エージェントに読ませてレポートで受けられないか？」と自問。

## 0. 委譲の粒度 — 起動は固定費（2026-07-23 ユーザー指示で明文化）

- エージェント起動には固定費（起動・必読の読込・報告往復）がかかる＝細切れタスクの多数起動は損。
  **関連する小タスク（同一ファイル群・同一領域・同一真因系）は1体の委譲仕様に束ねる**（所有権も1体に寄り並走管理が楽）。
  ただし**束ねも無条件ではない**——束ねた結果が下記の谷（~30ターン）を大きく超える見込みなら細切れと同型の設計ミス＝束ねない。
- 「調査→合格なら実装」は general-purpose 1体の2段指示で連続（§6・memory `feedback-investigate-then-implement-same-agent`）。
- **切る軸の統一規範（2026-07-25 ユーザー裁定）**: 同一エージェント原則が禁じるのは**工程で横に切ること**
  （調査体→実装体の引き継ぎ＝調査で築いた所在・機序の文脈が外部化と再読で丸損）。ただし同一エージェント＝サイズ無制限ではない。
  **~30ターンは上限規約でなくトリガー（再考の合図）**＝起動固定費と長走行の超線形コスト（文脈肥大・再読・ストール率）が
  釣り合う**谷の経験的プロキシ**。EOQ と同型で √(固定費/可変費係数) に比例して動く——SubagentStart 自動注入で固定費が
  下がれば小さい側へ・必読が重いタスク（実機作法など）は大きい側へ。**谷 ~30 は維持**（2026-09-07 再測）。
  集計＝`tools/measure_subagent_run_length.py`（データ源は count_delegation_turns.py の `delegation-stats.jsonl`）。
  次の再較正は累計 n が再び倍増（~550件）したら＝現在 n=355 なので未達。
  ⚠️ **旧記載の「縮んだ＝運用が効いている証拠」は取り下げる（2026-09-07）**——一過性のくぼみを趨勢と読んだ誤り。
  全期間 n=355 で **中央値43・p75 66・p90 94・max 259**、窓別は 〜08-06 が中央値47/p90 97 →
  **08-07〜08-25 が中央値34/p90 75**（旧記載はここだけを見ていた。同じ窓・同じ方法で再現はする）→
  **08-26〜 は中央値44/p90 121/max 259 と戻った**。週別でも 51→49→30→32.5→58→42→54 で方向を持たない。
  **`30超` は全窓で 60〜78%＝30 を超えるのが常態**（全期間 70.1%）。∴ 30 は「守られている閾値」ではなく
  **超えた回数を数えても品質の指標にならない再考の合図**で、超過それ自体を逸脱と読んではいけない。
  谷を動かす根拠も依然として無い——**分布は「実際どう走ったか」の記録であって、コスト最適点の測定ではない**
  （谷の根拠は上の EOQ 型の費用構造の方であり、実測分布はそれを否定も肯定もしない）。
  ⚠️ **谷は単一の数字で運用しない**＝agent_type で桁が違う（08-26 以降・実測）:
  `device-verify` 中央値83・max 259／`general-purpose` 中央値46／`Explore` 中央値31。
  「必読が重いタスクは大きい側へ」は実測で裏づいた＝**実機系に 30 を当てるのは誤用**。
  ⚠️ 2026-09-04〜09-07 の測定は**データ分裂で信用できなかった**（フックが旧 project slug を直書きしたまま
  リポジトリが移動し、記録が 2 ファイルへ割れた）。フックの置き場を slug 非依存の
  `~/.claude/delegation-meter/` へ移し、分裂分は統合済み（同 2026-09-07）。上の数値は統合後のもの。
  ⚠️ **較正値の指標は `tool_uses`（ツール呼び出し回数）であって、セッション jsonl の assistant ターン数ではない**——
  後者で測ると 1 ターンに複数ツールを呼ぶぶん系統的に大きく出て「谷を大きく超えている」という逆の結論になる
  （2026-08-26 に実際に踏んだ）。また旧記載の母数「n=96」は同期間・同方法で再現すると n=169 になり**再現しない**
  （中央値・p90・max は一致するので同じデータではある）＝**母数は引用しない**。
  **超えそうなら、まず §6 の軸「共有文脈を人数分読み直すか」で独立に割れるかを問う**:
  ①割れる（別ファイル・別真因系・必読がほぼ交わらない）→ **領域で縦割り**（各体が調査→実装を完結。コスト中立以上＋
  監督チェックポイントが増える品質便益つき） ②割れない（直列依存・共有文脈が厚い）→ 分業は重複読み実測≈4倍＝
  **割らずに長走行を許容**し、緩和策（watchdog・進捗の外部化・中間チェックポイント）で
  ⚠️ **「Nターン走ったら一旦部分報告せよ」と仕様に書いても実行されない**（2026-09-07 実測＝子が「サブエージェントはターン終了時にしか本文を返せないため実行できていない」と報告）。
  中間報告が要るなら **①親から `SendMessage` で問う（transcript 保持＝安い）か ②タスクを分割起動する**のどちらかしかない。
  故障モードだけ潰す。健全な長走行は実在する（2026-07-25 の実機検証3件束ね＝113 tool uses で全 PASS）。コミットは都度でよい。
- 並列化の価値判断は §6 のコスト規律が正本（独立タスクの並走はコスト中立・分業型のみコスト増）。

## 1. 委譲仕様の書き方

- **必読リスト（読む順番つき）を仕様に書く**。監督が接地するのは正本の「所在」だけ（例外＝ADR/台帳など短い判断文書）。
- 曖昧語は質問で止めず**仮説分解**→検証可能な系統を全部モック化して見せる。
- 裁定が返ったら次の仕様に**「確定事項」として明文化**。書かない再委譲は自己判断＝逸脱の温床。
- バグ修正委譲は「症状隠し禁止・真因を報告に明記」＋疑いどころ（先入観禁止と併記）。
- 完了定義を外給: 存在確認可能な成果物・自己diff・ゲートGREEN・報告様式。
- **機械置換バッチを委譲するときの2つの盲点**（2026-07-13 F余白離散化で実測）:
  ①**不変リストは全数列挙でないと守られない**——「構造インセット 92/210 は不変」と代表2値だけ書いたら、
  同種の 96/90/60/44 は律儀に丸められた。カテゴリ名でなく**値の全数列挙**を仕様に書く（0件になるまで
  洗い出してから委譲する）。②**較正値クラスの見落とし**——コメントの算術（「14dp＋leading 13.5＝27.5≒
  折り返し行間」）や境界等式（`Adaptive(minSize126)＋gap20＋側24×2＝ちょうど320dp→2列`）に参加する値を
  単独で丸めると、**等式が壊れてコメントが嘘になる**。事前に「数値を含む近傍コメント」を grep して
  除外指定するか、事後レビューで変更値の近傍コメントの算術との矛盾を全数突合する。
- **想定ターン規模を仕様に書き、大タスクは委譲前に分割（子1体 ≤30ターン目安）**。委譲コストの支配項は
  子の走行長（較正値は**§0 が正本**＝指標は `tool_uses` でありターン数ではない。⚠️ 旧記述「実測 2026-08-06 n=96: 中央値45.5ターン・p90 103」は §0 で撤回済みの数値をこの行だけが持ち続けていた＝2026-09-05 に削除）。p90級は設計ミス＝割る。
- 定型規律は SubagentStart hook が自動注入（正本＝`.claude/hooks/inject_subagent_briefing.py`）＝仕様には
  **タスク固有の内容だけ**（必読・確定事項・成果物・所有権）。矛盾時は仕様が勝つ。
- 実装系の深さは `.claude/agents/general-purpose.md` で effort: xhigh 固定（モデル制御＝memory `claude-code-subagent-model-control`）。

## 2. 受け取り（知見の搾り取り）

- 報告に**行数上限（≤8〜25行）と必須項目**: 変更ファイル／真因・機序／較正値・判断／ゲート出力要約（失敗数まで）。
- 狙いは要約でなく**外部化**——較正値・真因・判断がレポートに落ちた瞬間、エージェントの文脈は捨てられる。
- 裁定・知見は**即・台帳へ**（ADR/plan/handover/knowledge）。台帳が正本を持てば監督の文脈も捨てられる＝本当の「圧縮」。

## 3. 検収は機械検分のみ（全文diffは読まない）

- 監督が見るのは**出力数行のコマンドだけ**: `git status --short`・`git diff --stat`・`grep -c` 禁止API・構文チェック・ゲート再実行の tail。
- 全文diffレビューは委譲先の自己検証。**自己申告GREENは信じず、ゲートは監督が自分で再実行**。
- 残余リスクは ①mockview目視 ②実機目視 ③テスト の多重で受ける。
- **監督は視覚検分をしない**（2026-07-19 指示「撮影など目視はしないで、オーケストレーションに徹して。あくまでね」）
  ——監督のコンテキストは司令塔業務（委譲・検収・裁定の往復）に温存する。画像読取は消費が大きい。
  **視覚裁定はユーザーの `mockview` 目視が正路**。
  例外は**ユーザーが「目視・裁定も監督自ら」と明示指示したときだけ**＝そのときの手順（headless Chrome＋
  `adb screencap` のパイプラインと2つの罠）は memory `workflow-supervisor-headless-visual-judgment` を開く。

## 4. 継続 vs fresh の境目

1. 要る知見は外部化済みか（未なら先に搾り取る）
2. 旧文脈は中立か有害か——微調整＝resume／方向転換・作り直し・「実物Xを使え」系＝fresh
3. 決まらない時だけサイズ・時間: resume可＝TTL内×累計2回まで／fresh＝TTL跨ぎ or 3回目 or 30万超
- fresh の固定費は必読を絞って最小化。役目を終えたエージェントは閉じる（再送しない）。
- ⚠️ **resume は「元エージェント起動時の model」を引き継ぐ**（親セッションの現在モデルではない。SendMessage に
  モデル指定の口も無い）＝**モデル枠切れからの復旧は fresh 起動＋model 明示しかない**。2026-08-05 実証:
  Fable 5 の月次枠が切れて停止した3体を、セッションを Opus 5 へ切り替えてから resume したが**3体とも
  同じ枠切れエラーで即再死**した。

## 5. 並行運転

- **同一ファイルを触るエージェントは並走させない**（監督がキューを持つ）。ファイル素が交わらないものは積極並走。
  **同一ツリーで4〜6体を並列委譲するときの較正**（2026-07-17 M/P/J スキン実装・約15委譲で実測）＝
  **編集ファイルの所有権を互いに素に全数列挙**する（「これ以外の編集は絶対禁止」＋import は可、と明記）。
  エントリ画面ファイルは 1画面=1エージェント に割る。**最終ゲートは監督が回す**（各体の自己申告では担保にならない）。
- **重いジョブは並列で重ねず直列化する**——Gradle ビルド/テスト・PDF抽出・生成系サブは**同時に1つ**。
  2026-07-17、Gradle の record+verify をバックグラウンドで走らせながら PDF 抽出エージェントを並走させたところ
  **ノートPCが過負荷になり Claude Code プロセスごと落ちた**（「ノートPCが悲鳴を上げていました。もっと優しくして」）。
  ⚠️ Gradle は同一ツリー2本で「偽の赤」も出す（`/build`）。
  ⚠️ **2026-09-02 訂正＝「ノートPC」の資源根拠は現行機には当てはまらない**。実測は
  Threadripper PRO 3945WX **12C/20T・RAM 94GB**（着手時 load 1.40・空き 84GB）で、**9体並列**
  （うち Gradle を回す6体）を走らせても過負荷にならなかった＝**重いサブを「同時に1つ」に絞る根拠を資源に置かない**。
  **それでも直列化は維持する**——理由が資源でなく**ゲート健全性の側**にあるため（同一ツリー2本＝偽の赤）。
  `tools/gwlock.sh` がツリー単位で排他するので、並列に出しても壊れず**待つだけ**になる
  （待ちが惜しいなら worktree で別ツリーにするのが唯一の道）。
- Gradle 等のビルドは並走させず監督の最終ゲートで一括。完了通知前に結果を予測しない・同じファイルを触らない。
- **「待ちます」駐機はストールと別の既知故障モード**（2026-08-06 実害2件・機序の正本＝
  `docs/knowledge/subagent-idle-stop-parks-forever.md`）: 子が background 完了通知を当てにしてターンを終えると
  子ゼロ停止＝完了扱いで駐機。**完了通知の result が「待つ」宣言だけなら即 SendMessage で再開**（transcript 保持
  ＝一発復旧の実測2件）。予防は SubagentStart 注入の FOREGROUND_RULE が自動配布。
- **ストール（Stream idle timeout）は珍しくない**。親は自走では目を覚ませない＝**長走行の子には派遣時に watchdog を装備**:
  Bash run_in_background の `until` ループで output ファイルの mtime 停滞を検知して1回通知させる。
  **閾値は 30〜40分以上に取る**（2026-08-06 ユーザー指示で旧値 >4分 から改訂）——mtime が動くのはツール呼び出しの瞬間だけで、
  **難問の長考中は正常でも30分超まったく更新されない**。短い閾値は「考えている子」を殺し、再開のたびに
  文脈の再構築を強いる（同日、1体を4分間隔で6回中断させた実害）。**簡単に中断させないことが既定**＝
  疑わしいときは待つ側に倒す。
  復旧＝TaskStop→SendMessage 再開。子は5分TTLのため復旧時は全量再write（1.25×）を織り込んで fresh と比較。
  停止自体は fresh 切替の理由にならない（判定は §4 のみ）。
- untracked WIP は**実機投入のたびに scratchpad へ版スナップショット退避**（v6 書き換えで v5 実機OK版を失った実害から）。

## 6. コスト規律（2026-07-24 実測。数値正本＝memory `feedback-subagent-context-hygiene`）

- **並列の判別軸は「共有文脈を人数分読み直すか」**。独立タスク（別ファイル・別成果物）の並走はコスト中立で
  時間短縮が無料＝積極的に使う（1体に直列でやらせるより前タスクの担ぎ賃が消える分むしろ安いことも多い）。
  **1つのタスクを速くするための分業だけがコスト増**（同じ仕様・ファイルを人数分重複読み＋統合。実測≈4倍）＝時間をコストで買う行為と自覚して使う。
- TTLは**親1h・子5m**。キャッシュミス再writeは親側でも頻発（モデル/effort切替・CC更新・放置）。
- 最大の節約レバーは**親メインの担ぎ賃**＝フェーズ境界fresh・台帳外部化の徹底が先。
- **探索委譲（成果物が要約で足りる調査）は sonnet 固定・haiku 不使用**。モデルは Agent 呼出時の `model` 指定か
  agent 定義 frontmatter で制御する（旧記述「Agent ツールは env `CLAUDE_CODE_SUBAGENT_MODEL` で opus 固定＝headless
  `claude -p --model sonnet` で迂回」の env 固定は 2026-08-06 に解除済み＝該当 env は現存しない。headless 迂回も引き続き可）。
  **モデル解決の優先順（上が強い）**: ① env `CLAUDE_CODE_SUBAGENT_MODEL`（⚠️ 設定されていると呼出時指定より
  **黙って勝つ**罠。現在このマシンでは未設定＝②以下が素直に効く）→ ② 呼出時 `model` → ③ `.claude/agents/<name>.md`
  frontmatter の `model:` → ④ **親セッションのモデルを継承**（省略＝`inherit`）。agents 定義が1つも無いと全サブが
  メインのモデルをそのまま継承する（メインを fable5 にした瞬間サブ5体も fable5 になったのはこれ＝設計どおり）。
  **`effort` は frontmatter でしか指定できない**（呼出時パラメータに口が無い）。
  プロンプトに「Read/Grep/Globのみ・許可を求めず代替で進める」明記。
  実装が続く調査は general-purpose（memory `feedback-investigate-then-implement-same-agent`）。

## 7. ループの型（1画面=1サイクル）

モック委譲（仮説N案）→機械検分→mockview一括提示→ユーザー裁定→確定事項を明文化して翻訳委譲→監督ゲート再実行
→APK→実機投入→ユーザー目視→（差し戻しは真因指定で再委譲）→目視OK後にまとめてコミット提案。
台帳（plan/handover/ADR）は各裁定の直後に書く——コミット時にまとめては文脈が持たない。
