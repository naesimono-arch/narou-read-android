# /orchestration — 司令塔モードの運用規範

> 出自: 2026-07-19 リッチ化ラウンド（星図M深空）。ユーザー評価「大変素晴らしい運用」を受けて手順化。
> 原則の背後にある実測・境目計算＝auto-memory `feedback-subagent-context-hygiene`（定量指標つき）。

## 大原則: 監督の文脈に入れてよいのは「レポートと統計」だけ

監督は**判断**（仕様の翻訳・裁定の受け渡し・検収・台帳）に徹し、**読む・作る**はエージェントに置く。
迷ったら「これは私が読む必要があるか？ エージェントに読ませてレポートで受けられないか？」と自問する。

## 1. 委譲仕様の書き方（ユーザーの言葉の翻訳）

- **必読リスト（読む順番つき）を仕様に書く**——監督は編集起点ファイルも大きなモックも開かない。
  エージェントに読ませ、監督が接地するのは正本の「所在」だけ（例外＝ADR/台帳など判断に直結する短い文書）。
- **曖昧語は質問で止めず仮説分解**: 「ぼやっとしてる？彩度？」→ 検証可能な仮説3系統（構造/色彩/解像）を
  全部モック化して見せる（memory `feedback-build-dont-ask-iterate` の司令塔版）。
- 裁定が返ったら、次の仕様に**「確定事項」として明文化**（例:「形=c・色=b・場=a・0.42不可侵」）。
  確定を書かない再委譲は、エージェントの自己判断＝逸脱の温床。
- バグ修正の委譲には**「症状だけ隠す修正禁止・真因を報告に明記」**と疑いどころ（ただし先入観禁止と併記）を書く。
- 完了定義を外給する（Opus処方と同じ）: 存在確認可能な成果物・自己diff・ゲートGREEN・報告様式。
- **定型規律は SubagentStart hook が自動注入済み（2026-07-19〜）**＝委譲仕様に毎回書かない。
  自動注入の内容（`.claude/hooks/inject_subagent_briefing.py` が正本）: 実装系（general-purpose/claude）＝
  コミット/adb/正本モック変更の禁止・真因規律・自己diff全量確認・testDebugUnitTest ゲートコマンド・
  日本語「なぜ」コメント・報告様式≤25行／調査系（Explore/Plan）＝報告≤25行・結論から・file:line・推測明記。
  **委譲仕様にはタスク固有の内容だけ書く**（必読リスト・確定事項・完了定義の成果物・所有権）。
  矛盾時は委譲仕様が勝つ（注入文にもその旨明記済み）＝定型を上書きしたい時は仕様に書けばよい。
- 実装系サブエージェントの深さは `.claude/agents/general-purpose.md`（同名上書き定義）で **effort: xhigh 固定**。
  モデルは env opus 固定と併存（機序＝memory `claude-code-subagent-model-control`）。

## 2. 受け取りの構造化（知見の搾り取り）

- 報告に**行数上限（≤8〜25行）と必須項目**を課す: 変更ファイル／真因・機序／較正値・判断／ゲート出力要約（失敗数まで）。
- 狙いは要約ではなく**外部化**——較正値・真因・判断がレポートに落ちた瞬間、エージェントの文脈は捨てられる。
- 受け取った裁定・知見は**即・台帳へ**（ADR/plan/handover/docs/knowledge）。台帳が正本を持てば監督の文脈も捨てられる状態になる＝これが本当の「圧縮」。

## 3. 検収は機械検分のみ（全文diffは読まない）

- 監督が直接見るのは**出力数行のコマンドだけ**: `git status --short`（所有権違反検出）・`git diff --stat`（規模）・
  `grep -c` 禁止API・`node --check` 等の構文・ゲート再実行の tail 数行。
- **全文diffレビューは委譲先の自己検証**（完了定義に「自分でdiffして差分範囲を確認」を入れる）。
  自己申告GREENは信じず、**ゲートは監督が自分で再実行**する。
- 残余リスク（虚偽申告・微妙な文言改変）は ①ユーザーのmockview目視 ②実機目視 ③テスト の多重で受ける設計。
- 視覚品質の目視検分を監督はしない（memory `feedback-orchestrate-dont-inspect-visuals`）。

## 4. 継続 vs fresh の境目計算

判定順（詳細な実測値は memory `feedback-subagent-context-hygiene`）:
1. 要る知見は外部化済みか（未なら先に搾り取る）
2. 旧文脈は新タスクに中立か有害か——微調整＝resume／方向転換・作り直し・「実物Xを使え」系＝fresh
3. 決まらない時だけサイズ・時間: resume可＝TTL内×累計2回まで／fresh＝TTL跨ぎ or 3回目 or 30万超
- fresh の固定費は必読リストを絞ることで最小化。役目を終えたエージェントに再送しない（＝閉じる）。

## 5. 並行運転の規律

- **同一ファイルを触るエージェントを並走させない**（Color.kt 等の共有ファイルは直列化。監督がキューを持つ）。
- モック生成×コード修正のように**ファイル素が交わらないものは積極的に並走**。
- Gradle 等のビルドは並走させず、監督の最終ゲートで一括。
- 完了通知が来るまで結果を予測しない・先回りで同じファイルを触らない。
- **ストール対処（2026-07-19 実測3件）**: サブエージェントの Stream idle timeout は珍しくない。無応答の疑いは
  output ファイルの mtime を `stat` で機械判定（10分更新なし＝ストール確定）→ TaskStop→SendMessage 再開で
  文脈保持のまま復旧する。**停止は fresh 切替の理由にならない**（fresh 判定は §4 の文脈有害性・累計だけで行う）。
- **untracked WIP の版管理**: コミット前のファイルに版を重ねる探索ループでは、**実機投入のたびに scratchpad へ
  版スナップショットを退避**する（v5 実機OK版のコードが v6 全面書き換えで消え、差し戻し先を失った実害から）。

## 6. ループの型（1画面=1サイクル）

モック委譲（仮説N案）→ 監督の機械検分 → mockview 一括提示 → ユーザー裁定 → 確定事項を明文化して翻訳委譲
→ 監督ゲート再実行 → APK→実機投入 → ユーザー目視 → （差し戻しなら真因指定で再委譲）→ 目視OK後にまとめてコミット提案。
台帳（plan/handover/ADR）は各裁定の直後に書く——コミット時にまとめて書こうとすると文脈が持たない。
